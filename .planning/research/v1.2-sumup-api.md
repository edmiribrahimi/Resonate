# SumUp API Research for Resonate v1.2

**Researched:** 2026-03-06
**Domain:** SumUp REST API -- deeper integration beyond checkout/webhooks
**Overall confidence:** HIGH (verified via OpenAPI spec, official docs, multiple sources)

---

## Executive Summary

SumUp espone una REST API ben strutturata con endpoint raggruppati in: Checkouts, Transactions, Refunds, Customers, Payouts, Receipts, Merchants, Members/Roles. Il progetto Resonate attualmente usa solo 3 endpoint (create checkout, get checkout, refund transaction). Per il milestone v1.2, gli endpoint piu rilevanti sono: **Transactions History** (riconciliazione e dashboard pagamenti), **Refunds** (rimborsi programmatici, gia parzialmente implementato), **Payouts** (tracking dei bonifici ricevuti), e **Receipts** (dati ricevuta per email conferma).

L'autenticazione attuale tramite API key (`SUMUP_API_KEY`) e sufficiente per tutti gli endpoint necessari. Non serve migrare a OAuth 2.0 a meno che non si voglia operare su conto di altri merchant.

Rate limits non sono documentati pubblicamente da SumUp. Questo e un rischio da mitigare con caching e retry logic.

## 3. Authentication

### Metodi Disponibili

| Metodo | Caso d'uso | Stato Resonate |
|--------|------------|----------------|
| **API Key** | Integrazioni single-merchant, server-to-server | **IN USO** -- `SUMUP_API_KEY` |
| **OAuth 2.0** | Multi-merchant, autorizzazione delegata | NON NECESSARIO |
| **Affiliate Key** | Card-present (terminali fisici) | NON NECESSARIO |

### Scopes Necessari per v1.2

| Scope | Endpoint | Stato |
|-------|----------|-------|
| `payments` | Checkouts, Refunds | Gia attivo (crea checkout e rimborsa) |
| `transactions.history` | List/Get Transactions | **DA VERIFICARE** -- potrebbe servire attivazione |
| `user.profile_readonly` | List Payouts, Get Merchant | **DA VERIFICARE** |
| `payment_instruments` | Customers, Card Tokenization | NON NECESSARIO per v1.2 |

**Nota critica sulla Refunds API:** La documentazione SumUp specifica che i rimborsi richiedono un access token ottenuto tramite **Authorization Code flow**, NON tramite Client Credentials flow. L'attuale implementazione usa un API key statico. Verificare che funzioni correttamente in produzione, oppure potrebbe essere necessario un token OAuth per i rimborsi.

### Token Management

- API keys non scadono (gestibili dal dashboard SumUp)
- OAuth tokens scadono e richiedono refresh
- Per l'uso attuale (single-merchant) l'API key e sufficiente

## 4. Transactions History API -- Dettaglio

Questo e l'endpoint piu importante per v1.2 (dashboard admin).

### `GET /v2.1/merchants/{merchant_code}/transactions/history`

**Query Parameters:**

| Parametro | Tipo | Descrizione |
|-----------|------|-------------|
| `transaction_code` | string | Filtra per codice transazione specifico |
| `statuses[]` | array | `SUCCESSFUL`, `CANCELLED`, `FAILED`, `REFUNDED`, `CHARGE_BACK` |
| `payment_types[]` | array | `ECOM` (rilevante per Resonate), `CASH`, `POS`, `RECURRING`, etc. |
| `entry_modes[]` | array | Include `APPLE_PAY`, `GOOGLE_PAY`, `QR_CODE_PIX`, etc. |
| `types[]` | array | `PAYMENT`, `REFUND`, `CHARGE_BACK` |
| `oldest_time` | ISO8601 | Transazioni create dopo questa data |
| `newest_time` | ISO8601 | Transazioni create prima di questa data |
| `changes_since` | ISO8601 | Transazioni modificate dopo questa data |
| `limit` | integer | Max risultati per pagina (default: 10) |
| `order` | string | `ascending` / `descending` |
| `oldest_ref` / `newest_ref` | string | Paginazione cursor-based |
| `users[]` | array | Filtra per email merchant |

**Risposta:**

```json
{
  "items": [
    {
      "id": "uuid",
      "transaction_code": "string",
      "amount": 25.00,
      "currency": "EUR",
      "timestamp": "2026-03-06T10:00:00Z",
      "status": "SUCCESSFUL",
      "payment_type": "ECOM",
      "type": "PAYMENT",
      "card_type": "VISA",
      "product_summary": "string",
      "refunded_amount": 0,
      "fee_amount": 0.65,
      "payout_date": "2026-03-08",
      "payout_type": "BANK_ACCOUNT",
      "simple_status": "SUCCESSFUL"
    }
  ],
  "links": [
    { "rel": "next", "href": "limit=10&oldest_ref=..." }
  ]
}
```

**Paginazione:** Cursor-based tramite `oldest_ref`/`newest_ref`. Il campo `links[].href` contiene i parametri per la pagina successiva.

### `GET /v2.1/merchants/{merchant_code}/transactions`

Recupera una singola transazione. Richiede **uno** di questi query params:
- `id` (UUID)
- `transaction_code`
- `internal_id`
- `foreign_transaction_id`
- `client_transaction_id`

**Risposta include campi aggiuntivi:** `fee_amount`, `vat_amount`, `tip_amount`, `card` (last_4_digits, type), `products[]`, `vat_rates[]`, `transaction_events[]`.

### `POST /v0.1/me/refund/{txn_id}`

**Gia implementato** in `src/lib/sumup.ts`.

| Aspetto | Dettaglio |
|---------|-----------|
| Rimborso totale | Body vuoto `{}` |
| Rimborso parziale | `{ "amount": 24.42 }` |
| Risposta | `204 No Content` |
| Fee | Le commissioni SumUp sulla transazione originale NON vengono rimborsate |
| Metodo rimborso | Accreditato sul metodo di pagamento originale |
| Limite temporale | Non documentato esplicitamente |

**Limitazione importante:** La documentazione afferma che i rimborsi richiedono un token ottenuto tramite Authorization Code flow. L'attuale implementazione usa `SUMUP_API_KEY` come Bearer token. Questo funziona per i checkout (scope `payments`), ma potrebbe non funzionare per i rimborsi. Da testare in sandbox.

## 8. Webhooks

### Stato Attuale

| Aspetto | Dettaglio |
|---------|-----------|
| Evento supportato | `CHECKOUT_STATUS_CHANGED` (unico evento) |
| Payload | `{ "event_type": "CHECKOUT_STATUS_CHANGED", "id": "checkout-id" }` |
| Configurazione | Parametro `return_url` nella creazione checkout |
| Retry policy | Backoff esponenziale: 1min, 5min, 20min, 2h |
| Risposta attesa | Qualsiasi 2xx, body vuoto |
| Sicurezza | NESSUNA firma/HMAC -- verifica obbligatoria tramite `GET /checkouts/{id}` |

### Limitazioni Webhook

- **Un solo tipo di evento** -- non ci sono webhook per rimborsi, payouts, o altre azioni
- **Nessuna firma crittografica** -- chiunque puo inviare un POST al webhook endpoint (mitigato dalla verifica via API)
- **Nuovi eventi possibili** -- SumUp puo aggiungere nuovi event_type senza preavviso. Il codice attuale gestisce correttamente questo caso (ignora event_type sconosciuti)

## 9. Rate Limits

**SumUp NON documenta pubblicamente i rate limits.** Questo e stato verificato cercando nella documentazione ufficiale, OpenAPI spec, e fonti web multiple. Nessun riferimento a limiti specifici.

**Raccomandazioni:**
- Implementare retry con backoff esponenziale per 429 responses
- Cachare le risposte di list transactions lato server (Supabase o in-memory)
- Non fare polling aggressivo -- usare i webhook come trigger primario
- Per la dashboard admin, caricare dati on-demand con paginazione, non batch completi

## 13. Gotchas e Limitazioni

### Critico

1. **Nessuna firma webhook.** SumUp non invia un HMAC o firma con i webhook. L'unica protezione e verificare lo stato checkout tramite API dopo ogni notifica. L'implementazione attuale lo fa correttamente (`getCheckout(body.id)` nel webhook handler). Non rimuovere mai questa verifica.

2. **Refund richiede Authorization Code flow?** La documentazione refund dice esplicitamente: "you _cannot_ use an access token obtained via the Client credentials flow". L'API key potrebbe funzionare (e un terzo tipo di auth), ma va verificato in sandbox prima di esporre il rimborso nella UI admin.

3. **Fee SumUp non rimborsabili.** Quando si rimborsa una transazione, le commissioni SumUp sulla transazione originale non vengono restituite. L'admin deve saperlo.

### Importante

4. **Paginazione cursor-based nelle transazioni.** Non si possono fare "salta alla pagina 5". Si naviga avanti/indietro con `oldest_ref`/`newest_ref`. La dashboard admin deve implementare infinite scroll o navigazione prev/next.

5. **Filtro `payment_types[]` per ECOM.** Tutte le transazioni Resonate sono `ECOM` (e-commerce). Usare questo filtro nella dashboard per escludere eventuali transazioni da terminale fisico.

6. **`checkout_reference` deve essere unico per l'applicazione.** Gia gestito dal codice attuale (usa UUID o purchase ID).

7. **Checkout expiration.** I checkout creati scadono (10 min per card widget, 30 min per hosted). Il cleanup via `DELETE /v0.1/checkouts/{id}` e opzionale -- SumUp li gestisce internamente -- ma utile per pulizia dati.

### Minore

8. **Campo `product_summary` nelle transazioni.** Corrisponde al `description` passato alla creazione checkout. Usarlo per mostrare "Ticket - Event Name" o "Drinks - Event Name" nella dashboard.

9. **`simple_status` vs `status`.** Il campo `simple_status` nelle transazioni ha piu granularita: `SUCCESSFUL`, `PAID_OUT`, `REFUNDED`, `CHARGEBACK`, etc. Usare questo per la dashboard.

10. **CSV export payouts.** L'endpoint payouts supporta `format=csv`. Utile per export contabile senza parsing JSON.
