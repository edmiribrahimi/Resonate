    Indexes, all IF NOT EXISTS: production_plan (date); production_plan (series_id, number);

    public.production_pipeline_rule — one row per (format, piece kind) the pipeline owes:
    id, format_id uuid NOT NULL REFERENCES public.formats(id) ON DELETE CASCADE,
    piece_kind text NOT NULL, anchor_kind text NOT NULL, anchor_weekday integer,
    anchor_direction text NOT NULL, derivable boolean NOT NULL DEFAULT true,
    episodes_from_lineup boolean NOT NULL DEFAULT false, episode_count integer,
    note text, created_at.
    Named constraints: production_pipeline_rule_format_kind_unique UNIQUE (format_id,
    piece_kind); production_pipeline_rule_kind_check mirroring the same six piece kinds;
    production_pipeline_rule_anchor_kind_check CHECK (anchor_kind IN ('self',
    'next_edition','next_edition_listing')); production_pipeline_rule_direction_check
    CHECK (anchor_direction IN ('on','before','after')); and
    production_pipeline_rule_weekday_check CHECK (anchor_weekday IS NULL OR anchor_weekday
    BETWEEN 1 AND 7), ISO-8601 with Monday = 1.

    THE STORAGE FORM IS (anchor kind, weekday, direction) AND NEVER A DAY OFFSET, and the
    table comment must say why in the project's own words: the night falls Friday OR
    Saturday, so the same Tuesday sits 4 days before a Saturday and 3 before a Friday. A
    planner that stores offsets sees two rules where there is one and flags a perfectly
    correct night as an error. It has already happened once — a check written during the
    phase discussion reported a night as out of rule on three pieces, and it was the check
    that was wrong (D-44-25).

    Seed the rules from the published weekday table, resolving format_id by subselect on
    the public format code rather than by a hard-coded uuid, each INSERT ending
    ON CONFLICT (format_id, piece_kind) DO NOTHING:
      - the satellite format: listing (self, Tue, before, derivable); tonight (self, on the
        night's own day, derivable); recap (self, Mon, after, derivable); livecut (self,
        Mon, after, derivable).
      - SunSet: livecut (self, Mon and Tue after — two episodes, episode_count 2,
        derivable); listing (self, Tue, before, derivable FALSE) with a note carrying the
        measured reason: the anticipation is 11 or 18 days and is not a fixed number, so
        nothing may derive it (D-44-23).
      - the night: timetable (self, on the night's own day, derivable — 7 of 7, which
        corrects the module's older parenthetical); livecut (next_edition, Tue/Wed/Thu of
        that edition's ISO week, derivable, episodes_from_lineup TRUE and episode_count
        NULL, because three is not a constant — one archived edition carries two);
        after_movie (next_edition_listing, Mon, before, derivable); listing (self, Tue,
        before, derivable FALSE) with the note that the night's listing is no more derivable
        than SunSet's — a Tuesday one to two and a half weeks out, three distinct
        anticipations across six editions.
      - the Nizza series: listing (self, Tue, before, derivable); livecut (self, Mon, after,
        derivable, episode_count 1 — the light pipeline).
      - MotionLab: seed the SAME four rows as the satellite format, and add a note saying
        the weekday of the night itself is a SEGNAPOSTO and not decided
        (`production-calendar.md`, gate segnaposto dichiarato). MotionLab has zero dates in
        the calendar (D-44-19); the rows exist so that the day it has one, the checklist
        knows what it owes.

    Format codes and series names used here are the five already published in
    `.claude/rules/production-calendar.md` and in Phase 36's own migration; NO VENUE WORD
    and NO DATE is written by any statement in this file. If a format code has no row in
    public.formats, the subselect inserts nothing — that is the correct behaviour and the
    comment should say so rather than leaving a silent zero.
