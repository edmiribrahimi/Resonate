  <action>
    Create `src/lib/production/ics/reconcile.ts` exporting
    `reconcile(classified, existing, pipelineRules, now): ReconcilePlan`.

    `existing` is a plain snapshot of what the database already holds — plan rows, pieces,
    commitments — passed in by the caller. This module opens no connection and takes no
    client. **`reconcile` returns a plan and performs no write.** State this divergence from
    the analog in the docblock, in the shape `formats/actions.ts:41-51` uses for its own:
    `src/lib/door/classify.ts` has no write to withhold, this one does, and withholding it
    is what makes a dry run possible.

    `ReconcilePlan` carries, as separate lists:
      - `plansToInsert`, `plansToUpdate`, `piecesToInsert`, `piecesToUpdate`,
        `commitmentsToInsert`, `commitmentsToUpdate`, `checklistItemsToInsert`
      - `absences` — rows present in a previous run and absent from this file
      - `divergences` — the report of D-44-07
      - `unsupportedRecurrences`, `unclassified` — carried through from the classifier
    Every entry of every list carries a `source_uid` and, where it is a divergence or a
    finding, a REASON CODE. **No entry of any list carries a `SUMMARY`, a title, a venue
    word or a line-up.** A divergence is a UID and a reason, which is safe to read anywhere.

    THE KEY IS `UID` (D-44-03). 92 of 92 are unique and Apple maintains them across edits.
    Not the `SUMMARY`, which changes when the owner renames a night; not `(date, title)`,
    which both change; not a content hash, which changes on every edit — the opposite of
    what an identity needs. The write the caller performs is
    `ON CONFLICT (source_uid) DO UPDATE`, so a second run is a no-op BY CONSTRUCTION rather
    than by care. For an expanded recurrence the key is `UID` plus occurrence date, because
    one `UID` covers many days.

    THE NUMBER IS READ FROM THE FILE AND NEVER GENERATED. No counter, no `max()+1`, no
    second watermark — `party_series.highest_assigned` and `bump_series_watermark` already
    exist and must be respected, not re-implemented. When a known `UID` arrives carrying a
    different number, emit a DIVERGENCE and put the row in NEITHER update list. The database
    trigger of plan 44-04 is the layer that survives a caller who forgot this one; both
    layers exist on purpose.

    DISAPPEARANCE IS NOT DELETION. A row present before and absent now goes into `absences`
    with an `absent_since` value; it is never queued for deletion. It may be a `UID` change,
    a partial export or the wrong file — and a plan row already linked to an announced night
    must survive absence unconditionally, because deleting it would orphan a night with
    tickets on sale, which is exactly the harm D-44-06 separates the two tables to prevent.

    CHANGE DETECTION uses `SEQUENCE` (observed range 0 to 18, so it genuinely moves) and
    `LAST-MODIFIED` (present on all entries and maintained rather than copied). A
    **decreasing** `SEQUENCE` for a known `UID` is an anomaly: report it as its own
    divergence reason, never silently accept it.

    PIECES: a piece written in the file gets `origin: 'file'` and its date, and NOTHING
    RECOMPUTES IT (D-44-09b part 1) — an override is simply a date that differs from the
    rule, and the re-import re-reads it every time. For each piece a format OWES and the
    file does not carry, call `proposePieceDate` and emit either a row with
    `origin: 'proposed'` and its date, or a row with the matching `unresolved_reason` and no
    date. `conforms_to_rule` is computed for written pieces and stored for the divergence
    report only.

    CHECKLIST ITEMS: for each plan row, emit one `piece` item per owed piece plus the
    production steps of D-44-14 — venue confirmed in writing, dj confirmed, photo arrived,
    and the exhibition space's approval where the format is the one that needs it. Due dates
    come from the piece's resolved date where there is one and are left null where there is
    not. Emitting is `ON CONFLICT DO NOTHING` at the caller, so a re-import never duplicates
    an item and never un-ticks one.

    **THE IMPORT NEVER WRITES `event_parties`.** No list of `ReconcilePlan` targets it, the
    string does not appear in this directory, and the announcement act is the single bridge
    (D-44-06). Write that sentence, because it is the property that makes a re-import unable
    to move a night that has tickets on sale.
  </action>
