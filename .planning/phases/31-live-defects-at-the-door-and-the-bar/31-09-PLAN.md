<objective>
Make a refund leave something behind.

Four writers, one shape, one defect. Every path writes or updates the
`ticket_refunds` row and **then** deletes the ticket:

| Path | Line |
|---|---|
| `src/app/(public)/tickets/refund-actions.ts` — free / guest-list branch | `:126-143` |
| `src/app/(public)/tickets/refund-actions.ts` — paid branch, after the SumUp refund | `:166-183` |
| `src/app/(admin)/admin/finance/actions.ts` | `:100-110` |
| `src/app/api/cron/reconcile-refunds/route.ts` | `:109-121` |

Plan 31-04 changed `ticket_refunds.ticket_id` to nullable with `ON DELETE SET
NULL` and added four evidence columns that are deliberately **not** foreign keys:
`refunded_ticket_id`, `refunded_party_id`, `refunded_event_id`, `refunded_at`.
This plan fills them.

The ordering rule is the whole point: write the evidence **before** the
`delete()`. After the delete the values are unreadable, and that is the defect
Option B repairs.

Two further things are wrong in the same fourteen lines and are fixed here because
nowhere else will see them:

- **No writer checks the `delete()`'s error.** `guest_list_entries.ticket_id` is a
  foreign key with no `ON DELETE` clause (`20260310000000_guest_list.sql:56`), so a
  guest-list ticket's delete can raise a violation — and the refund is marked
  approved while the ticket survives, silently. Money and access then disagree, and
  nobody finds out. Plan 31-03's probe settled whether this fires; apply what it
  recorded.
- **The cron collapses every cause into one counter** (`reconcile-refunds/route.ts:125-127`
  — `catch { errors++ }`). `ticketing-payments.md` requires per-item progress, and
  `meta-gates.md` forbids a `catch` that makes distinct causes indistinguishable.

Purpose: `fetchEventRevenue` (`src/lib/analytics/event-queries.ts:84-92`) computes
refunds by collecting an event's ticket ids and querying `ticket_refunds` by those
ids. Both sides of that join are destroyed today, so `ticketRefundsTotal` is
structurally zero and the finance surface under-reports without any error. The
evidence columns are what makes that number real again, and what lets the door
admit a refunded holder at all.

Output: three files, four call sites.

        from the same value already used for `processed_at` so the two cannot drift

    existing `insert`, where `ticket.party_id` and `ticket.event_id` must be present
    in the ticket selection — check the select list and add them if missing, because
    after the delete they cannot be recovered.

    Add a one-line comment at each site: written before the delete, because after it
    these values are unreadable — which is the whole reason the columns exist.

    Do **not** touch `ticket_id`. It remains set to the same id it holds today; the
    database will null it on the delete now that the foreign key is
    `ON DELETE SET NULL`. `refunded_ticket_id` is the durable copy. Comment that
    duality once, in `refund-actions.ts`, so a reader does not "tidy up" the
    apparent duplication.

    do not stop deleting the ticket. Option A — soft-invalidating `tickets` — is
