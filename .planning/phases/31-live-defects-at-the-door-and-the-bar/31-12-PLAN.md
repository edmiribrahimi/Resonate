<objective>
Give the night a review list that is empty when nothing happened, and that says
*what kind* of thing happened when something did.

FIX-11 asks for four classifications and one deliberate absence:

- a **double read** — same ticket, same operator, same device, within a short
  window — is deduplicated and does **not** appear, because one person cannot enter
  twice from one door in seconds. **But it is counted**, because a rising count
  means the scanner's feedback is not visible at the door, and that is a defect to
  correct rather than to filter away. The counter is a signal about the hardware
  and the light, not about the guest;
- a **second unused ticket held by the same buyer for that night** is shown as "the
  same code was read twice", requiring no action beyond making the entry count add
  up;
- **two different devices, minutes apart** is the one duplicate that deserves
  attention: two people may have entered on one ticket;
- **an invalid signature** — a code this system did not issue — is the only outcome
  also surfaced to staff at the door when the network returns;
- a **refund issued after the night began** does not appear at all. It is
  accounting, and it belongs to the finance surface. One classification, two
  readers: the review list filters `refunded_after_night` out and finance queries
  the complement.

Three constraints that shape the implementation more than the feature does:

1. **The classification runs at read time, over `door_scan_events`, never at the
   scanner** (FIX-04a). That is also why a rule can be corrected after a night
   without redeploying anything to a phone that is holding a cached bundle.
2. **FIX-12 is a serialisation rule, not a second policy.** An organizer can
   already read every profile (`profiles_select_admin`,
   `20260224_rbac_migration.sql:151`), so restricting the technical view to a master
   is an interface affordance and must not be presented as a boundary. What *is*
   enforceable: the table stores no name and no email by construction, and the
   copyable view renders its columns straight, joining nothing. A plan that adds a
   `door_scan_events_select_master` policy has misread the requirement.
3. **FIX-13 is a negative requirement and needs a negative check.** No code path
   added here writes to `public.profiles`, and the list carries no per-member
   aggregate that would function as a label.

The surface lives under the **organizer** tree, beside
`events/[id]/{sales,tickets,guest-list,analytics}` — the owner's decision. Phase 34
collapses the duplicated admin and organizer trees and would otherwise have to
redirect a new top-level address.

**No notification path.** FIX-11 says the list raises no notification and asks for
no action. Nothing here sends an email, adds a badge to navigation, or writes a
counter anyone is pinged about.

Output: one pure module and one page-plus-client pair.
</objective>
