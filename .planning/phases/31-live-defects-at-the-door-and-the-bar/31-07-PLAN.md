<objective>
Make the check-in route say one of three things, prove the code was read, and
write down what happened before it answers.

Everything wrong at the door converges on this 144-line file.

- **Five of six outcomes are HTTP 200.** Lines 41, 44, 59, 66 and 101 are
  `NextResponse.json` calls with no status argument. Because `res.ok` is true in
  every one of them, `sync-manager.ts:36` deletes the queue entry on a conflict —
  so the only evidence that two people walked in on one ticket is destroyed at the
  moment it arrives. That is FIX-03, and it is a consequence of this file's shape,
  not of the sync manager's.
- **`offlineSync && directTicketId` skips verification entirely** (`:34-36`). A
  queued scan carries no evidence a code was ever read, and a body-supplied
  identifier reaches a service client that bypasses RLS. FIX-10.
- **`already_by_you` is produced at `:96` and read by nothing** — verified by grep
  across `src/`. Worse, the same-operator branch returns `valid: true`, so a
  re-read renders as a fresh green admission. FIX-04a forbids exactly this: the
  system must not classify the cause at the scanner.
- **A refunded ticket reaches `not_found`** (`:58-60`) and the scanner shows a red
  "Ticket not found" — a false refusal in front of a queue, on data the person
  cannot argue with. FIX-09 exists because of the opposite failure.
- **An Event Pass is refused.** `:63` tests `ticket.party_id !== partyId`, which is
  always true when `party_id` is NULL. No requirement named this defect; the
  asymmetry forbids it anyway.
- **Two anti-patterns to remove while here**: `:50-56` discards the `.single()`
  error, so "does not exist" and "there are two" are the same failure; and
  `:112-119` performs the check-in update with no error check at all, so a failed
  write returns a green screen to the door.

Purpose: this is the file the whole phase is named for. Everything else either
feeds it or reads what it wrote.

Output: `src/app/api/tickets/checkin/route.ts` and
`src/app/api/tickets/checkin/undo/route.ts`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| scanned code ↔ the server | An HMAC-signed static bearer token; possession is the only claim it makes |
| request body ↔ the service client | The service client bypasses RLS; anything from the body that reaches it is untrusted input |
| authenticated staff session ↔ this route | A `master` or `organizer` session; the route trusts the session, never a header |
| device clock ↔ server clock | `scanned_at` arrives from a phone and is evidence, not authority |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31-07-01 | Spoofing | `offlineSync && directTicketId` accepting a bare identifier as proof of a read, over an endpoint that then uses an RLS-bypassing client — any staff session can mark any ticket id it can obtain as checked in | mitigate | The branch is deleted; `verifyTicketToken` runs on every path; asserted by a grep returning 0 for both `offlineSync` and `directTicketId` |
| T-31-07-02 | Repudiation | A duplicate entry acknowledged and then destroyed, because the conflict was returned before it was persisted | mitigate | The `door_scan_events` insert precedes every return; a failed insert returns a retryable failure instead of a 409 |
| T-31-07-03 | Repudiation | An undo erasing who admitted a person, with nothing recording who reversed it | mitigate | `checked_in_by` is preserved; the undo is its own append-only row with its own operator; a failed insert aborts the undo |
