<objective>
Rebuild the offline store so that what the door knows locally is never quietly
destroyed.

Four defects live in this one file.

- **FIX-05, and it is the most damaging.** `cacheAttendees()`
  (`checkin-store.ts:84-130`) opens one transaction, walks the `by-party` index
  deleting every row for the party, then re-inserts from the server payload
  including `checkedIn: a.checkedIn` straight from the server. A member checked in
  offline sits in `pendingCheckins` with `attendees.checkedIn = true` written by
  `checkInLocally`. The server does not know. The next refresh writes `false` over
  it: the person standing inside reads as *Not arrived*, a re-scan looks like a
  first arrival, and the door count is wrong in the direction that produces an
  argument at the entrance.
- **FIX-06.** The transaction is genuinely atomic — the W3C IndexedDB spec is
  explicit that an aborted transaction rolls back and that overlapping read/write
  transactions are serialised, and the current code awaits only IDB promises
  inside it. So "momentarily empty" in the literal sense is not the live defect.
  What *is* live: the cache shrinks to whatever the server said, and the server
  may have said something a day old. Plan 31-01 removed the stale-response path;
  this plan adds the second layer, which is a guard that refuses to apply a
  payload that would shrink the cache, and **returns that refusal as a value**.
  Today the call site is `cacheAttendees(...).catch(() => {})`
  (`ScannerClient.tsx:170`), so a refusal has nowhere to surface.
- **FIX-07.** `pendingCheckins` is keyed by `id` — a `ticketId`, a
  `guestListEntryId`, **or a `membership_code`** (`:39-47`, `:252-263`). A
  membership code is party-independent, so the same member at two parties on one
  device writes the same key twice and the second `put` destroys the first. A
  double bill is one event with two parties, so this is not a corner case.
- **FIX-10.** `handleVerify(code)` receives the whole scanned string and
  `ScannerClient.tsx:348` immediately throws away everything but the id. The queue
  therefore carries no evidence that a code was ever read. The token is already in
  hand at scan time: keeping it costs nothing offline.

Purpose: this is the only IndexedDB module in the repository, it holds attendance
records for people who paid, and some of those rows are on a device that is
offline and cannot be audited. The version-3 upgrade is written copy-then-delete,
never delete-then-create.

Output: `src/lib/offline/checkin-store.ts` at `DB_VERSION` 3.
</objective>

    `versionchange` transaction, which rolls back as a unit if anything fails.
    Never `deleteObjectStore` before the copy: those rows are attendance records for
    people who paid, and some of them are on a device that is offline right now.

    New shape:

    - `attendees`, keyPath `"key"` where `key` is `` `${partyId}:${subjectType}:${subjectId}` ``.
      Value fields: `key`, `partyId`, `subjectType` (`DoorSubjectType`), `subjectId`,
      `name`, `email?`, `tierName?`, `ticketType`, `checkedIn`, `checkedInAt?`,
      `checkedInBy?` (an operator label, needed so the offline `already_recorded` can
      say who), `refundedAt?` (needed so a refund known at download time produces the
      same amber admit locally), `guestListEntryId?`, `lastSeenAt`.
      Indexes: `"by-party"` on `partyId`, and a **new** `"by-subject"` on `subjectId`.
      The `by-subject` index is what lets the offline path answer "in the cache, but
      for another night" as `wrong_night` locally instead of falling through to red.
    - `pendingCheckins`, keyPath `"key"`, same composite key. Value fields: `key`,
      `type` (`"ticket" | "guest" | "membership"`), `subjectId`, `partyId`, `token`
      (the full signed string exactly as scanned; `null` for a membership code or a
      guest entry, which have no signature to carry), `scannedAt` (device clock at
      the read), `deviceId`, `attempts` (number), `state`
      (`"pending" | "blocked"`), `lastAttemptAt?`.
    - `failedCheckins`, keyPath `"key"` — a new store. Same fields as a pending
      entry plus `reason: DoorNotValidReason | "unexpected_response"` and `failedAt`.
      An entry that can never succeed leaves the queue and lands here; it is not
      deleted, because a lost entry and a synced one are indistinguishable to a
      counter.
    - `members`, keyPath `"membershipCode"` — unchanged. A membership code is
      genuinely global.
    - `meta`, keyPath `"key"` — a new single-purpose store holding `{ key, value }`.

    Export `attendeeKey(partyId, subjectType, subjectId): string` — one helper, used
    by every producer of a key, so the format exists in exactly one place.

    Export `getDeviceId(): Promise<string>` — reads `meta` for key `"deviceId"`; if
    absent, generates one with `crypto.randomUUID()`, writes it, and returns it. It
    is stable per install, which is what `door_scan_events.device_id` being NOT NULL
    requires and what makes the `two_devices` classification possible at all. A
    second browser profile does not reproduce a second device id, and the runbook
    already says so.

    The upgrade body, for `oldVersion < 3`:
      - create `attendeesV3`-shaped stores under their final names by first
        renaming: create the new stores with temporary names, copy from the old,
        delete the old, and — since IndexedDB has no rename — create the new stores
        directly under the final names only if the old ones have already been
        deleted. Resolve this by giving the new stores their final names and
        deleting the legacy stores **after** the copies are queued in the same
        transaction; if the legacy store name collides with the new one, copy into a
        temporary store, delete the legacy one, then copy back. State which of the
        two routes you took in a comment, because a reader needs to know the copy
        happened before the delete.
      - `attendees` rows: derive `subjectType` from the legacy value —
        `isGuestListEntry === true` → `"guest_list_entry"`, otherwise `"ticket"` —
        and `subjectId` from `guestListEntryId ?? ticketId`. `partyId` is already

        `"pending"`.
      - Only IDB promises are awaited inside the transaction. One `await` on
        anything else turns the upgrade into a partial commit, and there is no test
        runner in this repository that could catch it.

    Keep the file's existing style: no class, no singleton object, one
    single-purpose exported `async function` per operation, each with a one-line

    Replace `cacheAttendees` with `mergeAttendees(partyId, rows): Promise<MergeResult>`,
    where `MergeResult` is `{ applied: true; merged: number }` or
    `{ applied: false; reason: "empty_payload" | "payload_smaller_than_cache" }`.
    Export the type. The refusal is a **value**, not an exception and not a log
    line: the caller in plan 31-11 has to render it.

    Before opening the write transaction, read two counts: the cached row count for
    the party (`countFromIndex("attendees", "by-party", partyId)`) and the pending
    queue count. Then:
      - if the payload is empty and the cache is not, refuse with `"empty_payload"`;
      - if the queue is non-empty and the payload is smaller than the cache, refuse
        with `"payload_smaller_than_cache"`.
    Refusing keeps the existing cache untouched. At the door "not in the list" and
    "not on the list" are indistinguishable, so a shrunken cache is a false refusal
    waiting to happen.

    The merge itself, in one transaction over `attendees` and `pendingCheckins`,
    with **no** `clear()` and **no** cursor-delete sweep:
      - compute `key` with `attendeeKey`;
      - read the local row and whether a pending entry exists for that same key;
      - write `{ ...local, ...identity fields from the row, key, partyId, subjectType,
        subjectId, lastSeenAt: now }`;
      - **the monotone rule** — if the local row says `checkedIn` and a pending entry
        exists for the key, keep `checkedIn: true`, keep the local `checkedInAt`, and
        keep the local `checkedInBy` (falling back to a "this device" label);
        otherwise take the server's values. A refresh may add knowledge; it may never
        subtract an admission that has not yet been reported. This is the same family
        as the three monotone guards in `meta-gates.md`;
      - carry `refundedAt` from the payload;
      - **rows absent from the payload are left alone.** Do not prune here. Pruning
        belongs to a party switch, and only for rows whose `lastSeenAt` predates the
        night — add `pruneParty(partyId, olderThanIso)` as a separate exported
        function so the pruning is a deliberate call rather than a side effect of a
        refresh.

    Give `cacheMembers` the same treatment: it currently calls `tx.store.clear()`
    (`:232`). Merge instead — put each member, leave the rest. The roster is the
    device's only way to resolve a membership code offline, and clearing it during a
    refresh is the same defect with a different store.

    Await only IDB promises inside the transaction, and `await tx.done` last.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| device storage ↔ the app | IndexedDB on a staff phone we do not control, holding attendee names and the member roster |
| server payload ↔ local cache | A payload that may be stale, partial, or both, arriving over a connection that reports itself as healthy |
| queued entry ↔ the check-in API | The queue is the only evidence a scan happened; whatever it drops, nobody can reconstruct |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31-05-01 | Tampering | A stale or partial server payload silently replacing a good local cache, turning admitted guests into "not arrived" | mitigate | `mergeAttendees` never clears; the plausibility guard refuses an empty or shrinking payload and returns the refusal as a value the screen must render |
| T-31-05-02 | Repudiation | An offline admission lost because a refresh reverted it before it synced | mitigate | The monotone rule: local-true with a matching pending entry always wins over a server `false` |
| T-31-05-03 | Repudiation | A queued entry destroyed by a second scan of the same membership code at a different party | mitigate | The composite key `partyId:type:subjectId`; two parties produce two keys |
| T-31-05-04 | Spoofing | A synced check-in indistinguishable from a hand-typed identifier | mitigate | The full signed token travels with the entry; the route re-verifies it (plan 31-07). This store stops discarding the signature at scan time |
| T-31-05-05 | Denial of service | An entry that can never succeed retried on every `online` and `visibilitychange` event, forever | mitigate | A named attempts cap, and `markFailed` moving the entry out of the queue while keeping it visible |
