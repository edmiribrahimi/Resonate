<objective>
Stop the queue from throwing away the evidence it exists to carry.

`sync-manager.ts` is 105 lines and contains three separate faults in fourteen of
them (`:26-40`):

- **`ticketId: checkin.id`** — the queued entry has no token, so a synced check-in
  is indistinguishable from a hand-typed identifier (FIX-10). Plan 31-05 gave the
  entry a token; plan 31-07 removed the route's bypass. This plan sends it.
- **`if (res.ok || res.status === 409)`** — the `409` branch was written against
  `/api/tickets/attendance`, which does return 409 (`:214-219`); the ticket route
  never has. Since every ticket-route failure was HTTP 200, `res.ok` was true and
  `markSynced` deleted the conflict — the one piece of evidence that two people
  walked in on one ticket, destroyed at the moment it arrived (FIX-03).
- **No `else` at all.** A non-ok, non-409 response falls through to the next
  iteration and is retried on every `online` event and every `visibilitychange`
  (`:87-99`), forever. Meanwhile the membership branch (`:52`) marks synced on
  `res.ok`, and `/api/membership/verify` returned HTTP 200 for an unknown code — so
  the same handler both retained dead entries and deleted live ones (FIX-08).

The nearest discipline analog in the repository is the reconciliation cron
(`api/cron/reconcile-refunds/route.ts:95-127`): copy its per-item `try/catch`
inside the loop and its returned counters, and **do not** copy its
`catch { errors++ }`, which is the exact anti-pattern FIX-08 exists to remove.

Purpose: with no error tracking in this project, the queue's own counters are the
only observer of a failed sync that exists. A count is only worth showing if
nothing has been silently added to or removed from it.

Output: `src/lib/offline/sync-manager.ts`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| queued entry ↔ the API | The queue is the only evidence a scan happened offline; what it drops cannot be reconstructed |
| response body ↔ the classifier | Failure was encoded at HTTP 200 across two routes before this phase; the body is now authoritative |
| staff session ↔ the drain | A session can expire mid-night with a full queue |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31-10-01 | Repudiation | A duplicate entry deleted from the queue on a 200-encoded conflict, destroying the only record that two people entered on one ticket | mitigate | The classifier switches on the body's `outcome`; `already_recorded` is dropped only because plan 31-07 persists the row before responding, and the coupling is written in a comment at the branch |
| T-31-10-02 | Spoofing | Synchronising a bare identifier as though a code had been read | mitigate | The token travels with the entry and the route re-verifies it; a version-2 entry with a null token is recorded as failed rather than replayed |
| T-31-10-03 | Denial of service | An entry that can never succeed retried on every `online` and `visibilitychange` event, forever | mitigate | The dead bucket moves it out of the queue; `bumpAttempts` enforces the named cap for the retryable bucket |
| T-31-10-04 | Repudiation | A whole night's queue discarded because an expired session returned 401 on every entry | mitigate | The blocked bucket keeps the entries, stops the retries, and is recoverable in one action through `retryBlockedAfterSignIn` |
| T-31-10-05 | Information disclosure | A retry storm against `/api/tickets/checkin` from a device whose session is invalid, on an endpoint with no rate limiting anywhere in the repository | mitigate | 401/403 stops retrying immediately rather than backing off; RATE-01 remains deferred and is recorded, not silently relied upon |
| T-31-10-SC | Tampering | npm installs | accept | This plan installs nothing; the research explicitly rejects a background-sync library, because it would hide the retries the requirement asks to expose |
</threat_model>
