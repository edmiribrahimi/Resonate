<objective>
Settle the two claims in this phase that were read from DDL and never executed,
before a migration is written on top of them.

`31-RESEARCH.md § Answer E` carries two findings marked **MEDIUM confidence** —
unambiguous in the migration text, never run against a database:

- **A1.** `ticket_refunds.ticket_id` is `uuid NOT NULL REFERENCES public.tickets ON
  DELETE CASCADE` (`20260227200000_ticket_refunds.sql:3`). All four refund writers
  insert or update the `ticket_refunds` row and then delete the ticket
  (`refund-actions.ts:139` and `:177`, `admin/finance/actions.ts:109`,
  `api/cron/reconcile-refunds/route.ts:120`). If the cascade behaves as the DDL
  reads, the delete that follows the refund destroys the refund record written one
  statement earlier — and `fetchEventRevenue` (`src/lib/analytics/event-queries.ts:84-92`)
  computes refunds by joining both sides of a relation that no longer exists, so
  the finance surface under-reports with no error.

- **A2.** `guest_list_entries.ticket_id` is `REFERENCES public.tickets(id)` with
  **no** `ON DELETE` clause (`20260310000000_guest_list.sql:56`), so the default is
  `NO ACTION`. Deleting a ticket a guest-list entry points at should raise a
  foreign-key violation — and `refund-actions.ts:139` does not check the delete's
  error. If so, a guest-list refund is marked approved while the ticket survives,
  silently, which is money and access disagreeing with each other.

Purpose: `meta-gates.md` — do not build on an unexecuted reading. The answer to A2
in particular changes the migration in plan 31-04: if the violation is real, that
migration must give `guest_list_entries.ticket_id` an explicit `ON DELETE SET NULL`.
Discovering this after the migration is applied means writing a second one.

Output: one document recording the statements run, the literal output, and the
consequence for the migration.
</objective>
