<objective>
Bring the membership path into the same contract, and stop a double bill from
reading as a conflict every time.

Three defects, and the first one fires tonight.

1. **`attendances` had no party column** until plan 31-04, and the insert here
   still writes only `event_id` and `user_id`. A double bill is **one event with
   two parties** — a sunset act and a night act, communicated as one evening — so a
   member who is checked in at both collides on the old
   `unique(event_id, user_id)` and the second scan comes back
   `already_checked_in` (`:124-141`). Not a rare conflict: a **false** conflict,
   every time, in front of a queue. The migration replaced that constraint with two
   partial unique indexes; this route's insert and its `23505` re-fetch must both
   gain the `party_id` predicate, or the re-fetch returns the wrong party's row.

2. **An unknown member code returns HTTP 200** with `{valid:false, status:"not_found"}`
   (`:94-96`). `sync-manager.ts:52` marks a membership entry synced on `res.ok`,
   which is `true` — so the entry is **silently deleted**. Meanwhile a permanent 400
   (`:78-83`) or 404 (`:105-110`) stays in the queue and is retried on every `online`
   event and every `visibilitychange`, forever. The pending count is therefore both
   inflated by dead entries and deflated by lost ones, which is precisely what
   FIX-08's *"so the pending count means something"* refers to. Fixing the sync
   manager without fixing this route re-creates the `res.ok` bug on the membership
   path the moment anyone touches it.

3. **The conflict cannot say who.** `:135-140` returns `member_name` and
   `checked_in_at` but not the operator — and `attendances.checked_in_by` exists
   (`schema.sql:236`); it is simply not selected. FIX-04 requires the third outcome
   to carry who recorded it and when, on both paths.

Purpose: half the door's scans are membership codes. A review list that sees only
tickets is a review list that is empty for the wrong reason.

Output: `src/app/api/membership/verify/route.ts`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated GET ↔ this route | Answers "valid / not valid" for a membership code with no session and no rate limit |
| authenticated POST ↔ this route | A `master`/`organizer` session, then the service client, which bypasses RLS |
| membership code ↔ proof | The code is a plain string with no signature; possession is the only claim, and the whole roster is cached on the device |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31-08-01 | Repudiation | A queued membership scan silently deleted because an unknown code answered HTTP 200 | mitigate | The unknown-code branch returns 422 with `not_valid`; the queue classifies it as permanently failed and keeps it visible instead of dropping it |
| T-31-08-02 | Denial of service (against a paying guest) | A member refused at the second act of a double bill because `unique(event_id, user_id)` collided | mitigate | `party_id` on the insert and on the `23505` re-fetch, matching the two partial unique indexes |
