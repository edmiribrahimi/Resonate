    **The decision this file has to take, and take out loud.** `production_section` holds
    both the manifesto rows and the visual rows, distinguished by its `section` column, and
    a single table cannot carry one policy per key without either splitting the table or
    writing a two-armed predicate. Write **two** policies on that table — Postgres ORs
    permissive policies, which is exactly the semantics wanted — each restricted by the
    `section` column:

    · `production_section_select_manifesto` — `USING ((SELECT
      private.has_capability('production.manifesto.manage')) AND section = 'manifesto')`
    · `production_section_select_visual` — the same shape for `visual`.

    Do the same on `production_open_question`, whose `section` column is nullable: a
    register entry with **no** section is a question about the brand rather than about one
    body of rules, and it is readable by a holder of **either** key. Write that arm
    explicitly rather than letting a null fall through a comparison, because `section =
    'manifesto'` is `NULL` — not `false` and not `true` — for a null column, and a policy
    that admits nothing on a null row would hide the register's most general entries with
    no error anywhere.

    **`TO authenticated` on every arm, and say why the asymmetry with the six calendar
    policies is deliberate**: for `anon` the predicate can only ever answer false, so the

    Discretion and written into the file's header so the owner reads it at the
    authorisation checkpoint of plan 45-08:** the dj photo archive gets a **third,
    private bucket**, `visual-archive`, and not the existing public one and not the
    quarantine bucket.

    Not the public bucket, because an archive photo **is not published** — the listing that
    uses it goes out two days before a night and the archive precedes the listing; a photo
    that is publicly reachable the moment it is filed is a publication nobody decided.
    Not the quarantine bucket, because quarantine has a **short life by design** and a
    cleanup written for quarantine would one day delete the archive; two lifecycles in one
    bucket is one lifecycle nobody can change safely.

    In one transaction:
    · Insert the bucket with `public = false`, `ON CONFLICT (id) DO NOTHING`, with a size
      limit and an allowed-MIME list matching the existing media path rather than invented.
    · **No `INSERT` policy for `authenticated`.** Bytes arrive through the server, on the
      existing path: client → **quarantine** → `POST /api/media/finalize` → service role
      strips metadata → service role writes here. The client never writes to this bucket,
      and the absence of the policy is what makes that true rather than the code's habit.
    · One `SELECT` policy for `authenticated`, asking
      `(SELECT private.has_capability('production.visual.manage'))`, scoped to this
      bucket's id.

      `20260810161000:244-264` uses: name the harmful repair — a public read policy "so the
      thumbnails load" — so it is recognised if it is ever proposed. Thumbnails on a gated
      surface load through a signed URL minted by the server, which is the same door.

    If any new function is added by this file, **`REVOKE ALL … FROM public, anon,
    authenticated` first and `GRANT EXECUTE … TO service_role` second, as two statements in
