The dj photo archive: the material half of D-45-08, on the upload path that already exists,
into the private bucket applied in plan 45-08.

Purpose: the listing goes out two days before a night, so **that night's photo cannot exist
yet**. From an artist's second date the piece is pulled from an archive somebody has to
build, and the visual section is where that archive lives. Building a second upload
mechanism beside the existing one would be a second thing to secure; this plan extends the
one that is already stripped, quarantined and gated.
Output: one new predicate, one extracted module, one new finalize arm, one uploader, one
page wired.

    **`may-upload.ts` — a second predicate, `mayUploadToVisualSection()`**, asking
    `CAP.PRODUCTION_VISUAL_MANAGE`. It takes **no party**, because the archive has no night —
    that is the whole point of D-45-08, the archive precedes the listing and the listing
    precedes the night.

    **Do not widen `mayUploadToParty`.** Its own docblock argues against a nullable night and
    records the rename and the blast radius that forced the current signature. A second
    predicate in the same module keeps both questions unambiguous; a nullable parameter makes
    *may this person upload* answerable without naming what they are uploading to.

    **`src/lib/media/finalize.ts` — extract the shared work**: pick the object up from
    quarantine with the service role, **strip its metadata**, write it to a destination
    bucket, remove the quarantine object. Both routes call it and neither reimplements it.
    Two destinations reached by two copies of this code is one copy that will stop stripping.
    The module takes the destination bucket as an argument and **has no default** — a default
    destination is the bug that publishes an archive photo.

    **`/api/media/finalize` — unchanged in behaviour.** It calls the extracted module with
    the public bucket, and its two numbers and its fail-closed paragraph stay exactly where
    they are. Record in the SUMMARY that its externally observable behaviour did not change.

    **`/api/media/finalize-archive` — the new arm.** JSON in, object key only. It asks
    `mayUploadToVisualSection()` **first**, then calls the extracted module with the
    **private** `visual-archive` bucket, then returns the stored key. **Fail closed**: any
    step that cannot be completed leaves nothing behind and returns a named refusal.

    Its docblock says, in its own words, the thing that distinguishes it from its sibling:
    **this route is the place bytes become filed, not the place they become public.** The
    destination has no anonymous read policy, and it is that absence — not this route's care
    — that keeps an unpublished photo unpublished.

    **The log form on both routes:** `code=… message=…`, never the error object, and never
    the object key's user-supplied portion — a filename can carry an artist's name and a
    date.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the browser → the quarantine bucket | Where untrusted bytes with untrusted metadata arrive |
| quarantine → the destination | The one place stripping happens, now shared by two destinations |
| a signed URL → whoever holds the string | A URL is a string somebody forwards, so its lifetime is the control |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-45-11 | Information disclosure | an unpublished archive photo | mitigate | private bucket with no anonymous read policy and no client insert policy; thumbnails through short-lived signed URLs minted behind the visual key; the destination is a required argument with **no default**, because a default destination is how a filed photo becomes a published one |
| T-45-19 | Tampering | image metadata | mitigate | the shared module strips before it writes, on both paths, and `verify:media-strip` asserts it. *A file that has not been stripped is reachable by nobody* |
| T-45-04 | Elevation of privilege | the permission question | mitigate | a **second predicate**, not a widened one; `mayUploadToParty`'s signature is asserted unchanged; neither predicate is exported from a `"use server"` file |
| T-45-20 | Denial of service | the finalize route | mitigate | the bytes do not travel through the request — the 4.5 MB function limit against a 50 MB product limit is why, and both numbers are asserted still present |
| T-45-01 | Information disclosure | an artist name in an unannounced line-up | mitigate | rendered only behind the guard; in no page title, no `aria-label` and no log; the same banner the venue columns carry |
| T-45-SC | Tampering | npm/pip/cargo installs | accept | no package is installed; the stripper and the uploader already exist |
