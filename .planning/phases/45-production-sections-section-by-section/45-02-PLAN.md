<objective>
Build the instrument that authenticates as a real role, and use it once, under the
owner's authorisation, to record what the six production policies actually do to a
signed-in subject that holds none of their keys.

Purpose: success criterion 4 asks for a refusal *"exercised with a real role rather than a
service key"*, and **nothing in this repository can do that today** — every catalogue gate
connects through the Management API, which bypasses RLS. That is why Phase 44's criterion
4 could prove the six policies exist and never that they refuse. This plan is built
**before** the key split, not after, because it is the only thing that can say whether the
same people are still refused once the six policies ask a different key.
Output: one script, one registration, and one dated authorisation spent once.
</objective>

    A Node script under `scripts/`, run by name and never by `npm run verify`.

    **The header states, before any code, what a green does not mean.** In particular: it
    proves a *refusal on the read path of the tables listed below*, with the roles listed
    below, at the moment it ran. It proves nothing about criterion 1 — see the closing
    paragraph — and nothing about writes.

    **Subjects.** Master (from `MASTER_EMAIL`) as the positive control; a member as the
    refusal; the anonymous floor with the anon key and no session at all. **The member's
    address is read at run time from `public.profiles` with the service client, and never
    printed** — the script prints roles and counts, never identities. If more than one
    member exists it takes the first by `created_at` and prints only *"one member profile
    resolved"*.

    **Targets** are a **declared constant** at the top of the file — a list of
    `{ section, tables[] }` — so that a later phase adds a row rather than a script. It
    starts with the calendar's six `production_*` tables and grows to the five section
    tables of plan 45-01 when they exist. **A table that does not exist yet is a REFUSAL
    for that row, not a pass and not a failure.**

    **The assertion is a PAIR, per table, and never a single value.** Run the identical
    `.select("id", { count: "exact", head: true })` under the master session and under the
    member session, and assert `master.count > 0 && member.count === 0`. The trap this
    exists for is measured and is the reason the pair is mandatory: `anon` and
    `authenticated` hold table-level `arwdDxtm` on every `production_*` table, so an
    unentitled read is **not** `42501`; it passes the privilege check, meets the policy,
    matches nothing, and returns **HTTP 200 with `[]`**. On a table holding zero rows the
    master's answer and the member's answer are byte-identical.

    So: **when `master.count === 0` the row REFUSES and the process exits 2** with the
    sentence *the measurement did not happen* — never a pass. A run in which every row
    refuses exits 2, and the transcript says so in its first line so nobody reads a
    scrollback as a green.

    **Read-only, and the script proves it about itself.** Before doing anything it greps
    its **own source** for `.insert(`, `.update(`, `.upsert(`, `.delete(` and `.rpc(` and
    refuses if it finds one — the shape `verify-conversion.mjs` uses so a gate cannot go
    green on the sentence forbidding the thing. The service key is used for exactly three
    calls — `generateLink`, the member lookup, and `signOut` — and for no `.from()` read of
    a production section table.

    **Revocation is verified, never assumed.** At the end, `signOut(access_token,
    'global')` for every minted session, then re-read each token with the anon client and
    print whether it still resolves. A minted session that outlives the run is a real
    person's session left open.

    **It prints no token, no email and no row content** — table names, role words, counts
    and outcomes only. A refusal probe that printed a row would be printing exactly the
    material the policies exist to hold.

    **The closing paragraph, mandatory:** this instrument cannot close criterion 1. Under
    D-45-03 both roles hold all three new keys, so no subject exists for whom *"holds one
    section, refused the others"* is true. What it can prove is that **the policies ask
    different keys** — read from `pg_policies` — which is a different sentence and must be
    written as such.
  </action>
