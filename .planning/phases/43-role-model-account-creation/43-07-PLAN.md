<objective>
`ACCT-04` is not an extension of an existing register. Measured: this repository
has **no** audit table for member acts, no `approved_by`, no `approved_at`, no
`promoted_by`. The trace today is the mutated row and nothing else, and
`updated_at` carries only the last write — so a promotion followed by a demotion
erases the promotion. **This is the first register.**

Three design decisions carry the weight, and each has its reason:

**One table, not columns.** A column holds the latest act. D-11 asks for
something a season can be read from.

**One transaction, not two calls.** The five acts do a single `.update()` today.
Two PostgREST calls cannot be atomic, so a mutation that succeeded while its
register row failed would produce exactly the untraced act D-11 forbids. The
write goes through a `SECURITY DEFINER` function that does both. The obvious
alternative — an `AFTER UPDATE` trigger reading `auth.uid()` — is named here so
it is not attempted: every one of the seven mutation paths uses the service
client, under which `auth.uid()` is **null**, so a `NOT NULL` actor would reject
the register write *and the mutation with it*.

**An actor that can be the system.** D-16's reconciliation-driven demotion has no
human author, and a plainly nullable actor re-opens the unattributed act. So
`actor_kind` sits beside the actor and the table refuses the combination that
would mean "nobody".

Purpose: the register every act in this phase writes to, shaped so Phase 35's
per-night assignment can write to it without changing it.
Output: one migration, one union module, one ninth capability, one applied schema.
</objective>

**2 — `public.membership_acts`.** Columns:
- `id uuid primary key default gen_random_uuid()`
- `act text not null check (act in ('created','approved','rejected','promoted','demoted','deactivated','reactivated'))` — mirroring the TypeScript union of task 2, both edited in one commit

- `note text` — optional, and a comment forbidding a person's name in it

Two indexes with the reason each is read for: `(subject_id, at desc)` to read one
person's history, and `(actor_id, at desc)` because *the simplest path to let
somebody in is also the one that must be made visible*
(`community-membership.md`, gate *chi decide è tracciato*).

**3 — RLS, and the deliberate omission.** `ENABLE ROW LEVEL SECURITY`; one policy,
`membership_acts_select_register_read`, `FOR SELECT USING ((select private.has_capability('register.read')))`
— the `(select …)` wrapper is load-bearing and it is not `STABLE` that produces
it. Then the paragraph, adapted from `door_scan_events:155-163`: no INSERT,
UPDATE or DELETE policy, deliberately; writes come only through the function
below, which runs as its definer; with RLS on and no write policy no session can
add, edit or remove a row. Without that paragraph the next reader takes it for a
bug and repairs it.

**4 — `public.record_membership_act(...)`.** `LANGUAGE plpgsql`,
`SECURITY DEFINER`, `SET search_path = ''`, every reference schema-qualified.
Arguments: the subject, the act, the actor, the actor kind, the role to write,
the status to write, an optional note, an optional party. Behaviour, in one
transaction:
- lock and read the subject's current `role`, `status` and `membership_code`
  (`for update`); a missing subject raises, and the message names the subject
  identifier, never an address;
- when a role or a status argument is given, `update public.profiles` with
  exactly those columns — this is the write the constraint of plan 43-06 judges,
  and a `23514` here aborts the whole call, which is the point: the act and its
  record fail together;
- insert the register row with the before-values just read, the after-values
  just written, the actor, the actor kind and the subject's membership code as
  `subject_label`;
- return the register row's id.

**Then lock the function down, and this is not optional.** It is
`SECURITY DEFINER` and it writes `role`. `revoke all on function` from `public`,
`anon` and `authenticated`; `grant execute` to `service_role` only. A
`SECURITY DEFINER` role-writer reachable by an authenticated session is a
privilege-escalation primitive, and PostgREST exposes `public` functions by
default. Write that sentence in the migration.

Finally, one comment recording **D-18**: a door override stays in
`door_scan_events`, which already holds outcome, operator, device and `is_undo`.
It does not enter this register, because an override does not change who someone
is, and two registers holding overlapping truths is worse than either.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| an authenticated session → a `SECURITY DEFINER` function in `public` | PostgREST exposes `public` functions; a definer function that writes `role` is a privilege-escalation primitive if it is callable |
| the service client → the register | It bypasses every policy, so the append-only property rests on there being no write policy at all rather than on the client's restraint |
| the register → the person it is about | It contains rejections; who may read it is a disclosure decision, not a convenience |
