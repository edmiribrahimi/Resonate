<objective>
`ACCT-01` through `ACCT-04`, in one surface.

Most of the mechanism already exists and the plan's job is to reuse it without
inheriting its three defects. `src/lib/guest-list/process-entry.ts:218-251`
creates an auth user and generates a recovery link — and it sleeps 500 ms instead
of synchronising, swallows a failed link into a `/login` fallback, and reads
`NEXT_PUBLIC_APP_URL` with a `||` default that this project has already been
bitten by (a trailing newline on that exact variable broke the SumUp webhook).
None of the three is copied.

Two traps are specific and measured. **A plain `createUser` produces
`status = 'pending'`** — for a created member that contradicts D-08 by putting
them back in the queue they were just let out of, and for a staff role it is a
hard `23514` from plan 43-06's constraint. So role and status are written in one
statement, exactly as `updateMemberRole` already does. And **a sleep instead of a
read-back** means the following update finds no row, affects zero rows, and
returns `error: null` — an account with no profile, no membership code, and no
entry, failing invisibly.

The ceiling is not a validation. D-07 forbids creating a `master`, and the way
that is guaranteed is that no union member, no argument and no branch in this
plan carries the value.

Purpose: the act that D-08 says is an approval, performed by someone entitled to
approve.
Output: one action, one Italian message, one form.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a form field → a role assignment | The role is the most consequential value on this surface, and it arrives from a browser |
| a server action → `auth.admin.*` | The service-role key is reachable from here; it bypasses every policy |
| an invitation link in an inbox | A bearer credential, sitting in a mailbox this application does not control |
| a creation endpoint → account existence | A response that differs for an existing address answers a question the caller did not have to be able to ask |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-43-11-01 | Elevation of Privilege | an organizer posting `role: 'master'` | mitigate | `'master'` is absent from the closed union and from every branch; the surface's `<select>` is a convenience, not the boundary, and a comment says so |
| T-43-11-02 | Elevation of Privilege | untrusted input reaching the service-role client | mitigate | Address and role validated against a closed set **before** the service client is constructed; the capability gate runs first; `access-gating.md`'s *service role* rule requires the commit to justify the use, and it does — `auth.admin.createUser` needs it |
| T-43-11-03 | Information Disclosure | the action as an account-existence oracle | mitigate | The surface is capability-gated to master and organizer, who are entitled to know; `already_exists` is not surfaced to anyone else, and no unauthenticated path reaches the action. Noted that this repository has **no rate limiting** anywhere, so the gate is the mitigation |
| T-43-11-04 | Information Disclosure | a password living in an inbox forever | mitigate | No password is generated or sent; `generateLink({type:'recovery'})` and a static grep assertion on the template |
| T-43-11-05 | Repudiation | a created account with no record of who created it | mitigate | The creation act goes through `record_membership_act` in the same transaction as the profile write, actor from `ctx.userId` |
| T-43-11-06 | Repudiation | a silent partial success — account created, invitation lost | mitigate | Two distinct causes, neither swallowed; the link failure returns the membership code so the person can still be admitted |
| T-43-11-07 | Denial of Service | an account created mid-night refused at an offline door | accept | The honest limit of an offline door; mitigated by copy on the surface and by the runbook answer, not engineered around. Recorded per `checkin-offline.md` |
| T-43-11-08 | Spoofing | an invitation link forwarded or intercepted | accept | Supabase Auth owns the link's lifetime and single use; plan 43-04 confirmed the configuration rather than widening it |
| T-43-11-SC | Tampering | npm/pip/cargo installs | accept | No package added — no validation library, no email library beyond what is already a dependency |
</threat_model>
