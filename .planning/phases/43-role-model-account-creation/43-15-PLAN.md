<objective>
`43-VALIDATION.md` states the coverage claim without softening it: of nine
requirements, **two** have strong automated detection, **one** weak, and **six**
depend primarily on written manual procedures — three of which cannot be observed
by any tool in this repository. *"A phase that reports itself verified without
those procedures written and executed has verified two of nine."*

The owner's working rule allows their **execution** to be batched — a check whose
outcome does not change what we write is deferred deliberately. It does not allow
their **writing** to be skipped, and one of them is explicitly not deferrable at
all: the IndexedDB upgrade, exercised in plan 43-13 because
`.planning/STATE.md` requires it before the first real night.

So this plan writes the eleven, records what has already been observed against
them, runs the whole-of-phase comparison, and states the honest coverage.

Purpose: leave the phase with its evidence, and with an accurate account of what
that evidence does not cover.
Output: one UAT file, one updated validation contract, one final comparison.
</objective>

  before it has ever signed in. This is ACCT-02's load-bearing check and no
  automated observation reaches it.
- **M-43-02 — entry with the radio off, both orders.** Once with the account
  created **before** the door phone downloaded its roster, once **after**. The
  second is predicted to be **refused**, and that is the honest limit of an
  offline door, not a defect: an unknown membership code is refused because a
  membership QR carries no signature. The procedure records the runbook answer —
  check the person in from the list rather than re-scanning — and the surface copy
  that says to create staff accounts before the night.
- **M-43-03 — the link sets a password.** Partly executed in plan 43-04; carry
  that result forward and extend it to an invitation produced by `createAccount`.
- **M-43-04 — the refusal is distinguishable in a production build.** `next dev`
  proves nothing here: Next redacts a Server Action's message only in production.
  The observation is the notice text, on a deployed build.
- **M-43-05 — demotion happens.** Executed in plan 43-12 case D; carry the result
  and its date.
- **M-43-06 — an unset or unmatched `MASTER_EMAIL` demotes nobody.** Executed in
  plan 43-12 cases A, B and C. `43-VALIDATION.md` calls it the highest-consequence
  check in the phase, because getting it wrong is a lockout — record it as such.
- **M-43-07 — an organizer cannot reach `master`.** Signed in as an organizer:
  the role list offers no master, and a crafted request cannot either, because the
  value is not in the action's union. Record the grep evidence beside the
  observation.
- **M-43-08 — five acts, one register.** Approve, reject, promote, deactivate and
  reactivate, then read the register: five rows, each with its author and its
  timestamp. **The harness cannot see this** — B3 proves who may write and never
  that an act was recorded, which `43-VALIDATION.md` names as ACCT-04's real risk.
- **M-43-09 — a member reads zero register rows.** Requires a **real member
  session**: the Management API bypasses RLS, so no query from any tool settles
  it. `.planning/STATE.md` records the identical outstanding item for
  `door_scan_events`, and this procedure should say so.
- **M-43-10 — a staff entry in the night's attendance, and readable.** Scan a
  staff card at a party, then answer *how many of tonight's entries were free
  staff entries* from the surface. A count is not a detector of legibility, so the
  observation is the answer, not the row.
- **M-43-11 — the IndexedDB upgrade strands no queued scan.** Executed in plan
  43-13; carry the before/after row counts and the version readings, and state
  whether the v2 path was exercised.

Then the file's preamble carries the **static assertions**, with the command and
the expected result for each, so they can be re-run as a set: `npm run build`;
`npm run verify:capabilities` (production and container, `5/5 green`);
`npm run verify:no-header-identity` (zero readers); `npm run verify:persona`;
`npm run baseline:container -- --seed-only --report` (12 grid cells, six refused
forbidden writes); the grep that no path passes `role: 'master'`; and the grep
that the invitation template interpolates no password.

**Roles, never people.** Every procedure names a role and a throwaway account; no
address, no name. And every one that creates a throwaway account ends by deleting
it and confirming the deletion — an undeleted account with a membership code is
admissible at any door.
