<objective>
`ACCT-03` says the message carries a link to set a password. `43-RESEARCH.md`
found that **the link has nowhere to land**: `supabase.auth.updateUser({ password })`
appears nowhere in `src/`, the recovery link deposits an authenticated person on
`/dashboard` where there is no password field, and Reset Password sends the same
kind of link back to the same place — a loop. The existing guest-list invitation
has had that hole since it was written.

So the surface is built first, before anything aims at it. That order is
deliberate: plan 43-11 sends the invitation, and an invitation whose button leads
to a page that cannot do the thing the email promised is the requirement failing
quietly, which is the failure mode this project treats as worst.

One thing travels with it. The callback already forwards an unvalidated `next`
to `NextResponse.redirect` (`route.ts:9`, `:45`). That is pre-existing and would
have stayed out of scope — except this phase adds a **second** parametric
redirect, so `access-gating.md`'s *redirect validato* stops being somebody else's
problem.

Purpose: make ACCT-03 achievable at all.
Output: one surface, one allow-list, one loop cured.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| an emailed link → an authenticated session | The recovery link is a bearer credential: whoever holds it becomes the account until it is used or expires |
| a `next` query parameter → `NextResponse.redirect` | Entirely attacker-controlled, and it runs **after** the session exists |
| browser → Supabase Auth | The password is chosen in the browser and never passes through this application's server |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-43-04-01 | Spoofing | open redirect from the authenticated callback | mitigate | `next` resolved against an enumerated allow-list of relative paths; `//`, schemes and absolute URLs refused; the substitution is flagged on screen |
| T-43-04-02 | Information Disclosure | a password reaching a log, a URL or the server | mitigate | The write is browser-side `updateUser({ password })`; no field value is logged or placed in a query string; an acceptance criterion asserts it |
| T-43-04-03 | Elevation of Privilege | the recovery link as a credential with too long a life | accept | Lifetime and single-use are Supabase Auth project settings, unchanged by this phase; task 3 confirms the configuration rather than widening it. V3 of ASVS: the surface must not extend the session, and it does not |
| T-43-04-04 | Denial of Service | a person with an expired link and no stated reason | mitigate | `no_session` is one of the four tagged outcomes with its own copy and a route back, instead of a bare redirect to `/login` |
| T-43-04-05 | Repudiation | a failure visible only in a log | mitigate | There is no error tracking in this product; every outcome renders a distinct notice, following `FailureNotice.tsx` |
| T-43-04-SC | Tampering | npm/pip/cargo installs | accept | No package added — no password-strength and no validation library. `43-RESEARCH.md` records that this phase installs nothing |
</threat_model>
