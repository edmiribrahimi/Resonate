## F-11-01 — the declaration line does NOT match the nine-sibling checksum, and that is deliberate

**This is the plan's one refused acceptance criterion and it is stated as one.**

The criterion reads: the clearance utility *"present, copied byte-identically from
`src/app/(public)/gallery/page.tsx:110`"*, and the orchestrator's brief adds *"their
declaration lines share one checksum — match it."*

**The utility token matches. The line does not.**

```
$ LC_ALL=C /usr/bin/grep -o 'md:\[--nav-inset-inline-start:14rem\]' \
      'src/app/(public)/gallery/page.tsx' | shasum -a 256
5ef9f6a0645e7c9882c5900a67feec9126e4efac4615d31a974ffeb4649d0bb4  -

$ LC_ALL=C /usr/bin/grep -o 'md:\[--nav-inset-inline-start:14rem\]' \
      'src/app/(public)/events/[slug]/menu/page.tsx' | shasum -a 256
5ef9f6a0645e7c9882c5900a67feec9126e4efac4615d31a974ffeb4649d0bb4  -
```

```
$ <the nine landed declaration lines> | sort -u | wc -l
       1
$ <the nine landed declaration lines> | sort -u | shasum -a 256
0050d1d2c973acfeb63de00eced17839960e9431741c9a7bb8aad368435d9166  -
```

The nine sites that landed before this one collapse to **one** unique string. This tenth
one is a different string:

```
gallery/page.tsx:110        <div className="md:[--nav-inset-inline-start:14rem]">
menu/page.tsx:283           <div className={isAuthenticated ? "md:[--nav-inset-inline-start:14rem]" : undefined}>
```

**Why the guard, and it is not a preference.** All nine of those surfaces mount the
responsive navigation **unconditionally**. This one does not, and has not since before
this phase: the file carries its own written product decision that the navigation is
hidden from guests *"so they don't navigate away from the menu and lose track of their
tokens"*. A conversion does not get to reverse that.

Given a conditional mount, a static declaration states — for every logged-out guest at
768px and up — that a 224px column is there to clear, when this page draws none for them.
The consequence is content pushed 224px to the right against empty space. That is the
same class of defect as content sliding under a column, arrived at from the other side.

`globals.css:295-311` settles which direction is correct, in its own words:

> *"the clearance is structurally unable to reach a route that does not mount the
> responsive form"*

and it records that the previous, ambient-value arrangement was *"a claim about eleven
surfaces that was never true of them"* (D-41.1-01). A route that mounts the form for half
its visitors is that same sentence with a predicate on it. Copying the static line here
would have reintroduced the exact falsehood D-41.1-01 was written to remove, on one
surface instead of eleven.

**What the gate reads, measured rather than assumed.** `verify-conversion.mjs:2783-2813`
scans for the bracketed property and walks back to a token boundary, and `"` is one
(`TOKEN_BOUNDARY`, `:2781`). The conditional expression is therefore fully legible to it:

```
  bracketed declaration(s) of the inline axis found : 10   (264 file(s) read, comments blanked)
      …
      src/app/(public)/events/[slug]/menu/page.tsx:277   md:[--nav-inset-inline-start:14rem]
      …
  file(s) DECLARING the column clearance            : 10
  file(s) MOUNTING the responsive form              : 10
```

*(The gate reports `:277` because it reads comment-blanked lines; the live file numbers it
`:283`.)*

**Pairing 10 / 10, both directions, `✓ E`.** Nothing about this weakens the gate.

**What a reader should decide, not this plan.** If a later reader prefers one shape across
all ten surfaces, the way to get it is to make **this page's mount unconditional** — which
is a product decision about whether a guest at a bar should be offered a way out of the
menu — not to make its declaration unconditional, which would only make the page lie
quietly.

## F-11-02 — the conditional bottom clearance was DELETED, where wave 0 said it must survive

`41.2-WAVE0-FINDINGS.md` §7.2 row 5 takes the maximum's disposition (**DELETE**, applied)
and adds a caution:

> *"The two conditional paddings on the same line are **not** the maximum and must survive
> the edit: they are the clearance for the phone navigation bar, and dropping the
> authenticated branch puts the menu's last row under the bar."*

**They did not survive, and the thing the caution protects is nevertheless protected —
by the mechanism built for it.** The arithmetic, from `PageShell.tsx:51-67` and
`globals.css:319-348`:

| Case | Before (hand-written) | After (the shell) | Verdict |
|---|---|---|---|
| signed in, phone | 96px | `--nav-inset-block-end` + 16px = 80 + safe-area + 16 = **96px+** | value-preserving on the device the pair was written for |
| signed in, ≥768px | 96px, under a wrapper that drew a bar at every width | 0 + 16 = **16px**, with the navigation now a leading column | **corrected** — the hand-written 96px becomes dead space the moment the bar leaves the bottom edge |
| guest, phone | 32px | **96px+** | **+64px of empty space**, recorded below |
| guest, ≥768px | 32px | **16px** | closer to the rhythm the phase uses |

**The row the caution is about cannot end up under the bar**, because the only case where
a bar is drawn is the signed-in one and the shell reserves exactly what the deleted branch
reserved there.

**The guest's +64px is a real regression and it is recorded rather than corrected.** A
guest sees ~64px more empty space below the last row on a phone, because the shell reserves
for a bar this page does not draw for them. It is the safe direction — too much clearance
never hides a row, too little does — and correcting it would mean a page overriding the one
measurement `PageShell` exists to own, which is how 47 pages came to each answer the same
question separately.

Keeping the pair was not an option that leaves the page correct: the shell's padding and a
retained `pb-24` are additive, so a signed-in visitor on a phone would have got 192px.

## F-11-03 — the cover image moved INSIDE the shell, and that is a visual change

The hero used to run full width above a 32rem column that climbed back over it with a
negative top margin. That construction only makes sense while the page owns its own
maximum, and it stopped owning one in this commit.

**Left outside the shell it would also have bled under the 224px column from 768px up**,
because the shell applies the leading inset and anything outside it does not.

Precedent, both already converted:

- `(public)/artists/[slug]/page.tsx:148` — this tree's converted hero, inside the shell;
- `(public)/tickets/[id]/page.tsx:197` — a contained cover image at §9's container radius.

So the strip is now a contained block at the container rung, with its scrim kept and only
its token changed. **A person should look at it**: the plan's human rows are the only thing
that can say whether a contained cover reads as well as a bleeding one on this surface, and
no gate in this repository renders a pixel.

## F-11-04 — the placeholder reserved a heading the page has never drawn

The hand-rolled `loading.tsx` drew a title bar and a date line above the selector. The page
has **never** drawn either: `page.tsx` carries a written decision to omit the event title
and date and keep the menu focused on drinks, and this plan declared the surface
deliberately headless (see the SUMMARY's heading section).

A placeholder that reserves a heading nobody renders does two wrong things at once: it tells
a reader a title is coming, and it makes the page jump upwards when the data lands — which
is the defect a skeleton exists to prevent, achieved by a skeleton. Both boxes are gone with
the six hand-rolled pulses.

## F-11-05 — a FIFTH silent failure on the money path, recorded and NOT repaired

**Found in this plan's own perimeter.** Plan 41.2-10 reported *"no fifth silent catch was
found in this plan's four files"*. There is one in this plan's.

```
src/app/(public)/events/[slug]/menu/PartyDrinkMenu.tsx:145-146   handleSave
src/app/(public)/events/[slug]/menu/PartyDrinkMenu.tsx:155-156   handleClear
```

Neither catches. `updateMenuClosesAt` throws on a refused capability
(`actions.ts:48,51`) and on a failed write (`actions.ts:60`). When it does, the transition
rejects, `setSaved(true)` is never reached, the confirmation never appears — and **nothing
at all is shown**. It is not a catch that collapses causes into one message; it is the
absence of any path from a failed write to a person.

**It is not the same shape as the four already recorded, and that matters.** Those four
swallow an error; this one never had a handler to swallow it with. The consequence is worse
in one specific way: an organizer who believes they set the menu to close at midnight, and
did not, has a bar still selling tokens at two — and this repository has no error tracking,
so nobody learns of it until somebody notices the effect.

**Left where it is**, per this plan's standing constraint and for the reason plan 41.2-10
gave for the other four: fixing it means designing what a person is told when a
money-adjacent write fails, which is new copy on a money path, and a visual conversion is
not where that gets decided. It belongs beside the four in the phase's consolidated record.

## F-11-06 — Clear's red hover hint was dropped, and what that costs

The incumbent Clear control tinted its border red on hover. The button ladder has no
hover-tint rung, and inventing one in this file would make it a second author of the button
contract — pitfall P6's shape.

**The consequence is real and is written here rather than carried by a colour only a
pointer can see:** clearing the explicit closing time falls the party back to its
`end_time`, and where there is no `end_time` the menu **never closes automatically**. That
**widens** the window in which drink tokens can be bought and, through the grace period,
redeemed.

**Clear did not take the destructive rung either**, and that is a decision on 41.2-10's
own F-10-04 reasoning: the destructive rung is for acts that destroy, and this act removes
a value that one further action restores. Over-signalling a reversible act spends the rung
that a genuinely irreversible one will need.

**What is unchanged:** what the control sends. `updateMenuClosesAt(party.id, null)` is an
unchanged context line and does not appear in the diff.
