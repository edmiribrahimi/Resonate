## F-41.2-04-01 — Two documents assign the phase's first `TYPOGRAPHIC_MEASURES` entry to two different plans, and this plan did not write it

**Severity:** blocking for whoever declares `/artists/[slug]` in `CONVERTED`.
**Disposition:** reported, not repaired.

`41.2-WAVE0-FINDINGS.md` §7.2 row 2 dispositions `(public)/artists/[slug]/page.tsx:126`
as **DECLARE**, and §7.3 goes on to spell the entry out part by part under the
heading *"The entry plan 41.2-04 writes is therefore"* — naming **this** plan as
its author, and closing with *"Write the entry in the same commit as the
declaration, per D-41-16."*

`41.2-04-PLAN.md`'s own conversion rule 1 says the opposite, in as many words:

> *"**This plan edits no file under `scripts/`** (D-41.1-22). It declares no
> surface and it adds no `TYPOGRAPHIC_MEASURES` entry — the reconciliation plan
> 41.2-05 does both, in one commit, on the authority of the tree."*

**The plan won, and the reason is D-41.1-22 rather than a preference.** Every gate
edit in a wave belongs to that wave's reconciliation plan; this plan ran in
parallel with another in a separate worktree, and two worktrees editing one gate
file is the same merge hazard as two appending to one findings file. So this plan
made **no edit under `scripts/`**, and `git status --porcelain -- scripts/`
returns nothing.

**What this leaves owing, stated precisely so nobody has to re-derive it.** The
line at `:126` is intact and its class string is byte-identical, which is the
state the entry needs. But **the entry does not exist yet**, and
`TYPOGRAPHIC_MEASURES` is still `[]` at `scripts/verify-conversion.mjs:1053`. So:

> **Whoever adds the `CONVERTED` entry for `/artists/[slug]` must add the
> `TYPOGRAPHIC_MEASURES` entry in the SAME commit.** A declaration without the
> entry is a check-D red on a correct line; an entry without the declaration is a
> refusal (`measuresOnUndeclaredPage`, exit 2, *"no CONVERTED surface declares
> this page file"*). Neither half stands alone, and D-41-16 already says so.

The entry, re-derived against the tree as it stands after this plan's two commits
— shape `[pageFile, maximum, fragment, reason]`, read from
`verify-conversion.mjs:1051` and matched at `:3170-3172`:

| Part | Value |

## F-41.2-04-02 — The measure line's leading whitespace moved by two spaces; its class string did not

**Severity:** informational — it changes nothing the gate reads.
**Disposition:** recorded so the next reader does not mistake a re-indent for an edit.

The plan asks that the line be left **byte-identical**. Measured, before and
after:

```
before   src/app/(public)/artists/[slug]/page.tsx:126
         ············<p className="mt-6 max-w-lg text-muted whitespace-pre-line text-left">
after    src/app/(public)/artists/[slug]/page.tsx:229
         ··············<p className="mt-6 max-w-lg text-muted whitespace-pre-line text-left">
```

*(dots stand for spaces: 12 before, 14 after.)*

**The class string, the element and the text are byte-identical. The indentation
is two spaces deeper, and it could not have been otherwise:** the conversion
replaces two wrapper elements (the viewport-height page root and the inline-padding
div) with three (the fragment, the declaring div and the shell), which is a net
gain of one nesting level everywhere inside. Preserving the column would have
required deleting the header's own centring wrapper, which is a layout change and
not a conversion.

**Nothing the gate reads is affected**, and that is read out of the matcher rather
than assumed — `verify-conversion.mjs:3170-3172` tests `e.maximum === m[0]` and
`line.includes(e.fragment)`, neither of which sees leading whitespace.

## F-41.2-04-03 — The artist dialog's catch collapses three distinct causes into one bucket, and it is carried forward

**Severity:** real, pre-existing, and it survives this conversion untouched.
**Disposition:** carried forward, **not fixed** — §11 of the contract is *none introduced*.

`src/components/artists/EditArtistButton.tsx:158`:

```ts
setError(err instanceof Error ? err.message : "Something went wrong");
```

One `catch` stands behind three different things: the action's capability
assertion refusing, the database update failing (`actions.ts:235` throws
`Failed to update artist: …`), and the request never arriving at all. In a
**production build Next redacts a thrown Server Action message**, so the first
branch degrades to a digest sentence and the second bucket is what a person
actually reads.

This is the newsletter defect recorded in `.planning/codebase/CONCERNS.md`,
alive on another surface, and this repository has **no error tracking** — so
what is written on screen is the whole of what anybody will ever learn.

**Why it is not fixed here.** Naming each cause is a rewrite of this surface's
copy, and it needs what the venue analog already has and this action does not: a
**result union** returned by `updateArtist` instead of a thrown `Error`.
`EditVenueButton.tsx:76-101` shows the finished shape — a total `Record` over the
refusal union, so a new refusal in the action becomes a compile error rather than
a blank panel. Building it here would mean **opening a server action**, which is
this phase's stop condition 2 and an explicit halt.

**The remedy, for whoever takes it:** give `updateArtist` a
`{ ok: true } | { ok: false, reason: … }` return, then copy
`EditVenueButton.tsx:76-101` and `:176-193`. One plan, both ends, and it owns the
copy decision.

## F-41.2-04-04 — Refused: rendering the artist form's Save control on the destructive rung

**Severity:** a refusal, recorded with its reason.
**Disposition:** not done. The analog's rung was used instead.

The execution brief asked that the dialog put *"the confirming control on the
destructive rung"*. **It was not done**, and the refusal is deliberate:

- `destructive` in the button ladder is `bg-sem-crit` (`Button.tsx:117`) — a
  filled red at 7.36 : 1, and §5.1 reserves it for an act that **destroys**.
  Saving an artist's own bio destroys nothing.
- The exact analog this plan is built on — `EditVenueButton.tsx:237-244`,
  converted by plan 41.1-07, and the file `41.2-PATTERNS.md` §2.3 calls *"the
  same file with different nouns"* — renders its Save on the **primary** rung.
  `41.2-PATTERNS.md` §2.4 is where `variant="destructive"` appears, and that is
  the **money** dialog (a refund), not the form dialog.
- The two properties the destructive-rung instruction exists to buy are both in
  place by another route: the initial-focus marker is on **Cancel** and on nothing
  else, so the key that arrives before anyone has read the panel does not save;
  and the refusal reports in the primitive's `status` region, outside the
  scroller, never through a toast.

Painting a red fill on Save would have been a visual regression on a public
surface, decided by an executor, against both the ladder and the named analog.
Recorded here rather than resolved silently in either direction.
