## F-17-01 — a discount applied before signing up is dropped when the purchase resumes

**This is the seventh recorded failure on this phase's money path and the first
that changes what somebody is charged.**

Measured, in the two files this plan opened:

```
src/app/(public)/events/[slug]/TierSelection.tsx:287-290
  localStorage.setItem(
    "resonate_intent",
    JSON.stringify({ type: "purchase", tierId: …, partyId, eventSlug,
                     discountCodeId: discount?.id ?? null })
  );

src/app/(public)/events/[slug]/PendingIntentHandler.tsx:42-47
  interface PurchaseIntent {
    type: "purchase";
    tierId: string;
    partyId: string | null;
    eventSlug: string;                     ← no discount identifier is declared

src/app/(public)/events/[slug]/PendingIntentHandler.tsx:84
  const result = await purchaseTicket(intent.partyId, intent.tierId);
                                                    ← two arguments, not three
```

The purchase action's signature takes three
(`src/app/(admin)/admin/events/actions.ts:1217`), the third being the discount
identifier, and it is **optional** — so nothing about this fails to compile, and
nothing about it fails at run time either. The value is written into the stored
intent and is never read out of it.

**The sequence that reaches it, in a person's terms.** Somebody without an
account chooses a tier, types a valid discount code, sees the struck-through
price beside the reduced one, and presses buy. They are sent to register. They
come back to the same night's page. The handler resumes the purchase **at the
undiscounted price**, and nothing on the screen says the code was dropped —
there is no refusal, because nothing refused.

**Why the signed-in path does not have it:** `TierSelection` calls the action
directly with all three arguments, so the code applies. The defect exists only
on the path through registration — which is the path a first-time guest takes,
and a discount code is most often given to somebody who is not yet a member.

**Not repaired here, and the reason is not caution.** Passing the third argument
changes what the purchase action is called with, which is a payload change on
the money path — the one thing this plan's own stop condition 2 forbids, and the
same standard under which plans 41.2-10, 41.2-12 and 41.2-13 left six other
failures at their `file:line`. It also needs a decision this plan does not own:
whether a code that has since been deactivated, exhausted or restricted to
another tier should refuse the resumed purchase or silently proceed without it.
The action already refuses all three cases by throwing — three consecutive
refusals at `actions.ts:1393-1395`, re-measured rather than remembered — so the
answer is probably *let it refuse*. But *"probably"* is not a thing to settle
inside a visual conversion.

**Route:** a plan that owns the guest purchase path, with the refusal copy
written for the case where a code no longer applies.

## F-17-02 — a malformed stored intent is discarded in silence

```
src/app/(public)/events/[slug]/PendingIntentHandler.tsx:69-74
  try {
    intent = JSON.parse(raw);
  } catch {
    localStorage.removeItem("resonate_intent");
    return;
  }
```

The catch has no binding, no log and no visible effect. A stored intent that
cannot be parsed is deleted, the component renders nothing, and **the purchase
somebody began simply is not there when they come back**. To the guest it is
indistinguishable from never having pressed buy.

This repository has **no error tracking**, so nothing reaches a person by
itself. `meta-gates.md` asks for an observable effect and says explicitly that
"log it" is not enough; this one does not even log.

**Recorded, not repaired.** Telling a guest that a purchase they started could
not be resumed is new copy on a money surface, and it needs a sentence that does
not manufacture alarm about an act that was never charged.

## F-17-03 — the branch in which a purchase resumes and nothing at all happens

```
src/app/(public)/events/[slug]/PendingIntentHandler.tsx:84-90
  const result = await purchaseTicket(intent.partyId, intent.tierId);
  localStorage.removeItem("resonate_intent");        ← removed BEFORE the test
  if (result.success && result.checkoutId) {
    …
  }
```

When that test is false the intent has **already** been removed, the `finally`
clause clears the in-progress flag, and the guard at `:104` — which draws
nothing when there is no progress, no failure and no checkout — returns `null`.
The guest sees the ordinary page, the stored intent is gone, and the purchase
silently did not resume. That is precisely the shape this plan's threat register
names as T-41.2-113.

**How reachable it is, stated honestly rather than dramatised.** Read out of the
action, its only return is a success carrying a checkout identifier
(`actions.ts:1477`); every other exit throws, and a throw lands in the catch and
does produce a visible refusal. So the branch is **not reachable today** through
this action. It is recorded because the removal sits on the wrong side of the
test, and a future change to what that action returns would make a silent drop
live without anybody editing this file.

## F-17-04 — the generic fallback, at its narrower form

```
src/app/(public)/events/[slug]/PendingIntentHandler.tsx:96
  setError(err instanceof Error ? err.message : "Something went wrong");
```

The banned shape `CLAUDE.md` names from the newsletter precedent — one sentence
covering every cause — is the second arm here, and it fires only for a throw
that is not an `Error`. The first arm relays the action's own sentence, and the
action's sentences are distinct per cause. So this is the defect at its narrow
end rather than at its wide one, and it is recorded at that width rather than
reported as the newsletter's twin.

## F-17-05 — the drinks list has no card shell, and the plan's model of it said it did

`41.2-PATTERNS.md` §1c row 44 lists `MyDrinks.tsx` against the card primitive as
an **exact** match, and this plan's task 2 asks for card shells to become cards.
Read at its render site there is no card in this file: it is a heading and a
grid, and the card is `DrinkTokenCard`, converted one wave earlier as spine.

Re-measured with the gates' own matchers over comment-stripped source, both
before and after:

```
MyDrinks.tsx   raw palette utilities : 0    legacy token utilities : 0
```

Wave 0's per-file census agrees by omission — the file is on neither of its two
lists. So the single conversion in this file was its section heading, one of the
ten spellings the type contract replaced. This is the same disposition
`SumUpCardWidget.tsx` received in wave 5, one step further along: there the
answer was *do not open it*; here it was *open it for one line, and say what the
other number is*.
