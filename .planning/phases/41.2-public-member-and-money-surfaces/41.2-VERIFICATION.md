### `DEF-41.2-C` — a `useId()` variable that shares its name with a money-bearing object key

`src/app/(public)/events/[slug]/TierSelection.tsx:242` — **added by this phase** — declares
`const discountCodeId = useId();`, a DOM id for the discount input's label.
`:293`, in the same component scope, writes the guest's stored purchase intent:

```js
JSON.stringify({ type: "purchase", tierId: selectedTierId, partyId, eventSlug, discountCodeId: discount?.id ?? null })
```

The explicit `key: value` form is **correct today**, and its value is `discount?.id`, not the
React id. But the key now shadows a live in-scope variable of an entirely different meaning.
**If anyone ever shortens it to the shorthand form** — which is exactly what the neighbouring
`partyId` and `eventSlug` already use, three tokens away — the stored intent would silently
carry a React-generated DOM id where a discount identifier belongs.

**never read back**. Its blast radius is therefore zero today. But the intended repair for
`DI-41.2-09` is *to start reading it*, and that repair would land in a file where the shorthand
trap is already set. Scanned tree-wide across the phase's diff: three `useId()` variables were
added and **this is the only one** whose name also appears as an object key in its own file.

Recommended: rename the local to `discountCodeInputId`. One line, no behaviour.
