### 1.1 Exit 3's irreversibility class, stated explicitly

A wallet pass **leaves the product**. It is signed, downloaded, added to a
device, and it syncs from there to that person's other devices. **Nothing in
this product can recall it** — there is no revocation path, no expiry that
removes the text already written, and no second act that un-writes a field on a
file already on a phone.

That is **the same irreversibility class as a sent reveal e-mail**: once it has
gone out, the address is out, and the project's own words for that case are that
there is no rollback — the mail has left, the screenshot exists. A wallet pass is
that with a longer tail, because it persists on the device rather than in an
inbox.

`ticketing-payments.md` already carries the neighbouring half of this — *«un pass
emesso e' sul telefono di qualcuno e non si ritira»* — about **validity**. This
finding records that the same sentence is true of the pass's **content**, and
that the content includes a venue.

**Why it falls off enumerations, measured:** `src/lib/apple-wallet.ts` carries
**zero** `className` occurrences, so no visual plan has any reason to open it,
and a perimeter built from class strings cannot see it. Wave 0 recorded this as
`DI-41.2-05` and declined the wider claim. This plan **read** the file and **did
not edit it** — `git status --porcelain` showed exactly one modified path
throughout, and it was the page file.

### 1.2 The divergence, stated once and marked unchanged

This surface and the public event page hold the same secret under **two
different predicates**.

- On the public event page a ticket holder reaches the address through that
  page's own reveal predicate.
- **Here a ticket holder sees the night's free venue text always** — the
  predicate is exit 1's, and it consults nothing.

The divergence is **deliberate and documented in the file itself**, at the
docblock which in the pre-diff tree sat at `:31-33` and which this conversion
kept verbatim (now `:99-101`), plus the render block's own in-place comment.

**This phase did not change it.** Four assertions were run over the pre-diff and
post-diff sources and all four passed:

1. the select's column list, as a **multiset over comment-stripped source** —
   15 tokens before, 15 after, identical;
2. the stored secrecy flag's occurrence count — **2 before, 2 after** — and no
   branch, ternary or comparison reads it, so the file has **not** grown a
   predicate it does not have;
3. the venue assignment — byte-identical;
4. the venue render block **and its comment** — byte-identical, **leading
   whitespace included**, and occurring exactly once.

**A note on assertion 4, because it is visible in the file.** The block now sits
two spaces shallower than its siblings. That is not a slip: the shell moved the
enclosing markup one level deeper, and re-indenting would have cost the assertion
its qualifier-free form — *byte-identical* would have become *byte-identical
apart from indentation*, which is a weaker claim than a venue guard deserves. The
under-indent is the record, and the file says so beside it.

**What would have been wrong to do:** reconciling the two predicates. That is a
behaviour change on the one act in this product that has no undo, and a visual
conversion is not where it gets decided. It is not proposed here either — it is
recorded as a divergence that exists, is deliberate, and is now written down in a
place a reader can find it.

## 2. A question owed to the owner — this surface's render mode is derived, not declared

**Not answered here, and not implemented.** `grep -c 'force-dynamic'` on the page
file returns **0** after the diff, asserted mechanically, so the question cannot
have been answered by accident.

### 2.1 The measurement, taken in this plan

`npm run build` (exit **0**) reports this route's render mode in its own route
table, quoted verbatim:

```
└ ƒ /tickets/[id]
```

with the legend, also verbatim from the same output:

```
ƒ  (Dynamic)  server-rendered on demand
```

So the route **is** dynamic today. **It does not say so.** It is dynamic only
because something in its tree reads a session — `getAccessContext()` at `:102`
and `supabase.auth.getUser()` at `:88`. Two of this phase's ten surfaces declare
their render mode; this is one of the eight that derive it.

### 2.2 What the one-line declaration would close

The same gap `D-37-09` closed on the public event page: **a later edit that moved
the session read would make this page static again with no error and no
warning.** A statically rendered ticket surface is a shared artefact carrying a
venue line, and `venue-secrecy.md`'s *gate cache e pre-render* is explicit —
*«ogni superficie che mostra il venue va marcata come dinamica e non
cacheabile»*. Today this surface satisfies that gate **by derivation**, which is
to say it satisfies it until somebody refactors something unrelated.

`nextjs-architecture.md` says the same thing from the other side: *«ogni
superficie che mostra dati per-utente o dati segreti dichiara esplicitamente di
non essere cacheabile»*. **Declaring, not deriving.**

### 2.3 Why this plan did not take it

Because it is a **render-mode change on a surface carrying money and a venue,
delivered inside a visual conversion**, and the precedent for that declaration on
the event page is a *declared decision*, not a plan's inference.

`41.2-CONTEXT.md` carries the standing rule that a file or a change outside a
plan's declared territory is an **owner decision, not a plan-level inference** —
however small and however well measured. The recorded precedent is a file that
was measured, whose measurement was right, and whose inclusion was still refused
until the owner decided it.

**A conversion that hardened a venue guard on its own authority would be doing
the right thing by the wrong route, and the next conversion would do the wrong
thing by the same route.** The direction of the change is not what makes it
safe — the authority for it is.

### 2.4 The question, in the form it should reach the owner

> Eight of this phase's ten surfaces render on demand only because something in
> their tree reads a session. Should `/tickets/[id]` — which renders a venue line
> and a ticket — **declare** its render mode, as the public event page does?
>
> - **Cost if taken:** one line, in a plan that owns the decision.
> - **Cost if not taken:** the surface keeps satisfying the no-stale-venue gate
>   by accident, and the accident is one unrelated refactor deep.
> - **What it is not:** it does not change who sees the venue line. The predicate
>   is untouched either way.
> - **Scope note:** if it is taken, the same question applies to the other seven
>   derived surfaces, and answering it once for all eight is cheaper and more
>   consistent than eight separate answers.

### 3.1 H-41.2-08-1, with the road not taken and why

Wave 0 §7.2 rows 3 and 4 dispose of both hand-written measures as **DELETE**,
with the width going *"to a construction inside the shell, **not** to a `focus`
declaration"*. Both were deleted together, as row 4 requires (*"Both go together
or the button stops matching the card"*), and `grep -c 'max-w-'` on the page file
returns **0**.

**On a phone nothing moves**: the deleted measure was 384px and the shell's
content box on a 375px viewport is narrower than that, so the card was already
edge-to-edge inside the gutters. **Above the tablet tier the card grows** to the
shell's content width.

Three ways to have kept the old width were considered and each was refused for a
stated reason:

1. **Declare the surface narrow.** **Unavailable, mechanically** — see §4.
2. **Write a `TYPOGRAPHIC_MEASURES` entry.** That mechanism is for a *reading
   measure on a text element*. Wave 0 classes both of these as **container
   maxima on a card and on a button wrapper** — there is no paragraph here — so
   an entry would be a false description of what the line is, in a list whose
   whole value is that its entries are true.
3. **Move the maximum into a component.** Check D reads the **page file only**,
   and `41.2-PATTERNS.md` §7.2 names that as *"a limit, not a permission."*
   Extracting the card to put the same measure somewhere the gate cannot see it
   is the definition of using the limit as a permission.

A fixed width (`w-96` and its neighbours) was also refused: it is 384px
**unconditionally**, so it overflows a phone by roughly 57px — a maximum and a
fixed width are not interchangeable, and swapping one for the other to satisfy a
grep would ship a horizontal scrollbar to the device this surface is used on.

### 3.2 H-41.2-08-2, with what was preserved

The pre-diff control was a pill filled with the legacy foreground token and inked
with the legacy background token. Both are on check B's legacy list and had to
go. The four-variant ladder of `41-UI-SPEC.md` §8.5 has **no inverted-fill rung**,
and adding one would be an edit to `ui/Button.tsx` — **spine, and a halt for this
phase**. So the choice was between a ladder rung and a hand-written off-ladder
fill, and the rung was taken: `variant` defaults to the accent fill, `size`
defaults to the 44px rung, and the focus expression comes from the one place that
declares it.

**Two properties were preserved deliberately, and both matter more than the
hue:**

- **The element is still an `<a href>`.** The primitive renders a plain anchor
  for an `href` — no router link, therefore **no prefetch**. A `Chip` would have
  been the wrong primitive here for exactly this reason: it renders a typed
  `Link`, and a link that prefetches would have a hover **mint a pass**. That is
  a behaviour change on a money path dressed as a styling choice, and it was
  avoided rather than discovered.
- **The address handed to it is unchanged**, character for character.

## 4. `focus` is unavailable on this surface, not deferred — and the words are not interchangeable

This surface wrote the narrow measure **by hand, twice**, which is the file
asking to be narrow. It cannot have it, and the reason is mechanical rather than
aesthetic:

- `scripts/verify-conversion.mjs` computes the set of surfaces that declare the
  narrow form **while mounting a navigation**, and reports every member of it as
  a **check-E failure**;
- the gate's own summary states the invariant as *narrow if and only if none is
  mounted*, and adds that §4's narrow list is **closed** and that **not one of
  its routes mounts a navigation**;
- **`D-41.2-01` mounts a navigation here**, and this plan landed that mount.

**Deferring implies it could be picked up later. It cannot be picked up at all
while this surface mounts a navigation.** `41.2-CONTEXT.md` `D-41.2-02` uses
exactly that word, and it is repeated here so the next reader does not re-propose
it from the shape of the file.
