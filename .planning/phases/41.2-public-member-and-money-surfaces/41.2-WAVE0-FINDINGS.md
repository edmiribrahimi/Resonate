## 0. The environment, stated before the numbers

Two facts about this checkout change how the figures below should be read, and both were
found rather than assumed.

**`npm run verify` exits 2 on this worktree, and it did so BEFORE the dry run.** One of the
sixteen gates, `verify:capabilities`, refuses (exit 2) because it needs Supabase
credentials:

```
FATAL: missing environment variable(s): SUPABASE_ACCESS_TOKEN, NEXT_PUBLIC_SUPABASE_URL.
Set them in .env.local (gitignored) or in the environment. Nothing was measured.
```

`ls -la` on the worktree root returns `.env.local.example` and **no `.env.local`**. This is
an environment condition, not a tree condition, and it is a **constant across the dry run**:
it refused identically before, during and after. It was deliberately **not** repaired —
supplying those credentials would point a gate at production, which D-41.2-04 forbids and
which this repository has an incident behind (D12: 63 rows deleted across seven tables, none
recovered, PITR not enabled).

**Consequence for every plan in this phase:** the acceptance criterion *"`npm run verify`
exits 0"* is **unreachable on a worktree without credentials** and should be read as *"the
sixteen gates report 15 passed / 0 failed / 1 refused, and the refusal is
`verify:capabilities`."* A plan that treats the exit code alone as the verdict will read a
credential gap as a conversion failure. The four gates this phase moves —
`verify:conversion`, `verify:dialogs`, `verify:breakpoints`, `verify:touch-targets` — all
exit 0 at baseline and are unaffected by the missing credentials.

### 4.2 The trap — check E uses TWO different meanings of "mount"

Under the dry run, check E's **route table** printed all ten as mounting:

```
      /                             default  mounted      AppNav.tsx + MobileNav.tsx  via  the page's own closure
      /newsletter                   default  mounted      AppNav.tsx + MobileNav.tsx  via  the page's own closure
      …
      /events/[slug]                default  mounted      AppNav.tsx + MobileNav.tsx  via  the page's own closure

      34 of 38 surface(s) mount a navigation; 4 do not.
```

…while the **pairing** in §4.1, in the same check, counted the same ten as **not mounting**.
Both are correct and they are not the same question:

- the **route table** asks *does a navigation module appear anywhere in this surface's
  closure* — and today `AppNav` is reached **through** `MobileNav`, so the answer is yes;
- the **pairing** asks *does this file import `AppNav` DIRECTLY and is it not the
  phone-locked wrapper* (`importsDirectly`, `verify-conversion.mjs:2803-2809`) — and today
  the answer is no.

**A plan that reads the route table and concludes "already mounting, no declaration needed"
ships a check-E red**, and the red is the loud direction: content sliding under a 224px
column at 768px and above. The conversion is a **change of import specifier and component
name in the page file** — nothing subtler — plus the declaration in the same commit.

### 7.3 The `TYPOGRAPHIC_MEASURES` entry for `/artists/[slug]`, spelled out

The mechanism, read from source rather than from memory — `verify-conversion.mjs:1051`
declares the shape `[pageFile, maximum, fragment, reason]`, and `:3170-3172` is the whole
matcher:

```js
const entry = measureUsage.find(
  (e) => e.pageFile === s.pageFile && e.maximum === m[0] && line.includes(e.fragment)
);
```

Three parts must all hold on the same live line, and a near-miss on any one **refuses**
(exit 2) with *"matches NOTHING: stale"* rather than failing. The entry plan 41.2-04 writes
is therefore:

| Part | Value | Why this value |
|---|---|---|
| `pageFile` | `src/app/(public)/artists/[slug]/page.tsx` | must equal the surface's declared `pageFile` **exactly** — the entry is compared against `s.pageFile` from `CONVERTED`, so it is the manifest's spelling, not the filesystem's, that has to match |
| `maximum` | `max-w-lg` | must equal `m[0]`, the token the width matcher captured — not `max-w-[32rem]`, not a substring |
| `fragment` | `whitespace-pre-line` | must satisfy `line.includes(...)` on the same live line |
| `reason` | *the artist bio is prose and reads at a measure; the shell's 1024px is a line length nobody finishes* | carried with the entry, per the file's own `[value, …, reason]` house style |

**Why `whitespace-pre-line` is the right fragment, and what makes it survive the conversion
plan 41.2-04 is about to perform on the same line.** Three measured facts:

1. **It is unique in the file.** `LC_ALL=C /usr/bin/grep -c 'whitespace-pre-line'` on that
   page returns **1**, and it is on line 126. `max-w-lg` also occurs exactly once, so the
   entry can match neither zero times (stale) nor twice (ambiguous).
2. **It is the only thing on that line that is not styling.** `whitespace-pre-line` is
   *semantic*: it preserves the line breaks an artist typed into their own bio. It is not a
   colour, not a spacing scale, not a token — so no conversion pass has any reason to touch
   it. A fragment of `mt-6` or `text-left` would be a spacing or alignment utility, and
   those are exactly what a conversion rewrites.
3. **Line 126 carries no other conversion pressure at all**, and this is the measured part.
   Under the dry run:
   - check A found **zero** raw palette hits in the whole file;
   - check B's twelve legacy-token hits in that file are at lines **56, 69, 72, 116, 143,
     154, 159** — **line 126 is not among them**. `text-muted` is not one of the four legacy
     roots (`card`, `card-border`, `background`, `foreground`);
   - the file's three G5 failures are at **:54, :111, :140** — not :126;
   - `src/components/ui/Typography.tsx` exports only `PageTitle` and `SectionHeading`
     (`grep -nE "^export (function|const)"`). **There is no body-text primitive**, so a `<p>`
     stays a `<p>` and this line is not a candidate for a primitive swap.

   **The only reason plan 41.2-04 opens line 126 at all is the maximum itself.** With the
   entry written, it does not need to open it.

**Write the entry in the same commit as the declaration, per D-41-16** — the mechanism was
placed before its first red run precisely so this arrives as a line rather than as an
argument with a gate.

### 7.4 `/tickets/[id]` — `focus` is unavailable, and the reason is check E

Rows 3 and 4 remove a 384px measure that is written by hand **twice**, and the obvious
disposition is *"declare the surface `focus` — the shell's focus form is `max-w-sm`, and
the maximum goes away by itself."* **That disposition is not available**, for a mechanical
reason and not a stylistic one:

- `verify-conversion.mjs:3372` builds
  `mountsUnderTheFocusForm = navigationBySurface.filter((s) => s.mounted && s.width === 'focus')`,
  and `:3613` reports every member of it as a **check-E failure**: *"N focus surface(s)
  mount a navigation the focus form reserves nothing for"*.
- The gate's own summary line states the invariant: *"all converted surface(s) declare the
  width their mounted navigation calls for — **focus if and only if none is mounted**"*, and
  `:2503` adds that §4's focus list *"is closed at four routes and NOT ONE OF THEM mounts a
  navigation"*.
- **D-41.2-01 mounts a navigation on all ten**, including this one.

So the width for `/tickets/[id]` is `default`, both maxima are deleted, and whatever narrow
column the ticket card needs is rebuilt **inside** the shell by a construction that is not a
container maximum. This is what D-41.2-02 means when it calls `focus` here *unavailable*
rather than *deferred*: deferring implies it could be picked up later, and it cannot be
picked up at all while the surface mounts a navigation.
