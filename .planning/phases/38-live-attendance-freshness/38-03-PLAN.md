<objective>
Put the reload discipline in place **before** anything can trigger a reload.

Purpose: this plan is where LIVE-02 stops being a promise. The channel does not
reach the verdict because there is exactly one way to ask for a reload, and that
way defers behind the scan lock. The reason is not React rendering: `mergeAttendees`
writes the same IndexedDB object store the offline verdict reads, and IndexedDB
serialises `readwrite` transactions on a store — so an unguarded merge really can
put itself between a scan and its answer, invisibly, in a way that looks like two
ordinary `await`s in review.

It also puts the parachute up. The safety reload is re-armed on every successful
fetch rather than run on a fixed period, which is what makes "this is not polling"
a fact instead of a claim: on a night with a queue in front of the door it fires
zero times.

Output: `ScannerClient.tsx` gains `requestReload`, `pendingReloadRef`,
`lastFetchAtRef` and one re-armed foreground-only timer. Nothing subscribes to
anything yet — plan 38-05 does that, and it will find the entry point already
here.

### Decisions this plan records

- **D-38-22.** A live reload that arrives while the operator is typing in the
  search box keeps `fetchAttendance(searchQuery)`, and therefore does **not** merge
  into IndexedDB — the existing `if (eventData && !search)` guard skips it. This is
  accepted, not fixed. The alternative changes what the operator sees mid-typing,
  and the phase's boundary says no change to how a scan is decided and no new
  surfaces; the cache catches up on the next unfiltered fetch and the safety timer
  re-arms regardless. The sentence goes in the code beside the call, because the
  next reader's instinct is to "repair" it into a merge of a filtered list — which
  is exactly the shrinking payload `mergeAttendees` already refuses.
- **D-38-23.** The coalescing window is 500 ms and the safety period is 5 minutes.
  Both are proposals with assumptions attached (A3, A2) and both are written as
  named constants with the assumption id in the comment, so that adjusting one is
  a decision with a number rather than a tweak.
</objective>
