<objective>
Write the one migration this phase needs: a fan-out helper that emits an empty
signal, four `AFTER` triggers that call it, and a single `SELECT` policy that
decides who may hear it.

Purpose: this file is where LIVE-01 and LIVE-06 are actually decided. Everything
on the device is discipline; this is the boundary. `access-gating.md` states it
plainly — the middleware decides where someone may go, RLS decides what they may
read — and a channel gated on the client is that error in a new costume.

**This plan writes the file. It does not apply it.** Plan 38-04 applies it,
behind a blocking checkpoint, after the owner has read the SQL. A build and a
typecheck pass without the migration being applied, because no Supabase client in
this repository is parameterised with `Database`; that is precisely why the apply
is its own `[BLOCKING]` step and not a footnote here.

Output: `supabase/migrations/20260811120000_live_attendance_channel.sql`, one
`BEGIN; … COMMIT;`, idempotent.

### Decisions this plan records, so they are visible rather than inherited

- **D-38-17 (F3, naming).** The policy is `realtime_messages_select_door_assigned`.
  `38-RESEARCH.md` § Pattern 5 proposed `door_attendance_broadcast_read`; the
  house form, declared at
  `supabase/migrations/20260809004600_event_media_quarantine_bucket.sql:129-133`
  and used by every policy since `20260805120000_door_scan_events.sql`, is
  `<subject>_<verb>_<question>` — `door_scan_events_select_admin`,
  `event_media_quarantine_insert_approved`. In both precedents the subject slot
  names the object the policy sits on. This policy sits on `realtime.messages`.
  Two naming forms coexisting is how a greppable convention stops being one.
- **D-38-18 (F1, the forgeable emit).** The fan-out helper is created as
  `private.notify_attendance_changed(uuid, uuid)` **and** carries an explicit
  `REVOKE ALL … FROM public, anon, authenticated` with no re-grant. Both, not
  either: the schema removes it from PostgREST's reach, the revoke is the
  greppable evidence and survives a future schema exposure change. Taking two uuid
  arguments makes it an ordinary callable function, not a trigger function — the
  `20260809004500_event_media_party_id.sql:253-262` paragraph about trigger
  wrappers needing no grant pair does **not** transfer to it.
- **D-38-20.** No trigger on `public.attendances`. `/api/tickets/attendance` does
  not read that table, and a membership admission always writes a
  `door_scan_events` row, which is covered. Whether the attendee list should show
  membership admissions is a question about the list, not about freshness
  (`38-RESEARCH.md` Open Question 4).
- **D-38-21.** No `WHEN` clause narrowing the triggers to "real" changes. A filter
  slightly too narrow drops a real change and leaves a stale list at a door; one
  too wide costs one GET. `checkin-offline.md` already states which direction to
  err in, and it points the same way here.
- **D-38-24 (new).** On `UPDATE`, a wrapper emits for the **old** night as well as
  the new one whenever the pair `(party, event)` actually changed. Without it, a
  ticket or a guest-list entry moved from one night of an event to another
  notifies only the destination door: the door that just **lost** an attendee is
  told nothing and falls back to the five-minute parachute. That is the same
  hiding shape as Pitfall 1 — every screen looks right while LIVE-01 has quietly
  become LIVE-04 for that door — and this phase has refused that shape everywhere
  else. It is also the expensive direction: `checkin-offline.md`'s asymmetry is
  about the door with a queue in front of it, and a stale list at the origin
  night reads a person who is no longer expected there as expected.
</objective>

    Three things about that guard, each of which is the reason it is written this
    way rather than another:

    - **`IS DISTINCT FROM`, not `<>`.** Both columns are nullable on three of the
      four tables, and `<>` answers `NULL` — neither true nor false — precisely on
      the transitions that matter: a row leaving the event level for a single
      night, or arriving at it. `IS DISTINCT FROM` treats null as a value and
      answers.
    - **The guard is what keeps the hot path at one emit.** The door's own
      check-in updates `public.tickets` on every scan without touching the party
      or the event, so the comparison is false and exactly one message is sent —
      the same as today. The second emit happens only on a genuine reassignment,
      which is rare and is the case that is currently invisible.
    - **The old branch inherits the fan-out for free.** Passing the old pair to
      the same helper means an old `party_id` of `NULL` fans out over every night
      of the old event — which is correct, because an event-level row that becomes
      a single-night row was valid for all of them. It also covers a row moved
      between two **events**, since the old event id travels with it.

    trigger to `AFTER UPDATE OF party_id`: an update to any other column —
    `checked_in`, `status` — also changes the attendee list and must still emit

    a second message is owed.
