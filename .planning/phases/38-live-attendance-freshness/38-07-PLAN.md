    1. **P3 — the pocket.** On the actual staff phone, door installed to the home

       This is the only procedure that settles assumption **A1** — that a suspended

       hand, and only the device says whether the composition works. It cannot be
       simulated from a desk.

    2. **P6 — the null-party fan-out.** This one creates a row in production, and
       this project lost 63 rows to a verification script on 2026-08-10. Four rules,
       and none of them is optional:

       - **Snapshot first**, over every table reachable by cascade from
         `guest_list_entries`, enumerated by reading the foreign-key constraints
         rather than remembered. A cascade is a write path nobody declared.
       - **Capture the primary key at creation time.** Not the name, not the email,
         not a position in a list.
       - **Delete by that primary key**, from the database. Never by clicking a
         delete control, never by selecting on a label, never by walking up a DOM
         tree — that is exactly the shape of the incident, and the direction of the
         two failures is the point: a selector that is too wide deletes more than it
         should, a primary key that is wrong finds nothing.
       - **Confirm from a different source than the one you acted on.** A count read
         from the page you just manipulated is an echo, not a measurement.

       The observation, in two acts on the same row and therefore on one
       authorisation. **Act one:** on an event with at least two nights, adding a
       guest-list entry with **no party** must make **both** doors reload. If only
       one reloads — or if neither does but both refresh five minutes later — the
       fan-out is not working and LIVE-01 has quietly become LIVE-04.

       **Act two — the reassignment (D-38-24).** Before deleting, assign that same
       entry to one of the event's nights. **Both** doors must reload: the night
       that gained it and the night that lost it. Move it to the other night and
       watch both again. If only the destination door reloads and the origin door
       catches up five minutes later, the old-pair emit is missing — and note that
       both doors will *eventually* be right, which is exactly why this has to be
       watched rather than inferred. Then delete the row by the primary key
       captured in act one.

       **Your authorisation to write to production is spent once, on exactly this —
       both acts, one row.**
       If the procedure has to be repeated, it is asked for again.
