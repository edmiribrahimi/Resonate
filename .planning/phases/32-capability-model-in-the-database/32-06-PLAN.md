<objective>
Write and apply the migration that creates the single definition: a `private` schema
holding a capability catalogue and a role-to-capability grant table, one resolver
function, and exactly one argument-less wrapper exposed in `public`. Name the same
eight keys once on the TypeScript side.

Purpose: CAP-01 says every capability is defined once and evaluated by the same
function whichever tier asks. CAP-04 says a grant takes effect on the next request.
Both are settled by where this migration puts things: in SQL, because a row-level
policy cannot call TypeScript; and out of the token, because this project's access
tokens live for 3600 seconds.

**No policy changes in this plan.** After it, B1 must be **byte-identical** to the
committed baseline and `auth_rls_initplan` must still be 26. A model that has been
created but not yet wired changes nothing, and proving that is the point.

Output: one applied migration, one TypeScript key module, updated hand-written types.
</objective>

<phase_decisions>
- **D-01** — the evaluator is SQL in a **non-exposed `private` schema**; TypeScript
  calls it. The placement is forced, not chosen: a policy cannot invoke application
  code.
- **D-02** — the two organizer shapes stay **two**. Thirty-four policies ignore
  `status`; four require `approved`. The disagreement is carried as a
  `requires_approved` column on the grant row. **Collapsing them is this phase's single
  unrecoverable CAP-03 defect** and no argument at execution time overrides this.
- **D-03** — capabilities never enter the JWT. Measured on this project:
  `hook_custom_access_token_enabled = false`, `jwt_exp = 3600`, so a token-carried
  capability would be stale for up to an hour. **Supabase's own RBAC guide recommends
  exactly that approach**, so the prohibition is written into the migration *with its
  reason*, or the next reader will propose it again.
- **D-04** — exactly one exposed wrapper, and it takes **no argument**. This
  repository has no rate limiting anywhere (`access-gating.md`, verified 2026-08-05),
  so a `has_capability(user_id, cap)` reachable over REST would be a free enumeration
  oracle. The shape of the API is the mitigation, because there is no limiter to add.
- **D-06** — the two `private` tables get **no RLS policy**, and the reason is written
  beside the omission: PostgREST exposes `public,graphql_public` only, so nothing in
  `private` is reachable over REST. That is a stronger answer than RLS. Without the
  paragraph the next reader repairs a non-bug — and the plausible repair, adding
  `private` to the exposed schemas so the tables "work", would turn every helper into a
  REST endpoint.
- **D-07** — both new functions are **`language sql`**, diverging deliberately from
  the four existing `plpgsql` helpers. A SQL body can be inlined by the planner and is
  the shape Supabase's examples use. Declared here rather than switched silently.
- **D-08** — `public.my_access_context()` **derives** its capability list by asking
  `private.has_capability` once per catalogue row. It does **not** re-implement the
  grant join. Two implementations of one table-driven rule are two definitions, which
  is what CAP-01 forbids; `32-RESEARCH.md` Pattern 2 sketches the duplicated join, and
  this is a deliberate improvement on it.
- **D-10** — the resolver ships as
  `private.has_capability(p_capability text, p_party_id uuid default null)` with the
  second parameter **accepted and unused**. Phase 35 adds a grant source by editing the
  body; no policy and no caller changes. Adding the parameter later would mean
  rewriting every policy body.
- **D-14** — the key set is **eight keys**, named by the **question asked**, not by the
  predicate. Three keys share one predicate today (`staff.manage`,
  `organizer.access`, `door.operate`); keeping them distinct is what lets Phase 35
  grant a night's door without granting sixteen tables.
</phase_decisions>
