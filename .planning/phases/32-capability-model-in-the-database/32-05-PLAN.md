<objective>
Build the instrument that turns the baseline into a verdict: a comparator that reads
the committed pre-phase artefacts and a fresh capture, and answers one question per
artefact — **did anything move that the whitelist does not explain?**

Purpose: 67 policies cannot be compared by reading a diff. Without a mechanical
comparator, CAP-03 is an opinion. The whitelist is what makes the comparison strict:
exactly **two** transformations are legal, and everything else is a defect until a
human overrules it in writing.

Output: `scripts/rls-baseline-compare.mjs` and one npm entry. No database change.
</objective>

<phase_decisions>
- **D-23** — the whitelist has exactly **two** entries and no third is added later
  without an explicit written decision in `32-VERIFICATION.md`:
  **(T1)** the token `auth.uid()` becomes `(select auth.uid())`;
  **(T2)** a P1–P5 predicate fragment becomes `(select private.has_capability('<key>'))`.
  T2's legal left-hand sides are enumerated by the comparator, not matched by a loose
  pattern: `(SELECT public.is_admin_or_organizer())`, `(SELECT public.is_master())`,
  the two inline `EXISTS` shapes on `public.profiles` used by `artists` and `venues`,
  and `(SELECT public.get_user_status()) = 'approved'`.
- **D-24** — a policy **added**, **dropped** or **renamed** is a defect regardless of
  predicates. `supabase-data.md`, gate *RLS contestuale*: permissive policies are OR'd,
  so an added policy widens; and B1 compares `policyname`, so a rename destroys the
  comparison itself. Predicates are replaced **in place** under the existing name,
  whatever a naming convention would have preferred.
- **D-25** — the comparator never "fixes" a mismatch and never rewrites a baseline.
  Its only outputs are a verdict, a defect list and an exit code.
</phase_decisions>

artefact files given by `--before` and `--after` (defaulting to the committed
pre-phase file and a freshly captured one). Same reporter and exit codes as the rest
of the harness: `0` clean, `1` a defect, `2` a wrong environment.

Structural comparison first, before any predicate is read. Build the set of
`(tablename, policyname, cmd)` triples on each side. Any triple present on one side
only is a defect of kind `policy_added`, `policy_dropped` or — when a predicate
matches under a different name — `policy_renamed` (D-24). Report the table and the
policy name. Also compare `permissive` and `roles` per triple: a `TO` clause added or
removed is a defect, and `event_media_insert_member` is the one policy in the set
carrying `TO authenticated`, so the column is not decorative.

Predicate comparison second. For each surviving triple, take the before `qual` and
`with_check` and generate the set of strings reachable by applying the whitelist:

  - **T1** — every occurrence of the token `auth.uid()` replaced by
    `(select auth.uid())`. Apply to any subset of occurrences, since a policy may have
    some occurrences resolved by T1 and others removed by T2. Compare after Postgres's
    own normalisation, which is what `pg_policies` re-prints; do not attempt to parse
    SQL, and normalise only whitespace and the case of the leading `SELECT` keyword.
  - **T2** — one of the enumerated legal left-hand sides (D-23) replaced by
    `(select private.has_capability('<key>'))` where `<key>` is any single-quoted
    identifier. Record which key each replacement used, so the run can report the
    capability-to-policy mapping as a by-product — the phase gate needs that mapping
    and it should be derived from the applied database, never hand-maintained.

If the after predicate is reachable, record the transformations used. If it is not,
emit a defect of kind `predicate_unexplained` carrying the table, the policy, the
before string and the after string, and exit `1`.

Print a summary: how many policies unchanged, how many by T1, how many by T2, how
many by both, and how many unexplained. Add
`"baseline:compare": "node scripts/rls-baseline-compare.mjs"` to `package.json`.
