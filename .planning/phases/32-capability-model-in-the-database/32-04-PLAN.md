<objective>
Give the baseline the personas production does not have, then capture and commit the
pre-phase baseline on **both** targets.

Purpose: production holds four profiles — one master and three members, all approved.
**There is no organizer and no non-approved row**, and `organizer/pending` is
precisely the pair where the two definitions of "organizer" disagree. Production
gives schema truth; only a container gives persona coverage. Neither alone is
sufficient.

This plan closes Wave 0. After it, and only after it, the first migration file of
this phase may be written.

Output: a throwaway PostgreSQL 17.6 target, its shim and seed, and eight committed
baseline artefacts.
</objective>

<phase_decisions>
- **D-20** — the container is **PostgreSQL 17.6**, matching production exactly. Plan
  `31-03` used 16.14; the InitPlan behaviour this phase depends on was proved on 17.6
  and a baseline captured on a different major version is a baseline of a different
  planner. **Docker was verified available on this machine on 2026-08-06** (server
  29.2.1), which closes `32-RESEARCH.md` assumption A7 and
  `32-VALIDATION.md` § *Known blocking dependency*.
- **D-21** — the container is built from `supabase/migrations/**` (33 files as of
  2026-08-06), applied in filename order, plus a shim for the objects Supabase
  provides and a bare Postgres does not. **The shim is the only hand-written schema in
  the container**, and `auth.uid()` in it is copied verbatim from the production
  definition so that the two targets evaluate the same function body.
- **D-22** — the container's B1 is expected to differ from production's, because the
  migration files have drifted from what is applied before (`31-VERIFICATION.md`
  records a foreign key on `pending_purchases` that no plan had seen). **That
  difference is a finding to record, not a failure**: production is the schema truth,
  the container is the persona truth, and each artefact carries its `target`.
</phase_decisions>

  <action>
Create `scripts/container/auth-shim.sql`, applied **before** the repository's
migrations. It creates: the roles `anon`, `authenticated`, `service_role`; schema
`auth` with a minimal `auth.users(id uuid primary key)` table for the foreign keys
`public.profiles` declares; the functions `auth.uid()`, `auth.jwt()` and
`auth.role()` **copied verbatim from the production definitions** — fetch them once
with `pg_get_functiondef` through the Management API and paste them into the file,
with a comment recording the date they were copied and the fact that they are SQL,
`STABLE`, and **not** `SECURITY DEFINER`; and schema `storage` with a
`storage.buckets` table carrying the columns the venues migration inserts. Grant
`usage` on the `public` schema and the usual table privileges to `anon` and
`authenticated`, because a bare Postgres grants nothing and RLS only narrows what a
grant already allows — a missing `GRANT SELECT` would make every persona read zero
rows and the whole baseline vacuously identical.

Create `scripts/rls-baseline-container.mjs`. It starts `postgres:17.6` on an ephemeral
port with a throwaway password, waits for readiness by polling, applies the shim,
then applies every file in `supabase/migrations/` in filename order, halting on the
first error and printing the filename and the SQLSTATE. It connects with `pg`
(`^8.18.0`, already a devDependency, and this is the first committed file to import
it). It exposes the **same target function signature** as `scripts/rls-baseline.mjs`
so the capture code is shared rather than copied, including the `read_only` flag —
which on this target maps to a `set transaction read only`. It always destroys the
container, including on failure, and it never runs against anything but a container it
created.

Add `"baseline:container": "node scripts/rls-baseline-container.mjs"` to
`package.json`.

Refusals: exit `2` if `docker` is not on the path or the daemon is not answering;
exit `1` if `select version()` inside the container does not report 17.6; exit `1` if
fewer than 20 tables report `relrowsecurity` after the migrations have run.
  </action>
  <verify>
    <automated>npm run baseline:container -- --smoke && docker ps -a --filter "ancestor=postgres:17.6" --format '{{.Names}}' | wc -l</automated>
  </verify>
  <acceptance_criteria>
    - A smoke run builds the container, applies the shim and all 33 migration files
      without error, reports `17.6` and **20** RLS-enabled tables, then destroys the
      container; `docker ps -a` shows no leftover container afterwards. All four
      observations pasted into the SUMMARY.
    - If a migration file fails to apply, the run stops and names the file and the
      SQLSTATE — observed by temporarily pointing the applier at a deliberately broken
      copy, then reverting. Mutation asserted as applied before its result is read.
    - `scripts/container/auth-shim.sql` contains `auth.uid()` with a comment recording
      the date its body was copied from production and that it is not
      `SECURITY DEFINER`.
    - Stopping the Docker daemon makes the run exit `2`, not `1` — the environment is
      wrong, not the measurement.
  </acceptance_criteria>
  <done>A throwaway PostgreSQL 17.6 database can be built from this repository and destroyed again, and the capture code reaches it through the same function it uses for production.</done>

  <action>
Create `scripts/container/seed.mjs`, called by the container target after the
migrations. It inserts, as the container superuser (RLS does not apply to the owner,
which is what makes seeding possible at all):

  - **Nine profiles**, one per `role` × `status` pair, with deterministic synthetic
    uuids derived from the persona label so a re-run seeds identical data and the
    fingerprints are stable across runs. Their `auth.users` parents are inserted
    first. Email and name fields carry obviously synthetic values; nothing resembling
    a real address.
  - **At least two rows in every one of the 20 tables**, and where the table has an
    owner column, the two rows are owned by **different personas** — one by
    `member/approved`, one by `master/approved`. This is the difference between a
    baseline and a green screen: without it, "mine" and "not mine" are
    indistinguishable and an inverted policy would not move a single fingerprint.

Reuse `PROBE_PAYLOADS` for the column lists so that the seed and the write matrix
cannot drift apart. Refuse to proceed (exit `1`) if, after seeding, any of the 20
tables holds fewer than two rows, or if any table with an owner column holds rows
owned by only one persona. Print the per-table row count.
  </action>

  </verify>
  <acceptance_criteria>

      The per-table report is pasted into the SUMMARY.
    - Nine profiles exist, one per role × status pair, confirmed by a grouped count
