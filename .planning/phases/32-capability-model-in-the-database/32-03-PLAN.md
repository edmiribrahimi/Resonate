<objective>
Complete the evidence harness with the two artefacts that measure what the database
actually **permits**: **B2**, the persona read matrix, and **B3**, the persona write
matrix — the only artefact that can baseline a `WITH CHECK` clause.

Purpose: four of this phase's five inherited predicates (P3 and P5) live in `WITH
CHECK` clauses, which no read ever touches. Without B3 the phase cannot tell a
preserved rule from a widened one on `artists`, `venues`, `event_media` or `rsvps`.

Output: `scripts/rls-baseline.mjs` gains `B2` and `B3` under the same `--only` flag
and the same determinism contract. No artefact is committed by this plan — the first
capture is plan `32-04`.
</objective>

<phase_decisions>
- **D-11** — the persona set is the **full 3×3 role × status grid**, plus
  `authenticated/no-profile`, plus `anon` — **eleven personas**. The grid is the
  minimum that can distinguish P1 from P3 (`organizer/pending` is the pair where they
  disagree); `authenticated/no-profile` exists because the middleware's `?? "member"`
  default and the `NULL`-versus-`false` behaviour of `is_admin_or_organizer()` for a
  missing profile row are both behaviour, and neither is observable with any other
  persona. A persona that does not exist on a target is recorded as `absent`, never
  omitted.
- **D-18** — a write probe's result is `ok:<affected_rows>` or the SQLSTATE. `ok`
  alone is not evidence: an `UPDATE` filtered to zero rows by a policy succeeds and
  changes nothing, and `ok:0` versus `ok:1` is exactly the difference a widening would
  move.
- **D-19** — a probe result outside `{ok:*, 42501}` (typically `23503`, a foreign key
  with nothing to point at on a nearly-empty production) is recorded with
  `conclusive_for_rls: false`. It still must be identical before and after; it simply
  proves less. Hiding it would be worse than recording it.
</phase_decisions>

Persona resolution. Add a resolver that, given a target, returns the eleven persona
labels with, for each, either the subject uuid to impersonate or `absent`. `anon` is
impersonated by setting the claims role to `anon` and `set local role anon`.
`authenticated/no-profile` is impersonated with a uuid generated by
`crypto.randomUUID()` that is asserted **not** to exist in `public.profiles` — no
data is needed for it, so it is available on every target. The nine
`role/status` personas are looked up with a single read-only query selecting, for
each `(role, status)` pair, the lowest `id` ordered by `id` so the choice is
deterministic. **The uuid is used and discarded: only the label reaches the
artefact** (D-11, `CLAUDE.md` Guardrail 5).

Table enumeration. Read the `public` tables with `relrowsecurity` true and, for each,
its primary-key column list from `information_schema.key_column_usage`. Refuse to
proceed (exit `1`) if fewer than 20 tables come back, or if any table reports no
primary key — a fingerprint without a stable key is not a fingerprint.

The B2 probe. One request per persona: a read-write transaction that opens `begin;`,
sets `request.jwt.claims` to a JSON object carrying `sub` and `role`, issues `set
local role`, then for each of the 20 tables selects the visible row count and
`md5(coalesce(string_agg(<pk expression>, ',' order by <pk expression>), ''))`, and
ends with `rollback;`. Reads cannot write, so batching all 20 tables into one
persona-transaction is safe and keeps the request count at eleven; the one-probe-per-
request rule in Task 2 applies to writes.

Emit rows as `{persona, table, count, pk_md5, vacuous}` sorted by `(persona, table)`,
where `vacuous` is true when `count` is zero — because a fingerprint of the empty
string proves nothing and the comparator must be able to say how much of the matrix
is vacuous rather than quietly counting it as agreement. Write
`32-BASELINE-reads.json` with `artefact: "B2"`.

Refusals: exit `1` if any persona resolves to `absent` on a target where it was
expected to exist, and exit `1` if **every** row of the matrix is vacuous.

  <action>
The payload table. Declare a `PROBE_PAYLOADS` constant: one entry per RLS-enabled
table, giving the `INSERT` column list and a minimal valid value expression, plus the
column an `UPDATE` may set to its own current value. Write one comment line per entry
naming what makes the row valid. **The harness refuses to run B3 (exit `1`) if any
enumerated table has no entry** — the `verify-persona.mjs` refusal pattern applied to
coverage: a write matrix that silently skips a table is a matrix that cannot fail.
Foreign keys are satisfied by selecting an existing id from the referenced table
inside the same transaction; where none exists the insert will fail with `23503` and
the cell is marked `conclusive_for_rls: false` (D-19).

The probes. For each persona, table and verb, **one request, one probe**:
`begin;` → set claims → `set local role` → the single statement → `rollback;`.
`INSERT` uses the payload. `UPDATE` sets one column to its own value with a `WHERE`
clause naming a single existing primary key. `DELETE` targets the same key. Capture
the affected row count from the statement result and record `ok:<n>`; on failure
record the SQLSTATE alone, never the message (a message can carry a value from the
row).

The rollback guarantee, as two independent clauses reported separately:
  1. **Before** any request is sent, assert of every probe string that it ends with
     `rollback;` and contains no `commit` in any casing. A probe that fails this
     assertion aborts the whole run with exit `1` before a single byte reaches the
     network.
  2. **After** the run, re-read all 20 table row counts with `read_only: true` and
     assert each equals the count read before the run started. A mismatch exits `1`
     and prints the table — this is the only thing standing between a probe and a
     permanent write.

Emit rows as `{persona, table, verb, result, conclusive_for_rls}` sorted by
`(persona, table, verb)`. Write `32-BASELINE-writes.json` with `artefact: "B3"`.

Note in the file header, in prose, why the probes cannot be sent with
`read_only: true`: that flag rejects `set role` with `42501`, so the safety comes
from the trailing `rollback;` and the row-count re-assertion, not from the API.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| script → production database, read-write | the only place in this phase where a script sends a statement that could write |
| impersonated role → RLS | the probe deliberately assumes another subject's identity inside a transaction |
| working tree → public repository | the artefacts are published |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-32-03-01 | Tampering | a write probe that commits to production | mitigate | two independent clauses: every probe string asserted to end `rollback;` and contain no `commit` **before** the request is sent, and all 20 row counts re-asserted unchanged after the run; both reported separately and both proved by mutation |
| T-32-03-02 | Information disclosure | persona uuids or member data reaching a public artefact | mitigate | labels only; fingerprints are an md5 of the sorted primary keys, never the keys; SQLSTATE without message text; asserted by grep on the written file |
| T-32-03-03 | Repudiation | a matrix that agrees because it measured nothing | mitigate | `vacuous` flag per read cell, refusal if the whole matrix is vacuous, and the two named cells (`member`→`venues` `42501`, `master`→`venues` `ok:1`) required as evidence that impersonation works |
| T-32-03-04 | Elevation | the harness accidentally probing as the service role and reporting a permissive baseline | mitigate | `set local role` inside the transaction, plus the acceptance criterion that `master/approved` must see strictly more than `anon` on at least one table |
| T-32-03-05 | Denial of service | ~700 serialised requests against production | accept | the probes are single statements inside rolled-back transactions on a database holding 4 profiles and 2 events; production traffic is nil during construction (`STATE.md`: no event is published) |
| T-32-03-SC | Tampering | npm installs | mitigate | this plan installs nothing; node built-ins and `fetch` only |
</threat_model>
