<objective>
Close the gap the compiler cannot: assert that the same eight capability keys exist in
`src/lib/capabilities/keys.ts`, in `private.capabilities`, and in the predicates and
route rules that ask for them.

Purpose: `src/lib/door/outcome.ts` gets half its cross-check for free, because its
literals are mirrored by a SQL `CHECK` constraint. A capability key is checked by
**nothing**. It is a string inside a policy body, a string in a table, and a string in
a TypeScript object, and no Supabase client in this repository is parameterised with
`Database`, so `npm run build` proves none of them exists. This is CAP-01 evidence
(iii), and without it "one definition" holds in the database and is a string literal
everywhere else.

Output: `scripts/verify-capabilities.mjs` and one npm entry.
</objective>

<phase_decisions>
- **D-33** — the check has **four sides**, not three: `keys.ts`, `private.capabilities`,
  the keys used inside policy predicates, and the keys used in `src/`. The fourth exists
  because Phase 34's CAP-02 will fail the production build for a capability mapped to no
  route, and a key that no caller asks for today is exactly that failure arriving early.
  It is reported as a **warning with a named key**, not a failure — Phase 34 owns the
  decision, and four of the eight keys gate tables rather than routes.
- **D-34** — every check is proved by deliberately breaking the invariant, watching it
  fire, and restoring — **and the mutation is asserted as applied before its result is
  read** (`ai-engineering.md`, gate *prova per mutazione*). That gate was written from an
  incident in `scripts/verify-persona.mjs`, where a substitution silently failed to match
  and a working check looked broken; in the other direction the same error certifies a
  dead check as working.
- **D-09** — English.
</phase_decisions>

Create `scripts/verify-capabilities.mjs`, ESM, node built-ins only, reusing the target
function from the baseline harness. Header comment in `verify-persona.mjs`'s voice:
why this script exists, and — the sentence that matters — that `npm run build` cannot
do this because no client is parameterised with `Database`, so a misspelled capability
key is a runtime denial, not a compile error.

Collect four sets:

  - **TS** — the values of the `CAP` object in `src/lib/capabilities/keys.ts`, read
    from the file rather than imported, so the script does not depend on a build step.
  - **DB** — `select key from private.capabilities`, read-only.
  - **POLICY** — every single-quoted argument to `private.has_capability(` appearing in
    any `qual` or `with_check` in `pg_policies` for schema `public`, read-only and from
    the applied database, never from the migration files.
  - **SRC** — every `CAP.` member reference under `src/`, excluding `keys.ts` itself.

Report four comparisons, each in **both** directions and each naming the offending key:

  1. TS versus DB — a key in TypeScript with no catalogue row, and a catalogue row with
     no TypeScript key. **Failure.**
  2. POLICY versus DB — a policy asking for a key that is not in the catalogue (which
     would deny silently forever, since `has_capability` returns false for an unknown
     key), and a catalogue key no policy uses. The first is a **failure**; the second is
     reported together with comparison 3.
  3. SRC versus DB — a `CAP.` reference resolving to a key with no catalogue row is a
     **failure**.
  4. Unused keys — a catalogue key asked for by neither a policy nor `src/` is a
     **warning** naming the key, with a line saying Phase 34's CAP-02 will make this a
     build failure (D-33).

Refusals, in the spirit of `verify-persona.mjs:225-233`: exit `2` if the environment is
wrong, and exit `1` if any of the four sets is **empty** — an empty set makes every
comparison vacuously green, and a check that cannot fail is not a check. Expect eight
keys on each of TS and DB; state that number as a pre-registered constant with the
comment that if it trips, the correct response is to look at the model, not to change
the constant.

Add `"verify:capabilities": "node scripts/verify-capabilities.mjs"` to `package.json`.
