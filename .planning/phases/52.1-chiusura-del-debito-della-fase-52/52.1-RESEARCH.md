## Summary

La fase e' una somma di quattordici chiusure piccole, ma tre scoperte di oggi
cambiano il piano rispetto a quanto il CONTEXT da' per scontato.

**Prima: la gallery non e' sola sui suoi pezzi.** L'archivio fotografico del
visual (`/admin/visual`, sezione di produzione) **usa lo stesso bucket di
quarantena `event-media-quarantine`** (`src/lib/media/finalize.ts:96`), lo
stesso modulo `finalize.ts`, la funzione `mayUploadToVisualSection` di
`may-upload.ts:351`, `upload-limits.ts` e lo stripper, attraverso la route viva
`src/app/api/media/finalize-archive/route.ts`. D-52.1-17 elenca fra le cose da
togliere proprio la quarantena e `may-upload`: tolti come scritto, l'archivio del
visual si rompe. **Il perimetro della rimozione va ristretto** a cio' che e' solo
della gallery (§DBT-13), oppure il proprietario decide di togliere anche
l'archivio. E un secondo fatto pesa sulla migration: Supabase blocca con un
trigger a livello di istruzione **ogni `DELETE` su `storage.buckets`**, anche a
zero righe — i bucket si cancellano dall'API di Storage, non da SQL.

**Seconda: «verify verde» ha quattro ostacoli, non tre.** Oltre ai due rossi
dichiarati (`verify:tables`, `verify:breakpoints` A e B) `verify:conversion`
esce **2 — RIFIUTATO** per una riga di `PageShell.tsx:164` cambiata il
2026-09-24 (`pt-6 md:pt-12`): un rifiuto non e' un passaggio, e `verify-all`
esce 2 finche' resta. La riga sta dopo il ritorno del ramo `focus`, quindi la
correzione e' rifissare il digest (§DBT-16). Siccome D-52.1-21 rende il verde
**precondizione del primo deploy della 52.1**, DBT-16 va nella prima onda.

**Terza: alcune cose sono gia' fatte o cambiano forma.** Il 16:9 della cover e'
**gia' in produzione dal 2026-09-24** (`events/[slug]/page.tsx:1323-1329`,
`aspect-video`, il `max-h-80` non c'e' piu'); le cinque cover di produzione sono
tutte 16:9 e **nessuna ha un blocco GPS** (letto oggi). La pagina «Door review»
(`/admin/events/[id]/review`) **non ha nessun link in ingresso** oltre a se
stessa: il controllo inverso di DBT-19 la segnalera' al primo giro, e serve una
decisione. «Who works» offre ancora l'assegnazione **«Photo»** (`media.upload`),
che dopo DBT-13 non aprira' niente.

**Raccomandazione primaria:** onda 1 = DBT-16 + DBT-19 + DBT-20 (nessuna
migration, spedibili subito, verde ripristinato); onda 2 = DBT-17 + DBT-18 (una
migration additiva); onda 3 = DBT-13 ristretto + DBT-14 (codice, poi atto per
policy e rimozione); onda 4 = DBT-15, DBT-05, DBT-06/07, DBT-04, DBT-10 e la
VERIFICATION. Libreria di trascinamento: `@dnd-kit/core` 6.3.1 + `@dnd-kit/sortable`
10.0.0 con `TouchSensor` a 500 ms. Sorgente d'ingresso: `utm_source` letto dal
client e ridotto a un vocabolario chiuso.

### Pattern 2: una scrittura per l'ordine intero (DBT-18)
```sql
-- schema, non codice finale
CREATE FUNCTION public.reorder_ticket_tiers(p_event_id uuid, p_party_id uuid, p_tier_ids uuid[])
RETURNS integer LANGUAGE plpgsql SECURITY INVOKER SET search_path = public AS $$
DECLARE v_scope integer; v_updated integer;
BEGIN
  SELECT count(*) INTO v_scope FROM ticket_tiers
   WHERE event_id = p_event_id AND party_id IS NOT DISTINCT FROM p_party_id;
  IF v_scope <> cardinality(p_tier_ids)
     OR cardinality(p_tier_ids) <> (SELECT count(DISTINCT x) FROM unnest(p_tier_ids) x) THEN
    RAISE EXCEPTION 'reorder.stale_list' USING ERRCODE = 'P0001';
  END IF;
  UPDATE ticket_tiers t SET sort_order = o.ord
    FROM unnest(p_tier_ids) WITH ORDINALITY AS o(id, ord)
   WHERE t.id = o.id AND t.event_id = p_event_id
     AND t.party_id IS NOT DISTINCT FROM p_party_id;
  GET DIAGNOSTICS v_updated = ROW_COUNT;
  IF v_updated <> v_scope THEN RAISE EXCEPTION 'reorder.partial'; END IF;
  RETURN v_updated;
END $$;
REVOKE ALL ON FUNCTION public.reorder_ticket_tiers(uuid, uuid, uuid[]) FROM PUBLIC, anon;
GRANT EXECUTE ON FUNCTION public.reorder_ticket_tiers(uuid, uuid, uuid[]) TO authenticated;
```
`SECURITY INVOKER`: la RLS `ticket_tiers_update` (`staff.manage`,
`20260807010000_policies_to_capabilities.sql:379-383`) resta il confine. Una lista
**incompleta o vecchia** (un tier creato da un altro telefono nel frattempo) si
**rifiuta**, non si applica a meta'. Il pattern esiste gia' nel repo per le serate
(`event_parties.sort_order`, `EventForm.tsx:588`).

### Pattern 4: cover attraverso la quarantena (DBT-14)
E' la forma di `finalize-archive` (`route.ts:66-74`): **i byte non attraversano
la richiesta** perche' una Vercel Function rifiuta un corpo oltre 4,5 MB (citato
con fonte in `src/app/api/media/finalize/route.ts:28-50`) e il limite cover di oggi
e' 5 MB (`EventForm.tsx:217`). Il client deposita in quarantena (policy
`event_media_quarantine_insert_staff`, `staff.manage`,
`20260921120000_drop_status_and_referral.sql:265-271`), poi posta la chiave; il
server scarica col ruolo di servizio, spoglia/ridimensiona con `sharp`, scrive in
`event-images` a una chiave **generata dal server** e toglie la quarantena.

### Anti-Patterns to Avoid
- **Cancellare `event-media-quarantine` o tutto `may-upload.ts`/`finalize.ts`**:
  rompe l'archivio del visual (§DBT-13).
- **`DELETE FROM storage.buckets` in una migration**: il trigger di Storage la
  rifiuta anche a zero righe (§Pitfall 2).
- **Due liste con il pulsante Refund sulla stessa pagina Sales** (§DBT-17).
- **Salvare `utm_source` grezzo**: testo libero da un URL e' un vettore di dati
  personali e di spazzatura; si salva solo il vocabolario chiuso.
- **Contare «pagati dopo la mail» con una join su `email_deliveries`**: non serve
  e sbaglia sui pagati entro l'ora (§DBT-15).
- **Abbassare `channelLive` per segnalare la radio**: `channelLive` dice «il
  canale e' unito», non «c'e' rete»; la radio entra come termine proprio nella
  condizione di `listIsStale` (§DBT-05).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Trascinamento con pressione prolungata, tastiera, annunci, scorrimento automatico | Pointer Events a mano | `@dnd-kit/core` + `sortable` | Tolleranza al tremolio, cancellazione dello scorrimento solo a trascinamento attivo, `aria-live` di trascinamento inclusi |
| Riordino atomico | N `UPDATE` dal client in sequenza | RPC a istruzione unica (Pattern 2) | Un errore a meta' lascia un ordine misto che il pubblico vede |
| Rimozione metadati/rotazione | parser EXIF | `sharp` (`.rotate()` poi ricodifica) gia' in `strip-metadata.ts` | Lo stripper esiste ed e' provato (fase 35/52) |
| Decodifica HEVC | binario libheif su Vercel | strada A (Safari converte) o `heic-decode` (wasm) | `sharp` precompilato non ha il plugin HEVC (misurato) |
| Svuotare/cancellare un bucket | SQL su `storage.objects`/`storage.buckets` | API Storage (`empty` + `DELETE /bucket/{id}`) o rimozione per chiave | Il trigger di Storage rifiuta il `DELETE` diretto |
| Firma del «modulo aperto» | un id d'ordine in chiaro | `generateTicketToken(orderId)` / `verifyTicketToken` (`src/utils/qr.ts:3,11`) gia' restituito al client | Senza firma chiunque marca ordini altrui |

**Key insight:** in questa fase quasi tutto esiste gia' in una forma vicina —
`finalize-archive` per la cover, `event_parties.sort_order` per l'ordine, l'order
token per il beacon, `addGuest` per l'import. Il lavoro e' **non duplicare**.

## DBT-20 in dettaglio — «Add several»

**`addGuest` oggi** (`src/app/(admin)/admin/events/[id]/guest-list/actions.ts:97-224`):
- Firma: `addGuest(eventId: string, data: { full_name: string; email?: string; party_id?: string })`
  → `{ success: true } | { error: string }` (mai un throw verso il client: il
  `catch` a `:220-223` restituisce il messaggio).
- Guardia: `verifyOrganizerAccess` (`:80-91`) = `assertStaffManage()` +
  `assertMayManageEvent(getServiceClient(), eventId, ctx)`, **prima** di ogni
  scrittura; restituisce `userId` che diventa `added_by` (`:148`).
- Nome: un campo solo, spezzato al primo spazio in `first_name`/`last_name`
  (`:119-125`); email: `trim().toLowerCase()` e regex `^[^\s@]+@[^\s@]+\.[^\s@]+$` (`:129-135`).
- **Scritture per ospite**: con sola email assente → **1** (insert,
  `:140-152`). Con email → insert + 2 letture (evento, serata) + `processGuestEntry`
  (`src/lib/guest-list/process-entry.ts`): lettura profilo per email; se esiste,
  biglietto gratuito (lettura + insert) + update della riga; se non esiste,
  `auth.admin.createUser` + link per la password + **attesa fissa di 500 ms** +
  biglietto + update. Totale ~4-6 scritture e una mail per ospite con email.
- **La mail parte senza `await`**: `sendGuestInvitation(…).catch(console.error)`
  dentro `processGuestEntry`. Su Vercel una promessa non attesa dopo la risposta
  puo' non completarsi [ASSUMED]; e' il comportamento **di oggi** per il singolo
  ospite e l'import lo eredita identico. Il piano non lo cambia (sarebbe un
  cambio alla mail d'invito, fuori dal requisito), ma lo **dichiara** e l'esito
  dell'import lo rende osservabile: la riga resta `ticket_issued` anche se la
  mail non parte; la consegna si vede nel registro `email_deliveries` solo se
  `sendEmail` arriva a `recordSend`.
- Doppioni: indice unico `(event_id, LOWER(email)) WHERE email IS NOT NULL`
  (`20260310000000_guest_list.sql:61-63`) — **per evento, non per serata**. Il
  codice 23505 diventa «This email is already on the guest list» (`:155-162`).
  **Sui soli nomi non c'e' vincolo**: il doppione di nome si vede solo in anteprima.

**Raccomandazione: anteprima tutta nel client, salvataggio con N chiamate alla
`addGuest` di oggi, in sequenza.**
- Nessuna nuova server action: `GuestListClient` riceve gia' `entries` (nomi ed
  email della serata, `guest-list/page.tsx:157-161`) e `parties`. La lettura e il
  confronto sono una funzione pura in un modulo **senza** `"use server"` (un file
  `"use server"` pubblica ogni export come endpoint, `may-upload.ts:28-29`).
- Salvare chiamando `addGuest` **una riga alla volta** dal client, aspettando
  ciascuna: e' letteralmente «la stessa azione», con la stessa guardia ripetuta per
  ogni riga, e rende visibile l'avanzamento («7 / 15»). Quindici richieste brevi
  stanno larghe nel limite di 300 s di Vercel Hobby **per richiesta**
  [CITED: vercel.com/docs/functions/configuring-functions/duration]; un'azione
  batch lato server metterebbe 15 × (fino a ~2 s, con l'attesa di 500 ms) in una
  sola richiesta e cambierebbe la forma della guardia.
- `router.refresh()` **una volta** alla fine, non per riga.
- **Quota di posta**: Resend free = **100 mail al giorno condivise** con i
  biglietti (`52.2-RESEARCH.md:42,123`); limite di velocita' **10 richieste/s per
  team** [CITED: resend.com/docs/api-reference/rate-limit]. In sequenza la
  velocita' non e' un problema; la quota si'. L'anteprima dice **quante mail
  d'invito partiranno** prima di «Save».

**Regole di lettura di una riga** (proposta per il piano; nessuna e' una regola di dominio):
1. `trim`; riga vuota → ignorata (non conta come errore).
2. Tolto un prefisso di elenco: `^\s*(\d+[.)]|[-*•])\s+`.
3. Email = il **token** che corrisponde alla stessa regex di `addGuest`, anche fra
   `< >`; **piu' di un'email** sulla riga → «not understood».
4. Nome = il resto, tolti separatori finali (`,` `;` tab, spazi). Nome vuoto →
   «name missing» (l'azione lo rifiuterebbe comunque, `:120-122`).
5. Esempi che il test di laboratorio deve contenere: `Nome Cognome, nome@dominio`,
   `Nome Cognome nome@dominio`, `Nome Cognome`, `nome@dominio` (solo email →
   rifiutata, nome mancante), `Nome, a@x.it, b@y.it` (due email → rifiutata),
   un doppione di email gia' in lista, un doppione di nome.
6. Doppioni **dentro la lista incollata** si segnalano come quelli gia' in lista.

**Anteprima**: tabella per riga (nome letto, email letta o «—», esito: *will be
added* / *already on the list (email)* / *same name already on the list* / *not
understood: motivo*). Le righe non comprese **non** si salvano (D-52.1-25). Il
doppione **di nome** e' una decisione: raccomandazione, deselezionato per difetto
con una casella per includerlo. **Esito finale**: aggiunte N, saltate M con la
ragione per ciascuna — e i rifiuti del server (`{error}`) si mostrano **come
arrivano**, per riga, mai collassati (`meta-gates.md`, zero fallimenti silenziosi).
`DataTable` e' l'unica tabella ammessa (`verify:tables`); su telefono diventa card.

**PostHog**: `addGuest` cattura `guest_list_add` per riga (`:208-217`); la chiave
PostHog non esiste in produzione (`event-queries.ts`, docblock dell'imbuto), quindi
nulla cambia.

## Common Pitfalls

### Pitfall 1: togliere la quarantena insieme alla gallery
**What goes wrong:** l'upload dell'archivio del visual fallisce al deposito.
**Why:** `ArchiveUpload.tsx:96` e `finalize.ts:96` usano `event-media-quarantine`.
**How to avoid:** perimetro ristretto (§DBT-13); `npm run build` non lo vede (e' una
stringa); prova manuale di un upload dell'archivio sul lab dopo la rimozione.

### Pitfall 2: `DELETE FROM storage.buckets` in una migration
**What goes wrong:** la migration fallisce con *«42501: Direct deletion from
storage tables is not allowed»*, **anche a zero righe**: il trigger e' a livello di
istruzione e si supera solo con `SET LOCAL storage.allow_delete_query = 'true'` o
dall'API Storage [CITED: segnalazioni pubbliche che citano la migration
`0055-prevent-direct-deletes.sql` di supabase/storage — MEDIUM, da riprovare sul lab].
**How to avoid:** svuotare per chiave e cancellare il bucket dall'API Storage come
passo dell'atto; la migration toglie tabella, policy e chiave.

### Pitfall 3: la doppia lista con Refund su Sales
Spostando «Sold tickets» senza toccare `SalesDashboard` il difetto si sposta, non
sparisce. Gate di verifica: `grep -c "RefundActions"` sulle due pagine dopo la
modifica = 1 montaggio per biglietto.

### Pitfall 4: i link nelle mail ancora su `/tickets`
Le tre mail d'allarme mandano l'organizer su una pagina che non mostra piu' la
cosa per cui e' stato avvisato. Si cambiano nello stesso commit di DBT-17.

### Pitfall 5: il riordino che si applica a meta'
N update dal client: uno fallisce, il pubblico vede un ordine misto. RPC unica che
rifiuta una lista incompleta (Pattern 2).

### Pitfall 6: tier a pari prezzo scambiati dal backfill
Si rilegge l'ordine pubblico di oggi della `003` prima dell'atto.

### Pitfall 7: `sm:` e `xl:` nel componente nuovo
`TierReorderList`, il riquadro «Add several» e le sezioni spostate stanno sotto i
gate dei breakpoint e dei touch target: nessun `sm:`, maniglia a 44 px.

### Pitfall 8: dichiarare chiusa la porta con la misura di Chrome
Chrome emette `offline` subito; il ritardo che conta e' quello del telefono
(`52-ESITI.md:388`). La VERIFICATION cita la misura su Android emulato **e**
sull'iPhone, o dichiara quale manca.

### Pitfall 9: una persona con path morti
`verify:persona` A diventa rosso dopo la cancellazione, non prima (il build non
conosce i glob). Rilanciarlo dopo (memoria di progetto).

### Pitfall 10: `buyer_email` nullo dove il codice lo crede stringa
Il tipo dice `buyer_email: string`; dopo `DROP NOT NULL` ogni lettore va riletto,
e il tipo cambia.

### Pitfall 11: il beacon «opened» senza firma
Un id d'ordine in chiaro permetterebbe di marcare ordini altrui. Si usa l'order
token gia' firmato.

```ts
// parse-guest-lines.ts — modulo puro, nessun "use server"
const EMAIL = /^<?([^\s@<>]+@[^\s@<>]+\.[^\s@<>]+)>?$/;
export function parseGuestLine(raw: string) {
  const line = raw.trim().replace(/^\s*(\d+[.)]|[-*•])\s+/, "");
  if (!line) return { kind: "blank" } as const;
  const tokens = line.split(/[\s,;\t]+/).filter(Boolean);
  const emails = tokens.filter((t) => EMAIL.test(t));
  if (emails.length > 1) return { kind: "unparsed", reason: "two_emails" } as const;
  const email = emails[0]?.replace(EMAIL, "$1").toLowerCase() ?? null;
  const name = tokens.filter((t) => !EMAIL.test(t)).join(" ").trim();
  if (!name) return { kind: "unparsed", reason: "name_missing" } as const;
  return { kind: "guest", fullName: name, email } as const;
}
```

## Project Constraints (from CLAUDE.md)

- **Header di classificazione** in ogni risposta; Critical (accesso, denaro, porta,
  venue, dati personali) = analisi d'impatto + validazione **prima** di agire:
  DBT-13, DBT-14, DBT-15 (cancellazione PII), DBT-05 sono Critical.
- **Il middleware e' UX, la RLS e' sicurezza**: nessuna pagina nuova protetta solo
  dal middleware.
- **La porta non ha rete**: DBT-05 si pensa offline e si misura sul telefono.
- **Il denaro non si fida di chi lo annuncia**: nessun percorso nuovo che muove
  denaro; il beacon non tocca lo stato di pagamento.
- **Zero fallimenti silenziosi**: ogni rifiuto con categoria, ogni cancellazione
  contata e osservabile; nessun error tracking esiste.
- **Nessun test runner**: verifica = `npm run build` + `npm run verify*` +
  procedura manuale scritta; mai «i test passano».
- **Le migration sono la fonte dello schema**, non `schema.sql`; applicate dal
  Management API **sotto atto datato**, prima sul lab, mai `db push`.
- **Repo pubblico**: niente UUID, ref, persone, sedi in trattativa nei file
  versionati; `docs/` e `.firecrawl/` restano ignorati.
- **macOS/BSD**: `grep -E`, `sed -i ''`; i file con byte NUL si leggono con
  `/usr/bin/grep -a` o Read.
- **Persona**: chi tocca `.claude/**` aggiorna versione/changelog, lancia
  `verify:persona` **dopo** le cancellazioni e rimisura il budget.
- **Lessico**: `attendee` non e' «socio»; `re:sonate` con la e normale; un
  *format* non e' un *evento*.
- **Cron solo di mattina UTC**; chi aggiunge un cron aggiorna il conteggio in
  `meta-gates.md` (oggi otto) — la raccomandazione di DBT-15 non ne aggiunge.
