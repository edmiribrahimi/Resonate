<constraints>
## The mechanism, decided, with the rejected alternatives named

**Two thin `page.tsx` files sharing one server component, both under `src/app/(admin)/`.**

- **`rewrites()` is rejected**, despite being the smallest diff and despite satisfying
  D-39-02. It disappears from `scripts/verify-routes.mjs`'s on-disk census and from
  `_everyStaffRouteIsBound`, leaving an address bound in the map with **nothing anywhere
  asserting that the binding is honest** — a step backwards on the one axis Phase 34 spent
  a whole phase building. It also carries an unmeasured middleware-ordering question (Open
  Question 1), and `next.config.ts` is where this project has **already** decided routing
  tables do not go (D-34-14, `organizer-redirects.ts:29-36`). **This plan uses no
  `rewrites()`, so Open Question 1 does not arise and is not reopened.**
- **A route re-export** (`export { default } from …`) works identically at runtime but
  carries no segment config, reads as one page to anybody scanning the tree, and makes the
  diff of the door's own file look like a deletion.
- **A route group or a parallel route** cannot produce a second URL by construction.
  Recorded so it is not re-proposed.

## Placement, and why it is not cosmetic

`src/app/(admin)/door/page.tsx`, **not** `src/app/door/page.tsx`. The group contributes no
URL segment, so the address is `/door` either way — but the file placement decides three
mechanical things:

- `verify-routes.mjs` check 2 censuses `src/app/(admin)` **only**. A page outside that tree
  is invisible to it.
- `_everyStaffRouteIsBound` will **never** see `/door`: `StaffRoute` extracts `/admin`-
  prefixed members of the union. An unbound `/door` page produces **no build error**.
- `isUnderWorkTree` in the middleware compares the **first segment** to `"admin"`, so for
  `/door` it is false: an unmapped `/door` takes the `entry === null` fall-through and the
  middleware **admits everybody**, leaving the page guard as the only refusal — with no
  `?access=` cause. That is not a hole (the guard is real and is mounted on both pages) but
  it silently changes which of the two gates refuses.

## What this plan must not touch

- **`ScannerClient.tsx` (~3450 lines).** Opened only for its `MobileNav` props, and that is
  plan 39-03's task, not this one. **This plan does not open it at all.**
- **`src/app/sw.ts`.** Nothing in it names the door's address; the four `NetworkOnly` API
  rules match on API **pathnames** and survive the move byte-identically. The `/events/**`
  rule is T-37-27 ACCEPT, monotone, and the plausible path to breaking it is exactly this
  phase: discovering that no document is precached and reaching for a broader page-caching
  rule. **Do not.** The door's state is IndexedDB and does not live under `/events/`.
- **`public/manifest.json`.** `start_url` stays `/` (D-39-04) and `scope` is absent, which
  already defaults to the whole origin — `/door` was in scope before the page existed.
  Adding `"scope": "/"` "for clarity" is a cosmetic change to the one file whose semantics
  govern what an already-installed home-screen icon does. Not worth it on the phone that
  works the door.
- **`assignmentOpenable: true`** on the door's entry. Restored by plan 34-03 after being
  left behind; without it the middleware refuses the person rostered to work the door, at
  two in the morning, in front of a queue.
- **Any `layout.tsx`.** There is no `(admin)` layout and there must not be one. The only
  layout under that tree is `admin/(work)/layout.tsx`, nested deliberately, and its docblock
  says it *pre-positions Phase 39*. A `door/layout.tsx` "for consistency" would put a second
  bottom nav or a tab bar on the door.
- **`src/utils/qr.ts:49`'s `Math.random()`.** A real, known, pre-existing defect. **Do not
  fix it in passing.**
- **Renaming `middleware.ts` → `proxy.ts`.** Next 16 deprecated the convention and the file
  says so; it is *"work for its own small plan, after Phase 39"*. Folding it in would produce
  two changes that look like each other in a diff, on the most safety-critical file in the
  repo.

## Two things left as they are, on purpose

- **The two stale description strings in the database.**
  `private.capabilities.description` for `door.operate` names *"the middleware rule for
  /admin/scanner"* and `admin.access` names *"/admin/* other than the scanner"*
  (`supabase/migrations/20260807000000_capability_model.sql:370,378`). Both were **already**
  stale before this phase — the middleware rules they describe were replaced in Phase 34 —
  and `scripts/verify-capabilities.mjs` does not compare descriptions. **This plan writes no
  migration.** They are left as provenance prose, and this sentence is the record of that
  choice rather than an oversight.
- **Blocker D7** — the middleware writes `?redirect=` and the login page reads `?next=`, so
  the destination after sign-in is lost on every protected address. **Pre-existing,
  out of scope, not fixed here.** Adding `/door` to `protectedPrefixes` does not repair it;
  it stops this phase from adding a *second* wrong turn on top of it.

## OQ3, deferred with its return route

in `39-DOOR-PASS.md` §0.5, observe §8, and take the question to `/gsd:discuss-phase` with
the reading attached. A cache lifetime for the door is a product decision about how stale a
door may be.
