<objective>
Close **GAP-CR-01** and the aggregate half of **WR-01**.

**GAP-CR-01.** `scripts/verify-all.mjs`'s reconciliation — plan 41-14's entire purpose,
and the thing this file's own docblock calls *"the whole point of the file"* — is still an
identity. The loop pushes exactly one `plan` entry per `OFFLINE` row on every path, and
the three filters partition on `state === "runnable"` versus its complement, crossed with
`optional`. Any state value therefore lands deterministically in one of the two `absent*`
buckets, `measuredOrExplained` is always a superset of `declared`, and `unaccounted` can
never be non-empty.

The docblock names the concrete triggering situation — *"somebody adds a fourth `state` to
the `plan` partition below — a `skipped`, a `deferred`, a `stale` — and the three filters
that follow it do not catch it"*. This round's verifier injected exactly that
(`state: "deferred"` for `verify:tokens`) and the entry fell into `absentRequired`, printed
*"MISSING, and this is a failure, not an omission"*, and exited 1 through a path that
predates the plan. The new refusal never ran. Plan 41-14's own mutation proof used a
different mechanism — a name-based exclusion in the runnable filter — which trips the new
code but is not the scenario the header claims to guard, and does not correspond to any
real change to the partition.

**WR-01, aggregate half.** When the suite finishes with refusals and no recorded failure,
the closing block prints *"Nothing failed. But a refusal is not a pass: those gates
measured NOTHING"*. Both halves of that sentence are false for a run in which a gate was
failing when it refused — which is precisely the shape plan 41-20 has just repaired inside
`verify-conversion`, and which `verify-touch-targets`'s seven exit-2 conditions can still
produce. And this plan's own fix creates a second instance here: making the reconciliation
reachable puts a refusal *after* the results are known, where it can outrank a MISSING gate.

Purpose: the safety net inside the aggregate does what its docblock says, and the aggregate
never reports a failure as a refusal.

Output: `scripts/verify-all.mjs` with a partition that is non-exhaustive by construction, a
reconciliation domain wide enough to catch a dropped entry whatever its registration, and a
verdict that keeps a failure visible.

**This plan closes no requirement.** All seven of the phase's requirement IDs are listed
because the aggregate runs every gate that touches them — not because any of them closes
here. DS-07, DS-08, DS-09, RESP-01, RESP-02, RESP-03 and RESP-04 all stay PARTIAL;
RESP-01 closes only after 41.2, and only by a written human pass. H41-1…H41-6 remain
unobserved and this plan does not touch them.

<interfaces>
Read from the shipped aggregate before editing.

- `OFFLINE` — `[npmScriptName, optional, note][]`. `NEEDS_SERVER` — `[name, reason][]`.
- `declared` — every `verify:*` key in `package.json`.
- `knownNames` — the union of the two declared lists.
- The two pre-run refusals: `undeclaredHere` (declared here but unknown to the runner) and
  `missingRequired` (known and required but not declared). Together they guarantee
  `declared ⊆ knownNames`, and that anything in `knownNames \ declared` is optional.
- The plan loop: pushes `state: "unregistered"` for a name absent from `package.json`,
  `state: "absent"` for a script path not on disk, `state: "runnable"` otherwise.
- `absentRequired` / `absentOptional` / `runnable` — the three filters, currently keyed on
  `state !== "runnable"` and its complement.
- `results`, `failed`, `refused`, `passed`, `accounted`.
- `measuredOrExplained` and `unaccounted` — the reconciliation.
- `refuse(message)` → exit 2. The verdict block: exit 1 when `failed` or `absentRequired`
  is non-empty, exit 2 when only refusals, exit 0 otherwise.

**Baseline first.** Before any change, run `node scripts/verify-all.mjs`, record the exit
code and the count block verbatim, and use *that* exit code as the negative-control target
throughout. It is not assumed to be 0: this repository has no test runner, several gates
read the tree as it stands, and a machine without credentials is a legitimate state. A
negative control that targets a number nobody measured is the same error as a mutation
proof that mutated the wrong thing.

    pre-run refusals and write the reasoning into the docblock: they guarantee
    `declared ⊆ knownNames` and that every extra known name is optional, and an optional
    unregistered name reaches `absentOptional`, so nothing on today's tree becomes

    whole suite to exit 2, which is the failure mode D-41-19 calls the worse one.

    paragraph above it false again. Say what a reader should do instead when a genuine
    fourth state is introduced: add it to `ABSENT_STATES` with its reason in the same
