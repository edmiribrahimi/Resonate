<objective>
**One helper, twenty-odd call sites, three blinded checks, two gates.** This is the
item on round 5's list that improves things regardless of any other decision,
because it repairs the foundation the others stand on.

`liveLines()` blanks a **whole line** when its trimmed text *starts with* a
comment opener, instead of blanking only the comment span. A blanked line trims
to the empty string and is skipped downstream. So the closed one-line form —
`{/* prose */}` followed by live code on the same line, which is idiomatic React
and not adversarial syntax — hides that code from **every** consumer of the
helper:

- `verify-conversion.mjs` check A (raw palette utilities), proven blind on the
  first surface this phase converted, a gated payment surface;
- `verify-conversion.mjs` check E's two frozen digests
  (`NAV_PROPERTY_SITE_DIGESTS`, `SHELL_CODE_OUTSIDE_WINDOW_DIGEST`) and
  `unfrozenPropertySites` / `propertyReadsElsewhere`, all built from
  `shellLines`. One such line reintroduces CR-01 on all four focus routes with
  the digest **byte-identical** to the clean tree, the permitted-site count at
  zero, a tick on E, exit 0, and a clean type check;
- `verify-dialogs.mjs` check B (undeclared dialog shells), where a nineteenth
  hand-rolled overlay costs one comment and leaves the `REMAINING` figure — the
  number the header tells the reader to trust instead of the tick — unmoved.

Round 4 asserted the shell **by digest of its live code**. The digest is honest;
what it is computed *from* is not. That is the sixth escape, and it is one token
wide.

**Both files' headers state a bound that the shipped code does not have**:
`verify-conversion.mjs`'s comment-hygiene paragraph and `verify-dialogs.mjs`'s
say the over-blank can happen *only* when a line begins with a JSX comment opener

    Four parts, and the fourth is why the first three are believable.

    **1. Blank the comment SPAN, not the line.** Today the stripper pushes the
    empty string whenever the trimmed text starts with one of its four openers.
    Change it so that a comment which CLOSES on its own line consumes only itself:
    from the start of the trimmed text, drop everything up to and including that
    comment's first closer, and keep what follows as live text. Repeat while the
    remaining text still begins with an opener that closes on the line, so two
    leading comments followed by code do not leave the second one's prose sitting
    in the live text — that would trade a blind spot for the false red DEF-41-02
    exists to prevent.

    Which closer belongs to which opener is the whole of the logic: the JSX opener
    is closed by `JSX_COMMENT_CLOSE`; the block opener and the block-continuation
    star are closed by the block closer. Assemble the block closer at run time the
    way the two JSX constants already are — no complete comment or utility literal
    is spelled in either file (DEF-41-01). The double-slash opener keeps whole-line
    blanking, because everything after it genuinely IS the comment.

    An opener with **no** closer on the line keeps today's behaviour exactly: the
    whole line is blanked, and for the JSX opener the multi-line state is entered
    and left as it is now. The star-continuation and block-opener lines of an
    ordinary docblock therefore keep blanking, which they must — these two files
    scan a tree whose components document their own class strings.

    **Preserve character positions.** Replace the consumed span with the same
    number of spaces rather than shortening the line. `findUtilityHits` computes
    `rest` from `m.index` and the match length, so a shifted column changes what
    the tolerated-scrim test reads. The line's length must be what it was.

    **Keep the counter honest.** `jsxCommentLinesBlanked` is printed on every run
    in both gates and is the only published measure of how much this heuristic
    removes. A line whose leading span was blanked still counts. If you change what
    the number means, change the label beside it in the same edit.

    Nothing else in either file changes: not `isOverlayLine`, not the caches'
    behaviour, not `REMAINING`, not `fenceMatch`, not `neverOpenedReason`, not
    `RUNG_FAMILY`, not `FULL_BLEED_VIEWER`'s skip path. Group B's four findings
    live in this same file family and are open; a commit that touches a file
    carrying six findings and mentions one will be read as closing all six.

    **2. Do not re-freeze anything.** `SHELL_CODE_OUTSIDE_WINDOW_DIGEST` and both
    entries of `NAV_PROPERTY_SITE_DIGESTS` must come out of this task
    byte-unchanged. The shell carries no line of the affected shape, so a correct
    fix moves neither. If a digest moves, stop: read which line changed and why,
    and report it. Copying the found digest in would be this gate certifying a
    change nobody looked at — the exact act WR-02 shows the refusal's own
    instruction inviting.

    self-contained on purpose, and the cost of that is that one fix has to be
    applied twice. Make the two helpers' text identical — same function name, same
    body, same comment — so a future reader diffing them gets nothing back. Prove
    it, do not assert it: extract each function's text and diff them.

    **4. Both headers stop claiming a bound the code does not have.** In each file,
    the comment-hygiene paragraph says the over-blank can happen only when a line
    begins with a JSX comment opener **inside a string**. Withdraw that sentence
    the way this file family already withdraws a false claim — quote it, say it was
    made, say what disproved it (a closed one-line comment followed by live code,
    with no string anywhere in it, measured with a control on three separate
    checks), and state the bound the shipped code now has, in both directions:

      - what is still blanked more than it should be — a line that BEGINS with
        those characters as part of a multi-line string literal loses its leading
        span, and a comment closed with a space between the star-slash and the
        brace is not recognised as closed and blanks onward to its real closer;
      - what is no longer blanked and used to be — every character after a leading
        comment's closer, which is where all of CR-01 and CR-02 lived.

    Write no measured line number into either paragraph. This edit adds lines above
    the numbers two headers already carry, and round 3 recorded exactly that going
    stale twice. State the invariant, not the address.

    Every sentence you add to either header must be a claim you have run.

    **5. Make the claim re-provable on every run, in `verify-dialogs.mjs`.** Its

    measures `isOverlayLine` on a raw probe string, so it says nothing about the
    stripper the matcher is fed from, which is where the defect was. Route the probe
    measurement through the shipped per-line stripper (the six existing probes begin
    with no comment opener, so their verdicts must not move — that is an acceptance
    criterion, not an expectation), and add four probes:

      - an overlay line behind a leading CLOSED JSX comment → must MATCH. This is
        the direction the docblock claims and the direction CR-02 disproved;
      - an overlay line behind a leading CLOSED block comment → must MATCH;
