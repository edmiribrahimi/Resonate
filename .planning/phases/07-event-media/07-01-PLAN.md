Create the Phase 7 migration SQL file that modifies the existing `event_media` table and creates the storage bucket. Follow the exact patterns from 07-RESEARCH.md migration example:

1. **ALTER event_media table** to add:
   - `uploaded_by uuid REFERENCES auth.users ON DELETE CASCADE` (who uploaded)
   - `status text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'approved', 'rejected'))` (moderation)
   - `file_size bigint` (for validation display)

2. **Add indexes** on `event_id`, `uploaded_by`, and `status` columns.

3. **Drop existing overly-broad RLS policies** (`event_media_select_all`, `event_media_all_admin` -- check actual policy names by reading existing schema/migrations first).

4. **Create new RLS policies:**
   - `event_media_select_approved`: SELECT for authenticated where `status = 'approved'`
   - `event_media_select_own`: SELECT for authenticated where `auth.uid() = uploaded_by`
   - `event_media_select_admin`: SELECT for admin/organizer (using `is_admin_or_organizer()` or equivalent helper -- check existing migrations for the actual function name)
   - `event_media_insert_member`: INSERT for authenticated where `auth.uid() = uploaded_by` AND user status is approved
   - `event_media_delete_own`: DELETE for authenticated where `auth.uid() = uploaded_by`
   - `event_media_update_admin`: UPDATE for admin/organizer (moderation)

5. **Create `event-media` storage bucket:**
   - `INSERT INTO storage.buckets (id, name, public, file_size_limit) VALUES ('event-media', 'event-media', true, 104857600)` (100MB)

6. **Create storage RLS policies** for the `event-media` bucket:
   - Approved members can upload (INSERT with `bucket_id = 'event-media'`)
   - Anyone can view (SELECT on public bucket)
   - Members can delete own uploads (DELETE where path contains their user ID)
   - Organizer/master can delete any event media

  <action>
Add media-related server actions to the existing `actions.ts` file in the event detail route. Read the existing file first to understand what actions already exist (likely ticket-related from Phase 6).

Add these server actions (all marked `"use server"`):

1. **`validateMediaUpload(eventId: string)`** -- Pre-upload validation:
   - Get authenticated user via `supabase.auth.getUser()`
   - Check user profile status is `'approved'`
   - Check ticket ownership: query `tickets` table for matching `(event_id, user_id)` -- this is the "checked in" gate per CONTEXT.md (ticket ownership = attendance)
   - Return `{ userId: string, canUpload: true }` on success
   - Throw descriptive errors on failure ("Not authenticated", "Not approved", "No ticket for this event")

2. **`registerMedia(eventId: string, storagePath: string, type: 'photo' | 'video', fileSize: number)`** -- Post-upload metadata insertion:
   - Get authenticated user
   - Construct public URL: `${process.env.NEXT_PUBLIC_SUPABASE_URL}/storage/v1/object/public/event-media/${storagePath}`
   - Insert into `event_media` table: `{ event_id, uploaded_by: user.id, url: publicUrl, type, file_size: fileSize, status: 'pending' }`
   - Return the inserted record or throw on error

3. **`updateMediaStatus(mediaId: string, status: 'approved' | 'rejected')`** -- Moderation action:
   - Get authenticated user
   - Verify user is organizer or master (query profile role)
   - Update `event_media` set `status` where `id = mediaId`
   - Use `revalidatePath` to refresh the event page after status change

4. **`deleteMedia(mediaId: string)`** -- Member self-delete or admin delete:
   - Get authenticated user
   - Fetch the media record to get `uploaded_by` and `url`/storage path
   - Verify user is either the uploader OR is organizer/master
   - Delete from Supabase Storage (extract path from URL, call `supabase.storage.from('event-media').remove([path])`)
   - Delete the `event_media` record
   - Use `revalidatePath` to refresh

IMPORTANT: Use the server-side Supabase client (`createClient` from `@/lib/supabase/server`). Check if there's also a service-role client pattern used in the project for operations that need to bypass RLS (look at existing actions.ts for patterns). The insert should work with the member's own auth since the RLS policy allows it, but moderation updates may need the user's session since the policy checks `is_admin_or_organizer()`.
