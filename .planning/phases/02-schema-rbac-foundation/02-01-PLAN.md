  1. **Add columns**: ALTER TABLE public.profiles ADD COLUMN role text NOT NULL DEFAULT 'member' CHECK (role IN ('master', 'organizer', 'member')), ADD COLUMN status text NOT NULL DEFAULT 'approved' CHECK (status IN ('pending', 'approved', 'rejected')). Use CHECK constraints (NOT native PostgreSQL ENUMs) per research recommendation -- easier to extend in production.

  2. **Migrate data**: UPDATE public.profiles SET role = 'organizer' WHERE is_admin = true. All existing users keep status='approved' (they registered before gating existed).

  3. **Drop old column**: ALTER TABLE public.profiles DROP COLUMN is_admin.

  4. **Update trigger**: CREATE OR REPLACE FUNCTION public.handle_new_user() that inserts role='member', status='approved' into the profiles row. Keep existing membership_code generation logic (RSN- prefix + 8 random chars from 'ABCDEFGHJKLMNPQRSTUVWXYZ23456789'). Must be SECURITY DEFINER.

  5. **Create helper functions**: Four security definer stable functions:

     - `get_user_status()` RETURNS text -- SELECT status FROM profiles WHERE id = auth.uid()
     - `is_master()` RETURNS boolean -- get_user_role() = 'master'
     - `is_admin_or_organizer()` RETURNS boolean -- role IN ('master', 'organizer')

  6. **Drop ALL old RLS policies** by exact name (from current schema.sql):

  <name>Task 2: TypeScript types update and master email detection in auth callback</name>
  <files>src/types/database.ts, src/app/api/auth/callback/route.ts, .env.local.example</files>
  <action>
  **Update src/types/database.ts:**
  - Add type aliases: `export type UserRole = "master" | "organizer" | "member"` and `export type UserStatus = "pending" | "approved" | "rejected"`
  - Add `role: UserRole` and `status: UserStatus` to the Profile interface
  - Remove any is_admin field if present (it is not currently in the interface, but verify)
  - Keep all other interfaces (Event, RSVP, Attendance, EventMedia, NewsletterSubscriber) unchanged

  **Update src/app/api/auth/callback/route.ts:**
  After the successful `exchangeCodeForSession` call and before the redirect, add master email detection:
  1. Get the current user via `supabase.auth.getUser()`
  2. If `user.email === process.env.MASTER_EMAIL`, update the user's profile: `supabase.from("profiles").update({ role: "master", status: "approved" }).eq("id", user.id)`
  3. This runs on every auth callback for the master email -- idempotent (setting master to master is a no-op)
  4. If MASTER_EMAIL env var is not set, skip the check silently (no error)
  5. Keep the existing redirect logic intact

  **Update .env.local.example:**
  Add under the `# App` section:
  ```
  # Master Admin
  MASTER_EMAIL=your-master-admin-email@example.com
  ```

  **Important:** The auth callback uses the server Supabase client which runs with the user's session. The RLS policy `profiles_update_own` would normally prevent role changes. However, the master email check happens during initial signup (first callback), and at that point the user already owns the row AND the `profiles_update_master` policy won't apply since they're not master yet. To solve this: the auth callback should use the Supabase service role client (not the session-based client) for the master promotion update. Import or create a service role client using `SUPABASE_SERVICE_ROLE_KEY` for this specific operation. Use `createClient` from `@supabase/supabase-js` directly (NOT the SSR helper) with the service role key for the update query only. Keep the regular SSR client for `exchangeCodeForSession`.
