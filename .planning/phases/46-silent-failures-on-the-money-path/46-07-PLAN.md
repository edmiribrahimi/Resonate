<objective>
Make the one failure in this phase that already has an observable channel actually use it.

Purpose: the cleanup step deletes expired drink tokens and then reports a number. It never
destructures the delete's error, so a refused delete reports as a full success; and its
coalesce is backwards — `.delete()` without an exact count returns null on the **success**
path too, so the fallback reports the *intended* length essentially always. **The rows that
remain are counted as deleted, and the run returns 200.**

D-46-06: the response tells the truth, *and the run terminates as failed*, so a failed
execution shows red in the platform's cron dashboard. This is the only observable effect in
the whole phase that costs nothing to build. The accepted cost is on the record: if it
fails often the red becomes wallpaper.

This route will be the **first converted cron in this repository**, so it is written for the
next one to copy.

Output: a truthful body, a category union with a total status `Record`, a non-2xx exit on a
failed run, and one `console.error` that stops leaking a whole error object.
</objective>

  <action>
    Two separate wrongs at the cleanup step, and they are fixed as two.

    **First, ask for the count.** `.delete()` without an exact count returns null on the
    success path too, which is why the fallback fires essentially always. Request the exact
    count on the delete so the number reported is a measurement.

    **Second, destructure the error**, and stop coalescing. `deletedCount` no longer falls
    back to the intended length. Report both figures — how many rows were asked for and how
    many were actually deleted — so *asked 40, deleted 40* and *asked 40, deleted 0* are
    different lines in a dashboard rather than the same one.

    Widen the response body to carry: refunded, refund errors, the number of rows the
    cleanup asked to delete, the number actually deleted, and the outcome category. Keep
    `refunded` and `refundErrors` under the names they already have — something may read
    them.

    **Then the exit status.** The run terminates as **failed** — a non-2xx response — when
    the cleanup delete was refused, or when fewer rows were deleted than were asked for.
    Whether `refundErrors > 0` alone also makes the run red is the owner's answer recorded
    in `46-COPY.md`; implement it as written. A run that did everything it set out to do
    still returns 200 with the truthful body.

    Log the delete failure through `logMoneyPathFailure` with a scope naming the cleanup
    step, code and message only.

    And **inherit the safe-log rule while in the file**: the refund loop's `catch` passes the
    whole caught value to `console.error`. Narrow it to code and message through
    `logMoneyPathFailure`, keeping the `orderId` in the scope string, which is the thing
    that made that line useful.

    **Forbidden.** Do not touch the window arithmetic — neither the grace window nor the
    24-hour cleanup window, both of which go through `menuCloseInstant` in Europe/Rome. Do
    not touch the refund call, the transaction-code fallback, the `refunded_amount`
    accumulation, or the token status transition to refunded: a payment reaching completion
    corrects forward, and nothing here may make an amount that was taken look like it was
    not. Do not move `refundedCount += tokens.length` out of the loop — per-item progress is
    a gate of its own (`ticketing-payments.md`, *cron non atomico*), and the deletion step
    being reported as one number must not undo the principle. Do not change the
    authorization check. Do not touch any other cron.
  </action>
