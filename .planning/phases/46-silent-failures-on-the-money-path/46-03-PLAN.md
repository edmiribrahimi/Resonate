<objective>
Stop three reads on the purchase path from discarding their errors, without changing what
any of them decides.

Purpose: `F-46-01` measured two reads inside `purchaseTicket` whose failure makes the
capacity check vanish or count every tier as zero sold — the server agreeing with a client
that already showed a full night as open. `DI-TODO-A` is the third: a failed count on a
discount code's usage limit reads as *this code has never been used*, so the limit opens.

**And the direction does not change.** D-46-05 settled it after reading the schema: the
real guard is `reserve_ticket`
(`supabase/migrations/20260310100000_discount_codes.sql:90`), which locks the tier row
`FOR UPDATE`, counts, raises `Tier sold out`, and validates `max_uses` in the same
transaction. In plpgsql a failed read **raises** — it cannot coalesce to zero — so that
guard fails closed. Closing the application-side pre-check on a transient read error would
refuse a buyer the database would have accepted. D-46-08: **observability, not a new
refusal.**

Output: three reads that say which failure they had, a docblock that records why the
direction is deliberate, and one honest statement of what this plan does **not** close.
</objective>
