<objective>
Answer one question — *what does a guest see when the browser cannot hold their receipt* —
in the one file where it is asked three times.

Purpose: for a person with no account, the entry under `resonate_drink_tokens_<event>` **is
the receipt**; nothing else in this product knows the purchase happened on this device.
Today the write swallows every cause, the read returns the empty list — which is also the
legitimate answer for *this browser bought nothing* — and a token fetch that cannot answer
returns the same status as one merely on its way. Three sites, one question, and splitting
them yields half an answer.

Two facts shape the mechanism and are not negotiable. **This file may not use a toast**: it
renders `Dialog`, and `scripts/verify-dialogs.mjs` refuses any file that renders `Dialog`
and imports `useToast`. And **the render site is where the defect completes**: a failed
custody read arrives at the early return as a zero-length list and the component draws
nothing at all, so whatever union is added is inert unless that return learns the third
state.

Output: a tagged custody contract, a token-fetch state union with a *could-not-answer*
member and a terminal state at the poll's bound, and a surface that says which of them
happened.
</objective>
