# Plan 29-01: Party Selection & Scoped Attendee List

## Goal
Staff opens check-in → sees a list of upcoming parties → picks one → attendee list, search, filters, and progress bar are scoped to that party only.

## Requirements
- CHKIN-01: Party selector screen
- CHKIN-02: Scoped attendee list with search and filters
- CHKIN-03: Progress bar for selected party

## Context

### Current State
- `ScannerClient.tsx` (426 lines) fetches ALL future/today parties via GET `/api/tickets/attendance`
- No party selection — all parties shown as separate cards
- Search and filters are global across all parties
- Progress bar is per-party already, but all parties visible simultaneously

### Key Files
- `src/app/(admin)/admin/scanner/ScannerClient.tsx` — main client component (rewrite)
- `src/app/(admin)/admin/scanner/page.tsx` — server component wrapper
- `src/app/api/tickets/attendance/route.ts` — GET attendee list, POST guest check-in

## Tasks

### Task 1: Refactor Attendance API to Accept Party Filter

**File:** `src/app/api/tickets/attendance/route.ts`

**Changes:**
1. Add optional `partyId` query parameter to GET handler
2. When `partyId` is provided:
   - Fetch tickets only for that party (`party_id = partyId`)
   - Fetch guest list entries only for that party
   - Return single party's attendees (not grouped by event)
3. Keep backward compatibility: if no `partyId`, return all (existing behavior)
4. Add `party_id` to the ticket check-in response so the client knows which party the ticket belongs to

**File:** `src/app/api/tickets/checkin/route.ts`

**Changes:**
1. After successful check-in, include `party_id` and `event_id` in the response JSON
2. This enables cross-event validation on the client side (SCAN-05, handled in Plan 29-02)

### Task 2: Build Party Selector & Scoped Scanner Page

**File:** `src/app/(admin)/admin/scanner/ScannerClient.tsx` — major rewrite

**Party Selector Screen:**
1. On mount, fetch available parties via GET `/api/tickets/attendance` (no partyId → returns all grouped)
2. Show a list of upcoming parties as selectable cards:
   - Party title + event title (if different)
   - Date and time
   - Venue (if available)
   - Check-in progress (X/Y checked in)
3. Tapping a party card sets `selectedPartyId` state and transitions to the scanner view

**Scanner View (after party selection):**
1. Header shows selected party name + date + "Change" button to go back to selector
2. Fetch attendees scoped to `selectedPartyId` via GET `/api/tickets/attendance?partyId=X`
3. Search input filters attendees by name (existing debounce 300ms logic)
4. Filter tabs: All / Not Arrived / Checked In (with counts for selected party only)
5. Progress bar: `{checkedIn} / {total} ({pct}%)` for selected party only
6. Attendee list with existing check-in buttons for guest list entries

**State Management:**
```typescript
const [selectedPartyId, setSelectedPartyId] = useState<string | null>(null);
const [parties, setParties] = useState<Party[]>([]); // all available parties
const [attendance, setAttendance] = useState<Attendee[]>([]); // scoped to selected party
```

**Navigation:**
- Party selector → Scanner view (forward)
- "Change" button → back to party selector (resets scanner state)
