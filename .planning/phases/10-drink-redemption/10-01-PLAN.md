  <action>
Create a new migration file with a `redeem_drink_token` SECURITY DEFINER PostgreSQL function.

The function:
- Takes `p_token_id uuid` as parameter
- Returns `boolean` (true if redeemed, false if already redeemed)
- Uses `SELECT ... FOR UPDATE` to lock the row and prevent race conditions
- Raises exception if token not found
- Returns false (idempotent) if token already has `status = 'redeemed'`
- Updates `status` to `'redeemed'` and `redeemed_at` to `now()` if token has `status = 'purchased'`
- Uses `LANGUAGE plpgsql SECURITY DEFINER` (same pattern as `fulfill_drink_order` and `reserve_ticket`)

Follow the exact pattern from the research:
```sql
CREATE OR REPLACE FUNCTION public.redeem_drink_token(p_token_id uuid)
RETURNS boolean
LANGUAGE plpgsql
SECURITY DEFINER
AS $$
DECLARE
  v_token record;
BEGIN
  SELECT * INTO v_token
  FROM public.drink_tokens
  WHERE id = p_token_id
  FOR UPDATE;

  IF NOT FOUND THEN
    RAISE EXCEPTION 'Token not found: %', p_token_id;
  END IF;

  IF v_token.status = 'redeemed' THEN
    RETURN false;
  END IF;

  UPDATE public.drink_tokens
  SET status = 'redeemed',
      redeemed_at = now()
  WHERE id = p_token_id;

  RETURN true;
END;
$$;
```

No new tables, no RLS policy changes needed. The function bypasses RLS via SECURITY DEFINER.

const { data: newTokens } = await supabase
  .from("drink_tokens")
  .select("id")
  .eq("order_id", drinkOrder.id);

if (newTokens) {
