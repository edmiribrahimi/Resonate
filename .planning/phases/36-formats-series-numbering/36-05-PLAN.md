  <action>
    Derive the project ref from `NEXT_PUBLIC_SUPABASE_URL` in `.env.local`. Read
    `SUPABASE_ACCESS_TOKEN` from the same file.

    Send `POST https://api.supabase.com/v1/projects/{ref}/database/migrations`
    with `Authorization: Bearer $SUPABASE_ACCESS_TOKEN`, `Content-Type:
    application/json`, and a body carrying the file's contents as `query` and the
    migration's name as `name`.

    **The migrations endpoint, not `/database/query`.** The second one applies the
    DDL and writes nothing into the project's history, which is how eighteen
    entries of drift accumulated (`36-RESEARCH.md` § 6, last part). Using it here
    would add a nineteenth.

    Do not paraphrase the file when sending it: the body carries the file, byte for
    byte, so that what is recorded as the version is what is on disk.

    If the request fails, read the error before retrying. The transaction is
    atomic — a failure means nothing was applied, and in particular the guard
    raising with a row count is a **successful** guard, not a broken migration:
    it means a row exists that the backfill did not name, and the answer is to
    find that row, not to loosen the guard.

    Record in the SUMMARY: the version the endpoint assigned, and the fact that
    the drift in the history predates this phase and is the owner's call to repair
    (`PUT` on the same endpoint upserts without applying).
  </action>
  <verify>
