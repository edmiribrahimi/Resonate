<objective>
Put the filter in the address and the format on the card — without giving a
visitor one bit of information about a night nobody has announced.

Purpose: FMT-06 lives on this page, and the page has already recorded, with the
measurement, that it **cannot prove its own gate**: `page.tsx:42-57` says forging a
master identity returns the same two slugs as an anonymous request because RLS
refuses unpublished rows to `anon` regardless of what the page decides. The format
filter inherits that exactly — a filter that does not show a draft has not been
shown to be incapable of showing one. So this plan's job is not to demonstrate
safety; it is to build the surface so that the one thing a draft could leak through
— a count, in any form — has nowhere to appear.

Output: a page that reads two parameters, a chip row that never varies with the
data, and a card that degrades to the narrower name.
</objective>

  <action>
    Extend `transformEvent` with a format axis. The formats travel the road venues
    and lineup already travel: collected from the nights, sorted by `sort_order`,
    deduplicated. Two nights of the same format produce one marker. **One card per
    event, never one card per night** — a double bill is one piece with two names,
    which is how it is communicated.

    Decide which name each marker carries, and this is the part that is a
    venue-secrecy clause rather than a display choice. If **every** night on the
    card has `venue_secret = false`, the marker shows the series public name. If
    **any** night on the card has `venue_secret = true`, every marker on that card
    shows the **format name alone**. A series public name is a stored string
    published on every surface its nights touch, so a series named after a venue
    publishes that venue every time; degrading when any night is secret means no
    series name can become an accidental reveal path — and it produces the brand's
    own string for a double bill without anyone special-casing it.

    Declare the predicate explicitly in a comment, because two candidates exist and
    they are not the same: the **stored flag** `venue_secret`, and the time- and
    entitlement-dependent verdict `isVenueVisible` returns. **This phase uses the
    stored flag, on both public surfaces**, because it is the narrower of the two —
    a night whose venue has since been revealed still shows the format name — and
    `venue-secrecy.md`'s default-closed gate says the narrower wins.

    If the reveal state cannot be determined at all — a missing row, a failed join —
    the marker shows the format name. The fallback is always the narrower string.
    And if the **format** row itself is absent from the join, render no marker for
    that night: an absent format row means an unlisted format, which means a format
    nobody has announced, and rendering nothing is the correct answer rather than a
    defect. Write that sentence, so a later reader does not "fix" it into a
    placeholder.

    Apply the format filter **on the array already rendered**, never as a second
    query. A separate *"does this format have anything?"* query is exactly the shape
    that would see a draft and turn it into a visible difference — FMT-06 failing in
    the one place nobody would look for it.

    Pass to the children: the catalogue list, the active format slug, the active
    tab, and the two filtered arrays. Do not pass a count of anything.
  </action>

    own order. Exactly one chip is current at a time.

    happens to have no visible nights. That is a count with one bit of resolution
    and it leaks the same fact: if a chip went dark when a format had nothing
    published, lighting up would be the announcement. No property of a chip may
    depend on the results array — that is the warning sign to check for.

    Anatomy from the spec: `rounded-full border min-h-11 px-4 inline-flex
    items-center gap-2`; off state transparent ground with `text-muted`; on state
    `bg-card` with `text-foreground`, the border overridden inline with a
    `color-mix` of the format's colour so the neutral `border-card-border` class
    stays underneath and the chip never loses its border; an 8px `rounded-[2px]`
    swatch at `opacity .4` off and full on; the label at 12px / 600 with
    **no `uppercase`**. Do not copy the active state of the growth toggle: it is
    `bg-accent text-white`, and accent is barred from the format channel.

    Each href preserves the other axis. Choosing a format must not silently return a

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the address bar → the page | `?format=` and `?tab=` are untrusted input |
| unpublished rows → any rendered byte | RLS refuses them, and nothing above may reintroduce them through an aggregate |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-36-11-01 | Information Disclosure | a count on a public surface | mitigate | No aggregate is fetched, no count is rendered in any label or attribute, the empty state is computed from the rendered array and never from a second query (D-36-14) |
| T-36-11-02 | Information Disclosure | a chip whose appearance depends on the data | mitigate | Chips are built from the catalogue only; no chip property may read the results array — a count with one bit of resolution is still a count (D-36-13, Pitfall 5) |
| T-36-11-03 | Information Disclosure | enumeration through a redirect | mitigate | No redirect on any value. Unknown, retired and unlisted slugs all behave identically to no filter, so the response is no oracle |
| T-36-11-04 | Information Disclosure | a series name publishing a venue | mitigate | The card degrades to the format name whenever any night on it carries `venue_secret`; the predicate is the stored flag, the narrower of the two candidates, and it is declared in the code |
| T-36-11-05 | Information Disclosure | two construction paths for the chip row | mitigate | One query, one path, for anonymous and staff alike (D-36-16) |
| T-36-11-06 | Input Validation (V5) | `?format=` as untrusted input | mitigate | Validation is membership of the active catalogue — an allow-list drawn from the data, the narrowest form available. No library, no error, no redirect |
| T-36-11-07 | Denial of Service | a failed catalogue read rendering as an empty row | mitigate | The read sits outside the catch that empties the lists, next to `getAccessContext()`, for the reason already written there |
| T-36-11-SC | Tampering | npm/pip/cargo installs | accept | No package is installed |
</threat_model>
