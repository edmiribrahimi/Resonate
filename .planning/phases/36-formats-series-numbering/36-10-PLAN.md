<objective>
Put the format, the series and the number on the surface where a night is created
and edited — and fix the bug that would otherwise make the whole of FMT-03
invisible.

Purpose: `updateEvent` does not destructure `{ error }` from either of its
per-night writes (`src/app/(admin)/admin/events/actions.ts:375-420`), while
`createEvent` does (`:296-302`). The named constraint this phase adds would fire,
the loop would continue, `revalidateEventPaths()` would run and the action would
return success. The constraint would work and the path would swallow it. That is
not a courtesy fix; it is what makes D-36-08 produce an observable effect at all,
and `meta-gates.md` is explicit that in a repository with no error tracking a
failure that counts must have an observable effect.

Output: three fields, one refusal a person can read, and an action that stops
lying about success.
</objective>

    Extend the per-party validation loop with three causes, each its own
    `throw new Error`, following the loop's existing form: a missing or non-uuid
    format is `Pick a format. A night cannot be saved without one.`; a missing or
    non-uuid series is `Pick a series before choosing a number.`; a number that is
    not a positive integer is refused with its own sentence. Coerce the number in
    place, the way the capacity check already does.

    Then the deliverable: **destructure the result of every per-night write in
    `updateEvent`.** For each night, capture `{ error }` from the `update` or the
    `insert` and act on it. Do not collapse the loop into a single failure message
    — the operator needs to know which night was refused.

    Branch on `error.code`. `23505` from
    `event_parties_format_series_number_unique` becomes the duplicate-number
    refusal, carrying the number and the series so the surface can render
    `Number {n} is already assigned in {Series}. Pick another.` `23503` from
    `event_parties_series_format_fk` becomes its own category — it means the chosen
    series does not belong to the chosen format, which the form should have
    prevented, so its arrival is evidence that the form's filtering has stopped
    working and it must say that rather than hide inside a generic write failure.
    Everything else keeps its own message naming the cause.

    Carry the category as a **returned value**, not as a thrown message: Next
    redacts the message of an error thrown out of a Server Action in a production
    build, so a client branching on message text works in `next dev` and stops
    working where it counts. Model the union on `AssignmentRefusal`
    (`assignments/actions.ts:106-140`), and document each member — including, for
    the pair that exists in both places, why the application guard and the database
    constraint do not substitute for each other: one keeps the row from existing,
    the other tells the operator what happened instead of handing them a constraint
    name.

    Log `error.code` and `error.message` and nothing else. Never the whole error
    object and never `error.details`: on a `CHECK` violation PostgREST returns the
    entire rejected row, and `.planning/todos/pending/postgrest-details-leaks-the-row.md`
    records that roughly twenty sites in this repository already pass the whole
    object. Do not make it twenty-one on a path that will now fail routinely — a
    number already in use is an ordinary operator mistake, not a rarity.

    Do not add an application-level pre-check that queries for an existing number
    before writing. Two people with two tabs open beat every application check; the
    database is the only place two concurrent requests meet, which is exactly why
    D-36-08 puts the rule there.

  <action>
    Add `format_id`, `series_id` and `number` to all three parallel shapes —
    `SubEventFormState` and its default, `PartyInitialData`, and
    `subEventFromInitial` — in the same commit. Missing one of the three is how a
    field silently never reaches the action; `number` is held as a string in form
    state with the `?.toString() ?? ""` convention the file already uses.

    Add the three controls to the per-night block, in this order, using the input
    styling already established.

    **Format** — a native `<select>`, required. Options are the **active** catalogue
    formats. One exception, and it prevents data loss: if the night being edited
    already carries a retired format, include that entry, label it `{Name}
    (retired)` and preselect it. Omitting it would mean that merely opening the edit
    form and saving would silently reassign an archived night, and archived nights
    are not rewritten. The select's job is to be able to display the truth; refusing
    a *change to* a retired format is the action's job.

    **Series** — a native `<select>`, filtered to the series of the chosen format.
    Changing the format clears the series and the number. This field never accepts
    typed text: a venue spelled two slightly different ways would silently start a
    second numbering from 1, which is the whole reason D-36-05 makes a series a
    catalogue row rather than a string on the night.

    **Number** — `<input type="number" inputmode="numeric" min="1">` with
    `tabular-nums`, **arriving pre-filled with one more than the chosen series'
    `highest_assigned`**, and fully editable. The suggestion is a read of a
    watermark, not a count of nights, and the difference is the point: `updateEvent`
    really deletes the nights removed from the form, so a suggestion derived from
    `max(number)` would re-propose a number that is already on a poster.

    Beneath the number field, in `text-xs text-muted`, the helper text from the
    copywriting contract, verbatim: *"Suggested from the last number in this series.
    What you save is stored as written and never recalculated — moving or deleting a
    night does not renumber the others."* This is the only place the stored-not-
    recalculated contract is stated to the person typing, so it is not decoration
    and must not be dropped as such. Helper text under a field is new in this file —
    `EventForm` uses placeholders today — so introduce it deliberately.

    The suggestion **is** a count-like affordance and it is allowed here: this is a
    surface behind a capability, and the no-count rule governs public surfaces. Say
    so in a comment, because over-applying the rule would remove the one thing that
    makes the field usable.

    Render the duplicate-number refusal attached to the number field with
    `aria-invalid="true"` and `aria-describedby`, preserving the typed value — the
    person came here with a number from a poster and clearing it would lose the only
    copy on screen. A network failure, a permission refusal and a duplicate number
    produce three different sentences on this form.

    Do not apply `uppercase` or `text-transform` to any element rendering a format
    or series name.
  </action>
