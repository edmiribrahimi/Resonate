### The 44px floor, and the line that declares it

§8.6 offers two mechanisms. This file takes the **first** — the label that
carries the minimum — for `Checkbox.tsx`'s reason and not a fresh one: *a label
carrying the minimum is also the control's programmatic name, so one element
does both jobs and there is no state in which the target exists and the name
does not.*

The declaring line, `src/components/ui/Switch.tsx:141-142`:

```
const HIT_AREA =
  "‹INLINE-FLEX› ‹MIN-WH› ‹POINTER-CURSOR› ‹CENTRE-CROSS-AXIS› ‹GAP-8›";
```

**`‹MIN-WH›` is the whole of the criterion**: an unprefixed 44px minimum on both
axes, on the element a finger lands on. The other four tokens are the layout the
label needs to hold a 24px track beside a name, and they are substituted for the
same reason as everything else in this file, not because they carry a decision.

and it is applied at `:173`, on the `<label htmlFor={id}>` that wraps the
control. The drawn track keeps its 24×44 (`TRACK`, `:117`, carrying
`‹TRACK-SIZE›`), which is byte-for-byte the size the four incumbents drew.

### Three things in it that are decisions rather than substitutions

1. **The knob is a sibling, not a pseudo-element.** An `<input>` is a replaced
   element and WebKit renders no pseudo-element on one — and this product's
   primary device is a phone, on which **every iOS browser is WebKit**. A knob
   drawn that way would simply be absent on the device that matters most. Being
   a *following* sibling is also what lets the track's own checked state reach
   it, which a descendant could not do.
2. **The knob changes colour with the ground under it.** Over the well it is the
   primary ink at **17.02 : 1**; over the accent fill it is the page ground at
   **6.85 : 1** — the same arithmetic that gives the primary button its ink. One
   colour cannot clear 1.4.11's 3 : 1 on both grounds. **The incumbent knob was
   white, which is 2.91 : 1 on the accent.** And colour is not the only channel:
   the knob's *position* carries the state.
3. **The boundary is the control token, and the fill is its own boundary when
   on.** The well against a card is 1.04 : 1, so the well does not say where the
   control is; the boundary does, at **6.78 : 1** over a card. When the switch is
   on, the boundary takes the fill's value — `Button.tsx`'s rule for the primary
   rung, not a second accent use.

## Deviations from plan

### 1. `[interpretation]` Tasks 1 and 2 landed in ONE commit, not two

**Issue:** the executor protocol commits per task; **task 2's action says the

**Taken:** one commit for both, `3d62ee5`. The plan's sentence is more specific

Task 3 kept its own commit.

### 2. `[Rule 3 — blocking]` The edit field is focused by id, not by a ref

**Found during:** task 2, converting the edit row's name field.

**Issue:** the file focused that field through a `useRef` threaded down as a
prop. `Input` is a plain function component whose props type does not admit a
forwarding ref, so the ref could not follow the field onto the primitive.

**The alternative, and why it lost:** leaving that one field as a raw `<input>`
carrying a hand-copied boundary string. That is finding A1 kept alive in a file
converted to close it, and duplication of exactly the string D-41-10 centralised.

**Fix:** the effect focuses `document.getElementById(editNameFieldId(editingId))`.
The id is required by the primitive anyway, it is produced by one helper read by
both the effect and the control so a second spelling cannot drift, and the `ref`
and its prop are gone. **The effect is unchanged**: opening an edit puts the caret
in the name field — row 9 of the manual procedure is what observes it.

### 3. `[Rule 2 — accessibility, beyond the substitution table]` Three controls that had no target and no focus indicator now have both

The plan's ladder names the toggle. Three neighbours on the same surface were
below the floor and silent on focus, and leaving them would have declared a
surface converted while a keyboard user still could not see where they were:

- the **back link** on the page — no minimum, no focus expression;
- the **name-and-price control** that opens the editor — no minimum, no focus
  expression, and its only affordance was a hover colour change, which **does not
  exist on a phone**. It now carries a dotted underline at rest;
- the **drag handle** — no minimum, no focus expression.

All three are inside this plan's declared files. Each is a 44px target carrying
the imported ring.

### 4. `[loss, recorded rather than hidden]` The remove control lost its destructive hue on hover

The incumbent tinted the trash control with a raw palette red on hover. Raw
palette does not survive, and the honest replacement — the destructive semantic —
could not be appended to the ghost variant's own hover ink: **both would be the
same property at the same variant, so which one wins is decided by Tailwind's
output order and not by the class attribute**, which is not something a contract
should rest on.

**Taken:** the ghost `IconButton`, unmodified. The control's meaning is carried by
its glyph and by its accessible name, both unchanged. **A variant that expresses
"destructive, but quiet" does not exist in the ladder, and inventing one here
would be a contract decision made inside a conversion commit** — the shape
`DEF-41-04` records as how a contract gets decided where nobody reviews it.
Reported as a deferred item below rather than taken.
