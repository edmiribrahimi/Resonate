## Decisions Made

1. **Neither dialog declares an initial-focus marker.** The analog puts one on its Cancel. Omitting it makes the primitive fall back to the close control, which is first in the DOM and is exactly the element the user agent focused before this conversion — so the focus target did not move at all. Between two equally harmless controls, not moving focus is the smaller claim.
2. **`lg` for both panels**, because §8.3's closed list names both by name.
3. **The suggestion list keeps its incumbent rung.** §10's z-index ladder assigns the dropdown rung to these two files by name, and the value did not move. No new rung.
4. **The list's highlight is a step on the surface ladder, never an accent tint.** §5.1's reserved list names *a state signal* among the things the accent is never for, and a hover highlight is one.
5. **The *Linked* marker keeps its word and loses its colour.** D-41.1-25 refuses an outcome tone; D-41.1-29 measured the only candidate pair at 1.23 : 1 against WCAG's 3 : 1, so the palette could not have carried it anyway. Recorded so no later wave re-opens it believing a colour pair was available and merely unused.
6. **No file-control primitive was published.** §8.6 specifies three text-entry controls and no file control. D-41-04 forbids publishing a primitive in a plan that is not converting its first consumer, and `src/components/ui/Skeleton.tsx` — correct, complete, zero importers — is this tree's own record of what the mistake costs. The label, the failure region and their association are written beside the field with the same tokens the field primitives use.
7. **The shared components' public props were frozen.** Making the autocomplete take the field primitive directly would have required its `id` prop to become mandatory, and its only mount site is `EventForm.tsx` — the file a sibling plan holds in another worktree. D-41.1-15's partition is about files; honouring it means honouring it at the API too, or the two plans leave a joint obligation belonging to neither.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 2 — Missing critical] The refusal collapsed every cause into one message**

- **Found during:** Task 1, both modals.
- **Issue:** Each `catch` printed the thrown error's message, or one fallback sentence. **Next redacts the message of an error thrown out of a Server Action in a production build**, and both creation actions throw — so a missing name, a duplicate name, a refused write, a capability refusal and a dead network all arrived as the same generic paragraph. This is the shape `meta-gates.md` records as this repository's own precedent not to repeat, and there is **no error tracking in this project**, so what the dialog prints is the only place a failure exists for a human being.
- **Fix:** Three causes are distinguishable from inside these files and each got its own sentence, branched on the **stage** a failure happened in rather than on message text — the same discipline the converted analog applies to its two throwing paths. The photo arm runs in the browser, so its underlying message is readable and is carried through; the unreachable arm is identified by shape; the third states plainly that the server's own reason does not reach the screen in a production build, and names what to check.
- **Why this is the deviation and not the plan:** the plan's action text asked for exactly this shape, and its acceptance criterion asked for *no user-visible string to change*. Both cannot hold. The reading applied: the **form's** copy — every label, placeholder, title and button word — is byte-identical and verified above; the **refusal region**, which the same task was instructed to rewrite, changed. Stated here rather than filed as compliance.
- **Files:** both modals. **Commit:** `3922136`.

**2. [Rule 1 — Bug] Escape left the dialog's state behind**

- **Found during:** Task 1, the venue modal.
- **Issue:** The close control and *Cancel* reset the form; the platform's own close event did **not**. So closing with Escape left the last refusal and a half-typed bio on screen at the next open. (The artist modal masked the same defect with a reset-on-open effect; the venue modal had none.)
- **Fix:** every close route lands on the same reset, which is what the primitive's `onClose` contract is for — its own docblock says a caller that resets on close puts it there and nowhere else, so no route can skip it.
- **Files:** `CreateVenueModal.tsx` (and the same routing applied to `CreateArtistModal.tsx`). **Commit:** `3922136`.

**3. [Rule 2 — Missing critical] The file field's label named nothing**

- **Found during:** Task 1, both modals.
- **Issue:** The photo field's label was a `<label>` with no `htmlFor` and the control had no `id`, so the visible word was not the control's programmatic name; the image failure sentence was not associated with the control either. The read-only name field had the same defect.
- **Fix:** real `htmlFor`/`id` pairs on both, and the image failure region gets an id, `role="alert"`, and `aria-describedby`/`aria-invalid` while it is on screen — the association the field primitive already makes for the fields that have one.
- **Files:** both modals. **Commit:** `3922136`.

### Named behaviour changes

**4. Pressing a lineup tag removes it**

Before, only the removal glyph did; a press on the tag's text did nothing. The plan instructs that each removable tag be a `Chip` and that the row stop being a row of small targets, and a chip's press **is** its action. Two things keep the change from costing anything: the announced name is unchanged (`Remove <name>`, carried in a visually hidden span placed before the name), and the glyph stays as the affordance. The alternative considered and rejected — keep the glyph as the only remover and grow it to 44px — puts a large destructive target immediately beside the text inside a pill that is not itself pressable, which is a *worse* mis-press shape rather than a safer one. One incidental effect: removing a tag now also focuses the text field, because the removal no longer stops the press from reaching the box. It opens nothing, since the field is empty at that moment.

**5. The venue profile prompt wraps**

Letting the row wrap is the one layout addition in that file. At 390px a sentence and two 44px pills do not fit on one line, and the incumbent's fixed row put the actions off the edge at exactly the width RESP-03 exists for.

## Open questions owed to the owner

**1. The creation actions throw where they should return — and the files are outside the authorised list.**

Telling *a duplicate name* from *a missing name* from *a refused write* is not reachable from a modal, because the server's message is redacted in production. Closing it means `createVenue` and `createArtist` returning typed refusal values instead of throwing — precisely the argument `src/app/(admin)/admin/venues/actions.ts` already makes, in its own prose, for the sibling update action, which was converted to that shape in phase 37.

`src/app/(admin)/admin/venues/actions.ts` and `src/app/(admin)/admin/artists/actions.ts` are **not** in this plan's `files_modified` and **not** on D-41.1-19's authorised list. Conversion rule 8 is a standing rule: the list grows **by owner decision or not at all**, however small the file and however well measured. So this is recorded as owed rather than done — and it is a **behaviour** change to a write path, which is a second reason a conversion commit is the wrong place for it.

*Measured, so the decision has numbers under it:* two files; the change is to the return type of one export in each and to the one caller of each, which is the dialog this plan just converted; no query, column, capability check or RLS policy is touched; the capability guard `assertCatalogueManage()` continues to throw and stays a separate arm.

**2. The autocomplete has no combobox contract, and building one is behaviour.**

Measured across both files: zero `role="combobox"`, zero `aria-expanded`, zero `aria-activedescendant`, zero `aria-controls`, and **no arrow-key handling** in `AutocompleteInput` at all. §12 asks for the contract; the tree does not have it, and did not before this plan.

Adding the roles **without** the key handling announces a widget that cannot be operated — worse than announcing nothing. Adding the key handling is a behaviour change. Both were refused inside a conversion commit, deliberately, and the state is written into both files so the next reader does not conclude the conversion dropped something.

**3. A measurement correction: the tag input is not a wrapper.**

The plan describes `AutocompleteTagInput.tsx` as *"the tag wrapper around"* `AutocompleteInput.tsx`, and its key-link says the base is converted *"in the same plan as its wrapper"*. **Re-derived from the tree: `AutocompleteTagInput.tsx` does not import `AutocompleteInput.tsx`.** They are two independent implementations of one control shape — same debounce, same two-character floor, same outside-click close, written twice. Converting both together was still the right call, and for a stronger reason than the plan gave: they are not a base and a wrapper that must agree, they are **two copies that can silently disagree**. Whether they should become one component is a question this plan did not answer and did not touch.
