## 1. Task 1 — the column array, pasted

`src/components/admin/TransactionList.tsx`, verbatim **except for one elision**:
the amount cell's class string is described rather than written, because

```tsx

    header: "Date",

    cell: (row) => formatDate(row.timestamp),
  },
  {

    header: "Description",
    card: "title",
    cell: (row) => row.description,
  },
  {
    key: "buyer",
    header: "Buyer",
    card: "subtitle",
    cell: (row) => row.buyer ?? "--",
  },
  {
    key: "amount",
    header: "Amount",
    card: "mark",
    figure: true,
    align: "end",
    cell: (row) => (

  },

    key: "status",
    header: "Status",
    card: "mark",
    cell: (row) => (
      <StatusBadge status={row.status} refundedAmount={row.refundedAmount} />
    ),
  },

```

**Every column names a slot, and the amount's is `mark`** — D-41.1-13, on the
surface that rule was written for.

| Column | Slot | Why |
|---|---|---|
| Date | `meta` | a labelled detail; it qualifies the row, it is not the row |
| Description | `title` | what was bought is what a row *is* |
| Buyer | `subtitle` | what identifies the row after its name |
| **Amount** | **`mark`** | **the figure that decides money is met first, never buried** |
| Status | `mark` | already a badge element; it fits the slot as rendered |

**Two things the array order does not decide.** The array is the *table's*
column order and is the one the table already had — Date first. The card's
layout comes from the slots, so the card leads with the description regardless.
They are independent and both were chosen rather than inherited.

**The money mark carries its own emphasis, and that is a measured necessity.**
RESEARCH §2.2's gap **G-c**: the primitive gives the `mark` slot *position* but
no weight — it renders the cell inside a bare element stacked at the trailing
edge. A bare figure placed there would sit at the card's ordinary size beside a
semibold title. So the cell renders its own emphasis and the data face, which is
G-c's own recommended resolution and needs no edit to the primitive's contract.
Nothing re-declares the numeric-variant shorthand (`40-REVIEW.md` WR-10).

**The buyer became a column of its own.** It used to be a second line *inside*
the description cell. A card cannot lay that out — the title slot truncates to
one line — so it becomes a column with the subtitle slot. It reads the same map
it always read; where no buyer was matched it now says so with the file's own
placeholder string instead of rendering nothing, because on a finance list an
unmatched sale is a fact an operator should be able to see. **The table branch
therefore has a `Buyer` header it did not have. No new data is read.**

## 2. The status map — **and why the plan's seven-to-four instruction was refused**

> **This is the one place this plan does not do what its own PLAN.md says, and
> the refusal is the point rather than an oversight.**

**What the plan asked for.** Task 1: *"Seven statuses map onto a semantic set of
four, so two pairs must share a token… write the seven-to-four map out in the
file with a sentence per collapse."*

**What was shipped instead.** Seven statuses, **one** neutral mark, and no tone
per outcome at all.

### 2.1 The reason, and it is a dated one

**D-41.1-25 says the status badge does NOT gain outcome tones**, that the badge
contract holds, and that the lost colour is an accepted loss. Its reason is
written in `Chip.tsx`'s own docblock: the emphasis fill means *look here first*
and **deliberately does not grade an outcome**, because assigning a colour per
outcome settles in a stylesheet a judgement nobody has written down — *a refusal
is a communication, not a hue.*

**The plan predates the decision.** `41.1-CONTEXT.md` dates D-41.1-25…28 as
*"Added 2026-08-13, after wave 3"*, and its own decision-coverage note records
that the manual check was run *"against the 24 plans"* — all twenty-four already
existed. This plan's paragraph comes from `41.1-RESEARCH.md` §2.3 reason 5,
which was written before the question was put and answered. **A superseded
instruction obeyed is worse than one refused with its reason attached**, which
is this project's own rule and the reason the refusal is written here at length
rather than resolved quietly.

Cross-checked against `meta-gates.md`'s conflict rule — *when two gates produce
contradictory requirements the more restrictive wins, and the conflict is
documented in the commit.* Adding four outcome tones is the less restrictive of
the two.

### 2.2 The map, as it now stands

| API status | What the mark shows | Tone |
|---|---|---|
| `SUCCESSFUL` | `SUCCESSFUL` | neutral |
| `FAILED` | `FAILED` | neutral |
| `PENDING` | `PENDING` | neutral |
| `CANCELLED` | `CANCELLED` | neutral |
| `REFUNDED` | `REFUNDED` | neutral |
| `CHARGE_BACK` | `CHARGE BACK` | neutral |

**Seven words stay seven and stay distinct. What is gone is the hue that
repeated them**, and the accessibility contract is met the way it was always met
— colour was never allowed to be the only channel, so removing it removes a
duplicate rather than the signal. Zero raw palette families remain:

### 2.3 The question this surface owes the owner — reported, not decided

**D-41.1-25 leaves exactly one criterion open:** *does the status grade a
person, or report a machine?* It names the newsletter broadcast result as the
one place the question may legitimately be re-asked, and says the answer is
**deliberately not to be decided inside a conversion commit.**

**A payment status reports a machine too.** `SUCCESSFUL`, `FAILED`, `PENDING`,
`CANCELLED`, `REFUNDED`, `CHARGE_BACK` are facts about a card transaction and
carry no judgement about anybody. By D-41.1-25's own stated criterion this
surface is a **second candidate**, alongside the newsletter's.

**It is reported and not answered.** Deciding it here would be exactly the move
the decision forbids, and it would be taken at a call site by an executor rather
than by the person who owns what the interface says. Two facts belong beside the
question when it is put:

- an operator scanning a page of payments for the refused ones is doing
  something a hue helps with in a way a word does not, and this is the surface
  where that scan happens;
- the row that judges it is a **human observation**, listed at §6 and unticked.
  A gate cannot see it, and neither can this file.

## 4. Task 2 — the second rendering, and the mechanism written into the file

`41.1-PATTERNS.md` §4.5: **no converted file in the tree has two whole
renderings of the same data.** There is no analog, which is why the mechanism is
prose in the file rather than a shape to be inferred.

### 4.1 What it is

The search rendering cannot become a table without changing what search does,
which would be behaviour. So it keeps its own *layout* and loses its own *field
list*. Both sources map into one row shape, and the search rendering fetches the
table's cell renderers **by key**:

```tsx
  /**
   * The mechanism that keeps the two whole renderings from drifting.
   *
   * The search rendering reads the **same** column declarations by key and calls
   * the same cell renderers. Change how an amount is written and both renderings
   * change together; there is no second place to forget, which is the property
   * `DataTable` gives the two branches of a table and which nothing gave these
   * two lists.
   *
   * A key that names no column returns nothing rather than throwing. On a
   * finance surface a missing field is visible to the operator reading it and a
   * thrown render is a blank page — between the two failure directions only one
   * is noticed, and it is not the blank page.
   */
  const cellFor = (key: string, row: TransactionRow) =>
    columns.find((column) => column.key === key)?.cell(row) ?? null;
```

And the call region it feeds — class strings elided for the reason at §1:

```tsx
                        <p className={/* the detail size and ink, with a small lead */}>
                          {result.eventTitle} &middot; {cellFor("description", row)}
                        </p>
                        <p className={/* the detail size and ink */}>{cellFor("date", row)}</p>
                      </div>
                      <div className={/* a trailing column that does not shrink */}>
                        {cellFor("amount", row)}
                        {cellFor("status", row)}
                      </div>
```

**What this removed, concretely:** the search branch used to write its own
amount — currency, a space, two decimal places — and its own date call, beside
the table's. Two copies of one format. They are now one, and the amount picked up
the money mark's emphasis in the process, which is the drift-proofing arriving as
a visible improvement rather than as an argument.

### 4.2 The four declared divergences

Each is written beside the markup that carries it, numbered.

| # | What the search rendering shows that the table does not | Why |
|---|---|---|
| 1 | **the lead is the buyer**, not the description | the table answers *what happened on this account*; this list answers *what did this person buy*. Same renderer, different position |
| 2 | **the kind of purchase** — a ticket or a bar order | one list holds two kinds of object; the transaction list holds one. It names a thing rather than grading an outcome, so it takes the plain mark and is told apart by its word |
| 3 | **the member's address** | the search matched on a person; the address is what confirms it matched the right one. The table has no person to confirm |
| 4 | **the night's title**, prefixed to the description | one member's purchases span several nights. Every row of the table already belongs to whatever the filters selected |
