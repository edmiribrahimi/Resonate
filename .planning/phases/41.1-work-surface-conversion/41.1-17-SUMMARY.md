# Phase 41.1 Plan 17: The Refunds Knot Summary

The refund confirmation is now the platform's modal element — **Escape, a focus
trap and an inert background, none of which existed before** — with Cancel first
in the DOM, first in the tab order, and the element the modal focuses. The
per-row control that two work surfaces mount is on the primitives, converted once
so those two surfaces stay two plans.

**No status transition, no refund amount, no idempotency key and no webhook path
moved.** Asserted by `command grep` over the diff with the five needles named,
quoted line by line below — not assumed, and not read through a wrapper that can
return a silent zero.

**Task 3 is not done. It is written, and it is owed.** Eight rows, every one
`pending`, none self-approved, and the three that a person must see **before this
ships** are named separately from the five that can travel.

### Cross-domain impact, before the fact

- **Ticketing and payments.** The confirmation's copy, its focus target and its
  button rungs all sit on the path to a refund. Changing any of the three changes
  how easy the refund is to trigger. The copy did not change; the focus target
  moved from *nothing* to the refusal; the confirming control kept the heaviest
  treatment available and gained none.
- **Access and gating.** The control is drawn for a role that may not be allowed
  to press it. The refusal path stays reachable, and it is now **announced**
  rather than merely printed — one of the two Rule 2 fixes below.
- **Check-in.** A refund issued after a night has begun is accounting and never a
  door event. Nothing here touches that boundary: neither file imports anything
  under the offline or scanner trees, and neither writes an attendance record.
- **Venue secrecy.** Not this surface. Asserted by grep at §5.3 rather than
  assumed.
- **Production calendar.** No series progressivo is read, derived, sorted or
  rendered by either file. Asserted at §5.4.

### Why the conversion tightens the guard rather than loosening it

The house rule for a destructive confirmation (§11 of the design contract, built
at `RetireFormatDialog.tsx`) puts the refusal first in the DOM, first in the tab
order, and gives it the marker the primitive focuses **imperatively after the
modal opens**. Before this plan, neither file had a `<dialog>` at all: both were
hand-rolled overlays with no Escape, no focus trap, no background inertness and
**nothing focused on open**. Every one of those four arrives with the platform's
modal element. There is no direction in which this conversion makes a refund
easier to trigger, and the eight-row procedure at §7 is how a person confirms
that rather than taking this paragraph's word for it.

## 3. The focus target — before and after, read out of the file

> The plan asked for this explicitly because *"it already focuses cancel"* is a
> claim to verify, not to assume: this phase already measured a React autofocus
> prop being **inert** on a native modal element.

### `RefundDialog.tsx`

| | Focus target |
|---|---|
| **Before** | **Nothing.** The file rendered a plain positioned element, not a `<dialog>`, and called nothing that focuses. Opening it left focus on the row control that opened it — *behind* the scrim — with no trap, so Tab walked straight into the page behind |
| **After** | **Cancel.** It is first in the DOM inside the actions region, carries the initial-focus marker, and the primitive focuses that element imperatively immediately after the modal opens |

**The file never carried the React autofocus prop**, so nothing was removed. Said
out loud because the absence is otherwise indistinguishable from a removal, and
because the analog's own record — that the prop does **not** survive the modal's
opening step, read out of the installed React rather than inferred — is the reason
the marker is the mechanism and the prop is not.

`command grep -c 'autoFocus'` on the converted file returns **0**. `command grep -c
'data-initial-focus'` returns **1**, and it is on Cancel:

```tsx
          <Button
            variant="secondary"
            …                       // the equal-share width utility, not spelled here
            data-initial-focus
            onClick={close}
            disabled={isPending}
          >
            Cancel
          </Button>

          <Button
            variant="destructive"
            …                       // same
            onClick={handleConfirm}
            disabled={isPending || !isValidAmount}
          >
            {isPending ? "Processing..." : "Confirm Refund"}
          </Button>
```

> The width utility is elided rather than quoted: `.planning/` is inside
> Tailwind's source-detection path (DEF-41-01, still open), and a class string in
> prose is indistinguishable from a use.

Cancel is the secondary rung; the confirming control is the destructive rung and
carries no marker and no autofocus. That is §11 verbatim.

### `RefundActions.tsx`

Same reading, same result: **before, nothing was focused**; after, Cancel is,
through the same marker on the same rung, with the confirming control on the
destructive rung.

**What no gate can confirm, and what §7 rows 1 and 2 exist for:** that the ring
is actually on Cancel when the panel appears, and that pressing Enter at that
moment refunds nothing.

## 8. Findings reported and deliberately not fixed

### 8.1 Approving a refund moves money on a single press

`RefundActions.tsx`'s approve/reject branch has an asymmetry the wrong way round:
**rejecting** a member's refund request takes two presses and a note field;
**approving** it — which is the one that moves money out — takes one, with no
confirmation at all.

Adding a confirmation is a **behaviour change on a money path**. This plan's own
rule forbids it, and stop condition 2 says a conversion that cannot proceed without
one halts rather than deciding at execution time. It could proceed without one, so
it did — and the finding is reported instead. **A question owed to the owner:**
should the approve control carry the same two-step confirmation the reject control
already has?

### 8.2 Every refusal on both surfaces collapses into one sentence

Both files report a failure as *whatever the action threw*, with a single bare
fallback word when the throw carried no message. So a permission refusal, a
network fault, a provider error and an already-refunded transaction are
**indistinguishable on screen**. That is the shape this project has already
recorded as indebuggable, and there is no error tracking behind it to compensate.

The right repair is the analog's `describe(reason)` — one sentence per cause, and
a default arm that identifies an unforeseen cause on screen rather than borrowing
a sentence written for something else. **Writing it means rewriting a money
confirmation's copy**, which §11 forbids to a conversion. Reported, carried
forward, and it is what row 8 of §7 is for.

### 8.3 The toggle is a selection, not a radio group

`RefundDialog.tsx`'s full/partial pair is a mutually exclusive choice. It is now
the shared selectable pill, which says which of the two is current to a screen
reader as well as to an eye — **before, the selection was announced by a fill and
by nothing else.** A grouped radio would be the more exact semantic still. That is
a behaviour decision on a money surface and is reported, not taken here.

### 8.4 The shrink allow-list does not apply, and the plan's analog does not hold

The plan pointed at the member table's row-action component and at the table
primitive's density argument as the analog for `RefundActions.tsx`.

**Measured: none of the four mount points is inside the table primitive.** Two are
in hand-written table markup on the sales dashboard, one is in that surface's card
branch, and one is in a plain list on the tickets surface. §6.3's shrink is
permitted on exactly one class of element — a row action inside the table
primitive's desktop branch — so it is not available here.

**Consequence, stated rather than discovered:** every control in that file stays
at the unconditional floor, and the rows that carried 28px controls now carry
44px ones. That is the contract being applied, and it will be visible at §7's
widths.
