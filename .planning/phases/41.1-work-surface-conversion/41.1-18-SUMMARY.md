## Impact analysis — written before the diff

**Classification: Critical.** Not for its size. This form writes a night: its
format, its series, its number, its venue link and its venue secrecy flag.

**Domain:** `venue-secrecy` primary (the file is named in that module's
enumerated exit points); `production-calendar` for the format, series and
number; `access-gating` and `supabase-data` for what the form submits;
`nextjs-architecture` for the file itself.

**What was opened:** `src/components/events/EventForm.tsx`, and nothing else.
`git status --porcelain` shows exactly one modified file across both commits.

**What was not opened:** the five components this form mounts — the two creation
modals, the two autocomplete inputs and the venue profile prompt — which belong
to plan 41.1-19 running in the same wave on a disjoint file set. The server
actions it calls were read and never edited. Nothing under `scripts/`
(D-41.1-22). No file outside this plan's `files_modified` (D-41.1-19).

**Cross-domain impact, stated before the diff:**

| Domain | The exposure | What was done about it |
|---|---|---|
| Venue secrecy | a control that can only be revealed, never re-hidden; and a layout change can surface an address earlier | the control's three deciding properties enumerated and each asserted unchanged; the reading order of both venue regions extracted from source and diffed |
| Production calendar | a progressivo assigned is already on a poster | the watermark read, its guard and the number field's optionality asserted byte-identical |
| Access and gating | the form is drawn for roles whose write may still be refused | every refusal path kept, and each refusal kept its own sentence |
| Accessibility | three tracks drawn at 24px against a 44px floor, each spelling its own focus suppression | all three adopt the primitive; the focus expression is imported, so it cannot be re-spelled here |

**The recorded todo this plan did NOT fold.** There is an open project todo
about the secrecy flag leaving no trace when it is unticked. It is a
**behaviour** finding. It was not made worse and it was not fixed. What the
conversion learned about it is in *Findings* below.

## The validation grep

**Result: no validation attribute changed meaning.**

The diff filter alone was not enough — it showed a `required` count moving by
two, and both were the word appearing in **prose I had added**. So the check was
done on the multiset instead, computed on the **comment-stripped** source of
both versions:

| attribute | before | after |
|---|---|---|
| `type=` (all forms) | 11 sites | 11 sites, unchanged one for one |
| `required` (bare, as a JSX attribute) | 5 | 5 — the same five fields |
| `required={required}` | 2 | 2 |
| `min={1}` | 3 | 3 |
| `min={DEFAULT_VENUE_REVEAL_HOURS}` | 2 | 2 |
| `maxLength=` (100, 500, 2000, 5000) | 5 | 5 |
| `inputMode="numeric"` | 1 | 1 |
| `accept=` | 1 | 1 |
| `pattern=`, `step=`, `minLength=` | 0 | 0 |

The five bare `required` sites are the same five fields before and after: the
per-night date, the per-night start time, the event title, the event description
and the event date.

**One asymmetry found and deliberately NOT changed.** The per-night **Title**
field is marked with an asterisk and carries **no `required` attribute**. That
is how it arrived. Adding one would change what the browser refuses to submit,
which is validation and not styling, so it was left and is recorded here as a
finding.

**One attribute did move, and it is named.** The asterisk on a required field
was a coloured `<span>` inside the label; the primitive's `label` is a string,
so the asterisk is now a character in the label text. The **character** is
identical, the **tone** is gone. The `required` attribute — the thing that
actually enforces anything — is untouched. Widening the primitive's `label` to
accept a node was refused: that is a spine API change mid-wave, which D-41.1-15
exists to prevent.

## The secrecy control, in three lines

1. **What guards it today:** its default is closed — `defaultSubEvent` sets the
   flag false and the event-level state falls back to false — and **nothing
   else**. It carries no confirmation, no disabled state and no second step, and
   it did not before this plan either.
2. **Each guard survives:** the default is still false on both paths, asserted
   by needle; the absence of a confirmation is unchanged, because adding one
   would be a behaviour change inside a conversion commit and is reported
   instead of performed.
3. **Nothing moved:** the control sits after the venue field and before the
   fields it gates, in both blocks, and the before/after sequences above are
   identical. The hit area grew from 24px to the 44px floor — **a fix for a
   mis-hit, not an invitation**: it makes the control harder to trip *by
   accident*, which is the direction `venue-secrecy.md` permits.

## Deviations from plan

### Auto-fixed

**1. [Rule 2 — Missing critical] Both error regions gained `role="alert"`**
- **Found during:** Tasks 1 and 2
- **Issue:** The form's refusal region and the image refusal were plain
  paragraphs. §11 says *every error region is `role="alert"`*, and this
  repository has **no error tracking** — an error not announced on screen is
  announced nowhere. Task 3's step 7 asks a person to confirm the refusal is
  reachable by a screen reader's alert, which it could not have been.
- **Fix:** `role="alert"` on both. No copy changed, no cause collapsed: the
  three distinct causes reaching the form region keep their three sentences, and
  the image region keeps its two.
- **Committed in:** `3d572e3`, `474238c`

**2. [Rule 2 — Missing critical] The reveal-window sentence became one constant**
- **Found during:** Task 1
- **Issue:** The sentence explaining **when an address leaves this system** was
  written twice, byte-identical. Two copies of a monotone-guard explanation are
  two places for it to drift, and an operator reading the more permissive of two
  floors is a venue-secrecy failure with a typo as its cause.
- **Fix:** `VENUE_REVEAL_HOURS_HELP`, the same move `SERIES_NUMBER_HELP` already
  makes in this file. The floor itself is still imported and never retyped.
- **Committed in:** `3d572e3`

**3. [Rule 2 — Missing critical] The cover-image label bound to its control**
- **Found during:** Task 1
- **Issue:** A `<label>` with no `htmlFor` beside a file input with no `id`. The
  control announced itself as "file upload" and nothing else.
- **Fix:** id added, `htmlFor` added. Both live in this file.
- **Committed in:** `3d572e3`

**4. [Rule 2 — Missing critical] The file input reached the touch floor**
- **Found during:** Task 1
- **Issue:** No minimum on the element, and none on the button the browser draws
  inside it. §6.1's floor is 44px.
- **Fix:** the minimum on both, unprefixed on the element so a gate can read it
  and on the `file:` variant so a finger can land on it.
- **Committed in:** `3d572e3`

**5. [Rule 2 — Missing critical] Five explanatory sentences gained their association**
- **Found during:** Task 1
- **Issue:** Five sentences sat beside their controls with no programmatic link —
  the retired-format note, the unreadable-format note, the unreadable-series
  note, the menu-closing note and the venue-hint note. `Input.tsx`'s `hint` slot
  exists for precisely this, and its own docblock records that the case which
  earned it was a venue-secrecy sentence.
- **Fix:** each becomes the control's `hint`. Same words.
- **Committed in:** `3d572e3`

## Findings — reported, not fixed

Each of these is behaviour or belongs to another plan. None was folded in.

1. **The secrecy control has no confirmation of any kind**, and the flag it sets
   is a monotone guard. It can be flipped in one tap, now on a 44px target. This
   plan did not add one, and did not make it easier to reach. **This is a
   question owed to the owner**, and it is adjacent to — not the same as — the
   recorded todo about the flag leaving no trace when unticked.

2. **`Remove` deletes a night with no confirmation.** `updateEvent` really
   deletes the nights taken off this form, and a night can carry a series
   progressivo that is already on a poster. The control was kept at its existing
   visual weight rather than promoted to the destructive fill, for exactly this
   reason. **Owed to the owner**, not to a conversion.

3. **The per-night Title is starred but not `required`.** The asterisk promises
   a refusal the form does not make.

4. **The two Lineup labels are unbound.** `AutocompleteTagInput` exposes no
   `id`, so there is nothing for a `htmlFor` to name. **Owed to plan 41.1-19**,
   which owns that component. Until then the field has a visible name and no
   programmatic one.

5. **The venue field's label is bound, but the control it names is not this
   plan's.** `AutocompleteInput` accepts an `id`, so the binding works — but
   whether that id reaches the element a screen reader focuses is inside a file
   this plan did not open. **Owed to plan 41.1-19** to confirm.

6. **The number field's refusal moved below its standing sentence.** The
   primitive draws hint then error; the incumbent drew error then hint. The
   `aria-describedby` order is unchanged — failure first — so what a screen
   reader hears is the same and what an eye sees is one line lower.

**No file outside this plan's `files_modified` was reached, and none needed to
be.** D-41.1-19's authorized-list rule did not fire.
