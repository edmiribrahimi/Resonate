<objective>
Build the two instruments before the work they measure, so the phase can be
judged by something other than a claim.

**Instrument 1 — the mechanical assertion.** After the conversions, criterion 1
is a *structural* property: a surface that cannot read the header cannot be
fooled by it. That is worth vastly more than sampling a few pages. Today the
measurement is `grep -rn 'x-user-' src/ | grep -v middleware.ts` → **98 lines**
(97 reads + one stale comment). At the end of the phase it must be **0**, and it
must stay 0 without anybody remembering to look.

**Instrument 2 — the probe.** Criterion 2 demands that a request forging an
identity header is answered exactly as an anonymous one. The obvious probe is
insensitive: `/events` returns the same two slugs forged or not, *and still does
with the middleware strip removed*, because RLS refuses unpublished rows to
`anon` regardless. A probe that has never been shown to fire proves nothing.
The one sensitive surface is measured and named, and the script encodes both
directions.

Purpose: this plan is deliberately in wave 1, before a single conversion. An
instrument written after the change is an instrument shaped by the change.

Output: two committed scripts and one npm entry.
</objective>

  <name>Task 1: scripts/verify-no-header-identity.mjs — the burn-down meter</name>
  <files>scripts/verify-no-header-identity.mjs, package.json</files>
  <action>
Write a zero-dependency ESM node script, node built-ins only, matching the
conventions of `scripts/verify-capabilities.mjs` and `scripts/verify-persona.mjs`
(shebang, a file comment that says what it does NOT prove, exit codes 0 / 1 / 2).

What it asserts: **no file under `src/` other than `src/lib/supabase/middleware.ts`
contains the literal substring `x-user-`.**

Implementation constraints, each with its reason:

- **Use a literal substring match. Do NOT reuse `splitCodeAndComments` from
  `verify-capabilities.mjs`.** WR-07 (`32-REVIEW.md`) records that its comment
  stripper is unsound: a regex literal containing a quote — and one exists at
  `src/app/(auth)/register/page.tsx:13` — opens a phantom string that runs for
  many lines, so line comments inside that span land in the "code" bucket. A
  security assertion built on a parser that an unrelated file can defeat is not
  an assertion. `String.prototype.includes` cannot be defeated by a regex
  literal.
- **Match case-insensitively.** HTTP header names are case-insensitive and
  `headers().get()` is too. More to the point, this repository has a recorded
  incident from exactly this class: `grep -c 'CREATE POLICY' supabase/schema.sql`
  returns **0** while `grep -ci` returns **37**, because `schema.sql` is
  lower-case and the migrations are upper-case — and that discrepancy is the
  origin of the false guardrail D-32-C, which tells readers not to look where 37
  policies are. Lower-case the haystack before the `includes`.
- **Walk `src/` with `fs.readdirSync(..., { withFileTypes: true })`**, skipping
  nothing except directories that do not exist. Do not skip `node_modules` —
  there is none under `src/`. Read every file as utf8; skip binary-looking files
  by extension allow-list (`.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, `.cjs`).
- **The exemption is one exact path**, `src/lib/supabase/middleware.ts`,
  compared as a normalised relative path — not a substring, not a glob. If that
  file is ever renamed (the Next.js `middleware` → `proxy` deprecation is real
  and is deliberately NOT this phase's work), the check fails loudly rather than
  exempting whatever moved into the name. Print the exemption in the output so a
  reader knows the assertion has exactly one hole and where it is.
- **Report, then verdict.** On failure print every offending `path:line:` with
  the trimmed line, then the count, then a sentence naming what it means: a
  surface that reads an inbound identity header is trusting client-supplied
  input, because only `src/lib/supabase/middleware.ts` may set those names.
  Exit 1. On success print the file count scanned and the exemption, and exit 0.

**This check is expected to FAIL until plan 33-14 lands, and that is its
purpose.** Say so in the file comment. It is a burn-down meter during the phase
and a regression guard afterwards. Do not wire it into `npm run build` — the
build is the type gate and must not start failing for a reason unrelated to
types halfway through a phase.

Add to `package.json` scripts: `"verify:no-header-identity": "node
scripts/verify-no-header-identity.mjs"`. Touch no other script and no
dependency.

Finally, prove the check by **mutation**, and assert the mutation applied before
reading any result (`ai-engineering.md`, gate *prova per mutazione*; this
project has a recorded incident of a green from an unapplied mutation):
1. Run it now. It must exit **1** and report **97** reads across **44** files
   plus the one comment at `src/types/database.ts` — 98 lines total, matching
   `grep -rn 'x-user-' src/ | grep -v 'src/lib/supabase/middleware.ts' | wc -l`.
2. Create a throwaway file `src/__probe_header.ts` containing the single line
   `const r = h.get("X-USER-ROLE");` — upper-case, deliberately. Confirm with
   `git status --porcelain` that the file exists, THEN re-run: the count must
   rise by one and the new path must be listed. This proves the
   case-insensitivity, which a lower-case-only check would silently miss.
3. Delete the throwaway file and confirm `git status --porcelain` shows no
   untracked probe before concluding.
  </action>

<task type="auto">
  <name>Task 2: scripts/probe-forged-identity.sh — the criterion-2 procedure, runnable</name>
  <files>scripts/probe-forged-identity.sh</files>
  <action>
Write an executable POSIX shell script (macOS/BSD: `grep -E`, `sed -i ''` if
needed) taking two arguments: a base URL and a published event slug. Usage line
in the header; refuse with exit 2 and a usage message if either is missing.

What it does, in order:

1. `curl -s` the page `${BASE}/events/${SLUG}/menu` **anonymously** → `/tmp/anon.html`.
2. `curl -s` the same URL with all three headers forged →
   `-H 'x-user-role: master' -H 'x-user-status: approved' -H 'x-user-id: 00000000-0000-0000-0000-000000000000'`
   → `/tmp/forged.html`.
3. The observable: `grep -c 'Add Item'` in each. **PASS is both zero.**

Encode the reasons in the script's comments, because the next person to run it
will otherwise pick a different surface and get a meaningless green:

- **Why `(public)/events/[slug]/menu/page.tsx` and no other surface.** It is the
  only header reader that combines all three properties: it is in the `(public)`
  route group so no middleware prefix rule gates it (`protectedPrefixes` is
  `/dashboard /membership-card /attendance /admin /organizer`); its `canManage`
  is decided from the header alone; and the branch that decision selects reads
  through `getServiceClient()`, which bypasses every RLS policy — so there is no
  second boundary behind it. Eight of the nine service-client header readers sit
  behind a middleware capability gate. This one does not.
- **Why `Add Item` and not byte size.** Two anonymous requests to the same URL
  differed by up to 2.3 KB in `next dev` (build ids, RSC nonces). A size
  assertion would be noise. `Add Item` is the management affordance only the
  `canManage` branch renders.
- **Why the `/events` listing is NOT the probe.** Forging `x-user-role: master`
  there produces the same two slugs — *and still does with the middleware strip
  removed* — because RLS refuses unpublished rows to `anon` regardless of what
  `canSeeDrafts` decides. It reports "no difference" because it cannot see one.

Add a **server-action** mode (a third, optional argument: a page path hosting an
action). It discovers the action id from the rendered HTML
(`grep -oE '\$ACTION_ID_[a-f0-9]{40,}'`), then POSTs with `Next-Action`,
`Origin: ${BASE}`, `Content-Type: text/plain;charset=UTF-8`, `--data '[]'` and
the forged headers, printing the status code. Comment the two mechanics that
will otherwise be misread:
- **`Origin` must match `Host` or Next kills the request with `500 Connection
  closed` BEFORE the action body runs.** Someone probing with `curl` and no
  `Origin` will conclude the forge was refused on permission grounds. It was
  not; it never reached the check. This is a second, independent barrier in
  front of every server action, and it is framework-provided — do not weaken it.
- The action id is discoverable from the HTML, which is how this works without a
  browser.

Add a `--positive-control` mode that does not mutate anything itself but prints
the exact mutation procedure and its expected result, so the operator performs
it deliberately:

> Comment out the three `requestHeaders.delete("x-user-*")` lines at
> `src/lib/supabase/middleware.ts:210-212` on a **dev server only**. Confirm the
> mutation is applied (`git diff --stat src/lib/supabase/middleware.ts` must be
> non-empty) BEFORE reading any result — a green from an unapplied mutation is a
> false negative and this project has a recorded incident of exactly that. Re-run
> the probe: `Add Item` must appear in `/tmp/forged.html` and not in
> `/tmp/anon.html`. Restore the three lines from a byte copy and confirm
> `git status --porcelain` is empty. Measured today: with the lines removed the
> forged response gained the management UI and +10 522 B on one live event and
> +23 442 B on the other; restored, the difference is noise.

⚠️ Print a warning at the top of that mode: the mutation removes the single
protection covering all 44 surfaces. Dev server only, reverted in the same
session, never on a deployed environment.

Note in the header that ports 3000 and 3002 are held by Docker on the
development machine (`next dev` auto-selected 3001; `npm start` needed an
explicit `PORT=3007`), which is why the base URL is an argument and not a
constant.

Do NOT run the positive control in this plan. Wave 1 has not converted anything
yet, so a "before" run is worth recording but the mutation belongs with the
phase gate (plan 33-14), where the *after* answer is the one that matters. Run
only the plain probe once, record its output in the summary as the pre-conversion
reference, and `chmod +x` the script.
  </action>
