<objective>
Convert the five top-level pages of the `(organizer)` tree.

Four are ordinary: `role !== "organizer" && role !== "master"` gating a
`redirect("/dashboard")`, plus nav props. One is not — `organizer/events/page.tsx`
uses the header-derived role and id to **narrow a query**:

```ts
if (role === "organizer") {
  query.eq("created_by", userId);
}
```

That is not a refusal, it is a scope. An organizer sees their own events; a
master sees all. Getting the polarity wrong here does not throw and does not
redirect — it silently shows one organizer another organizer's events, or shows
a master nothing. `npm run build` cannot see either.

Purpose: CAP-05 criterion 1 on the `(organizer)` tree's disjoint top level.
Plan 33-08 takes the seven per-event pages; the two file sets do not overlap, so
they run at the same time.

  <action>
Convert the gate at `:19` to `CAP.ORGANIZER_ACCESS` as above, then handle `:31`.

**Before** (`:25-33`)
```ts
// Organizer sees own events; master sees all
const query = supabase.from("events").select(…).order(…);
if (role === "organizer") {
  query.eq("created_by", userId);
}
```

**After**
```ts
// Master sees all; everyone else who reached this page sees their own.
// Expressed as "not master" rather than "is organizer" so the fourth role
// (staff, one phase later) inherits the narrow scope by default rather than
// the wide one. A new role that silently sees every organizer's events is the
// failure this polarity prevents.
if (!capabilities.has(CAP.MASTER_MANAGE)) {
  query.eq("created_by", userId);
}
```

Three things must be settled explicitly, not assumed:

1. **The polarity flip is the point.** Today the condition is *"is organizer"* —
   an allow-list of one. Rewritten as *"is not master"* it is a deny-list, and a
   fourth role added tomorrow lands on the safe side. `ACCESS-MODEL-DECISIONS.md`
   §1-2 says `staff` is coming and grants no work permission; under the old
   polarity a `staff` account that somehow reached this page would see **every**
   event. Under the new one it sees its own, which is none. The truth table for
   the three roles that exist today is identical, which is what criterion 4
   requires.
2. **The key is `MASTER_MANAGE`, and the question is *"may this person manage
   events they do not own"*.** That is the reserved-operation question
   `keys.ts:55` names. Not `ADMIN_ACCESS`, which is the question *"may they
   reach the admin area"* — this page is not in the admin area. The two keys are
   granted to the same role today; they are not the same question.
3. **`userId` may be `null` and `.eq("created_by", null)` is not the same query
   as `.eq("created_by", "")`.** After the capability gate, a caller without a
   session cannot be here — `ORGANIZER_ACCESS` implies an authenticated subject
   — but TypeScript does not know that and neither does a future reader. Add an
   explicit narrowing immediately after the gate:
   ```ts
   if (!userId) redirect("/dashboard");
   ```
   It is unreachable in practice and it is the honest way to make `userId` a
   `string` for the query. Do **not** write `userId ?? ""` here: an empty-string
   filter and a null filter are different requests to PostgREST, and silently
   sending either without saying so is how a list page starts returning the
   wrong set.

Verify the two verdicts by reading, and record them: with `role = master` the
query is unfiltered (`MASTER_MANAGE` held → no `.eq`); with `role = organizer`
the query is filtered to `created_by = <their id>`. Same two outcomes as today,
reached by asking a different authority.
