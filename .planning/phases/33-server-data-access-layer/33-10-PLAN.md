<objective>
Four inline blocks — `createArtist:41-60`, `updateArtist:118-136`,
`createVenue:41-59`, `updateVenue:118-136` — are the same twenty lines with one
word changed. `diff` proved it. There is no named function to delete here, so
"delete the duplicate" means: remove the inline block and call the shared gate.

**And there is a live semantic difference that must not be preserved by
accident, nor changed by accident.**

`artists` and `venues` are the two tables whose RLS policies use
`catalogue.manage`, which carries `requires_approved = true`. The **TypeScript**
check at these four sites tests role only and ignores status; the **RLS policy**
behind them tests status too. That is the measured `organizer/pending`
asymmetry: a pending organizer can insert a `ticket_tier` and is refused on
`venues` with `42501`.

So the four sites currently pass a pending organizer through the TypeScript gate
and let the database refuse them one layer later. Replacing them with
`CAP.CATALOGUE_MANAGE` would refuse them **in the action instead**. The verdict
is the same either way — refused — and *which surfaces each role reaches* does
not change, which is what criterion 4 protects. What changes is the **shape of
the failure**: `Forbidden: only organizers can create venue profiles` becomes
whatever the new path renders.

`32-CARRY-FORWARD.md` §3 calls collapsing `catalogue.manage` and `staff.manage`
*"this model's named worst-case defect"*. The research flagged this as
assumption A4 and said: **flag it to the owner rather than deciding it
silently.** This plan does exactly that, and does nothing until the answer
arrives.

Purpose: criterion 3 on the last inline duplicate family, with the one product
question in it surfaced rather than buried.

Output: two converted files and one recorded owner decision.
</objective>

  <decision>
Which capability key gates `createArtist`, `updateArtist`, `createVenue` and
`updateVenue`: `staff.manage` (status ignored — today's behaviour exactly) or
`catalogue.manage` (approved status required — the same key the RLS policies
behind these tables already use)?
  </decision>
  <context>
Today these four actions test `profile.role !== "organizer" && profile.role !==
"master"` — **role only**. The RLS policies on `public.artists` and
`public.venues` test `catalogue.manage`, which requires `status = 'approved'` as
well as the role.

The result is a two-layer gate where the layers disagree, deliberately:

| Caller | TypeScript gate today | RLS today | What the user sees |
|---|---|---|---|
| `organizer` / `approved` | passes | passes | the artist or venue is created |
| `organizer` / `pending` | **passes** | **refuses `42501`** | a Supabase error surfaces from the write |
| `member` / any | refuses | refuses | `Forbidden: only organizers can create …` |

This asymmetry is **intentional and measured** (`32-CARRY-FORWARD.md` §2):
*"can insert `ticket_tiers`, is refused on `venues` (`42501`); `organizer/approved`
can do both. Reproduce it, do not tidy it."*

**Neither option changes which surfaces any role reaches.** A pending organizer
cannot create a venue today and cannot create one after, under either option.
Criterion 4 is satisfied by both. The difference is entirely in the failure's
shape and in what the model says about itself.
  </context>
  <options>
    <option id="option-a">
      <name>`CAP.STAFF_MANAGE` — preserve today's behaviour exactly</name>
      <pros>
Byte-equal predicate: role ∈ {master, organizer}, status ignored. A pending
organizer still passes the action gate and is still refused by RLS, with the
same `42501` and the same rendered error as today. Zero observable change of any
kind. The lowest-risk possible conversion, and the one most obviously compatible
with "every role still reaches exactly the surfaces it reached before".
      </pros>
      <cons>
It writes the wrong question into the code. The question these actions ask is
*"may this person edit the catalogue"*, and the model already has a key with
exactly that name and exactly the right predicate. Choosing `staff.manage`
because its predicate matches is the substitution `keys.ts:38-45` warns against,
and `32-CARRY-FORWARD.md` §3 calls the collapse of these two keys the model's
named worst-case defect. It also keeps the two layers disagreeing, which means
the refusal a pending organizer sees remains a raw database error rather than a
sentence.
      </cons>
    </option>
    <option id="option-b">
      <name>`CAP.CATALOGUE_MANAGE` — align the action gate with the policy behind it</name>
      <pros>
The TypeScript gate and the RLS policy ask the **same key of the same
authority**, which is the whole point of the capability model. A pending
organizer gets a clear refusal from the action instead of a `42501` leaking out
of a write. The question in the code matches the question being asked. Nothing a
role can reach changes.
      </pros>
      <cons>
The failure shape changes for one persona: `organizer` / `pending` sees a
different message on a path where they see one today. That is owner-visible,
however small, and this phase promised not to change behaviour. It also refuses
earlier, which means the RLS refusal — the thing that actually protects the
table — stops being exercised on that path, so a future regression in the
policy would be masked by the action gate.
      </cons>
    </option>
    <option id="option-c">
      <name>`CAP.STAFF_MANAGE` now, with the divergence recorded as a carry-forward</name>
      <pros>
Ships the mechanical consolidation with zero behavioural risk inside a phase
that is already touching 63 sites, and hands the key question to a phase that
can give it its own before/after evidence — the same treatment D-32-A got for
`profiles_update_own`.
      </pros>
      <cons>
Leaves a known mismatch in place for at least one more phase, and carry-forward
items are how "not now" becomes "not ever".
      </cons>
    </option>

Rules that hold under every option:

1. **Resolve once per action invocation.** `cache()` does not memoise in a
   Server Action body (measured). Four actions × one resolve each is correct;
   two resolves inside one action is the defect.
2. **Delete, do not orphan.** The `auth.getUser()` and the `profiles` select
   existed only to authorise. They go. Where `user.id` is used downstream in the
   same action — check each of the four — it becomes `ctx.userId`, narrowed

3. **`supabase` is still needed** for the actual insert/update. Keep the

4. **Never a role list.**
5. **The four error strings differ only in the noun** ("artist profiles" /
