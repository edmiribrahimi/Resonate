<objective>
Build the one module the other thirteen plans consume, and build it once.

Three things must exist before any surface can stop reading a header:

1. **`user_id` in the `my_access_context()` payload.** Eleven `x-user-id` reads
   need a session-derived identity, and ten of them decide who owns an event.
   The alternative — an extra `supabase.auth.getUser()` inside the resolver — is
   paid on every navigation forever, because the resolver runs on every render.
   The migration widens nothing: it returns the caller's own `auth.uid()`, which
   the caller's own JWT already carries.
2. **`userId` on `AccessContextResult`.**
3. **One ownership function.** Ten sites decide `created_by !== userId` today, in
   three different polarities, with two different Supabase clients. This plan
   writes the single definition; plans 33-07, 33-08 and 33-09 delete the copies.

Purpose: CAP-05 criterion 1 says identity is resolved *in one place*. This is
that place. It already exists (`src/lib/capabilities/server.ts`); a second
resolver module would be the divergent copy criterion 3 exists to delete.

Output: one forward migration, an extended resolver, a new guards module, and a
`CAP-03: clean` verdict on both targets proving the migration moved nothing.
</objective>

<task type="auto">
  <name>Task 3: Write the one ownership definition</name>
  <files>src/lib/capabilities/guards.ts</files>
  <action>
Create `src/lib/capabilities/guards.ts`. It is **not** a second resolver: it
imports `getAccessContext` and asks it questions. Say so in the file comment,
and name CAP-01 as the reason.

Export exactly two things.

**(a) `ownsOrIsMaster(ctx: AccessContextResult, createdBy: string | null | undefined): boolean`**
— pure, synchronous, no round trip. It takes a context the caller has already
resolved and a `created_by` the caller has already fetched, so the eight pages
that use it pay nothing. Order matters and each line has a reason:

1. `if (ctx.capabilities.has(CAP.MASTER_MANAGE)) return true;` — the master
   short-circuit comes FIRST, before any consideration of the row. Two of the
   three current implementations already do this (`if (isMaster) return;`); the
   eight pages express the same truth with the opposite polarity
   (`role === "organizer" && …`). Consolidating on the short-circuit form is the
   safe direction: it means a master's verdict never depends on whether the
   `events` SELECT policy would let them read that row.
2. `if (!ctx.userId) return false;` — **this line is the reason the function
   exists.** The old sites read `headersList.get("x-user-id") || ""`, so an
   absent identity became `""`, and `created_by !== ""` refused. With `userId`
   typed `string | null`, a naive transcription of `created_by !== userId` would
   compare `null !== null` and **admit** on a row whose `created_by` is null.
   Ten separate transcriptions is ten chances to make that mistake. Make it
   once, here, and never again.
3. `if (!createdBy) return false;` — a row owned by nobody is owned by nobody.
4. `return createdBy === ctx.userId;`

Choose `CAP.MASTER_MANAGE` for the short-circuit and record the QUESTION in the
comment, not the predicate (`keys.ts:38-45`): the question is *"may this person
manage an event they do not own"*, which is the reserved-operation question
`master.manage` names, not *"may they reach the admin area"* (`admin.access`).
Three of the eight keys resolve to the same predicate today and picking by
predicate is invisible until phase 35.

**(b) `assertEventOwnership(supabase, eventId, ctx): Promise<void>`** — for the
three server actions that must fetch the row themselves. It short-circuits on
`ownsOrIsMaster(ctx, null)`'s master branch before reading, then reads
`created_by` **with the client it is given** and applies `ownsOrIsMaster`.
Signature takes the client as a parameter rather than creating one, for one
measured reason recorded in `33-RESEARCH.md` § D-4: two of the three call sites
read with the cookie client (RLS applies) and the third reads with the
service-role client (RLS bypassed). Those are not the same read. This function
does not decide which client is correct — plan 33-09 does, with evidence — and a
function that silently picked one would be exactly the phase-32 `event_parties`
trap in a new costume.

On refusal it throws `new Error("forbidden.not_event_owner")`. On a failed read
it throws `new Error("event.lookup_failed")`. Two distinct categories, because
this project has **no error tracking** and a `catch` that collapses "you may
not" with "I could not find out" is the recorded newsletter defect
(`meta-gates.md`, `.planning/codebase/CONCERNS.md`). Add no `catch` of your own.

Add to the file comment: any caller reachable from a client that needs to branch
on the category must carry it as a **tagged value decided by position**, never
by `err.message.startsWith(...)` — Next redacts server-action error messages in
production builds, so string matching works in `next dev` and silently stops
working in the deployment where it matters (CR-01, `32-REVIEW.md`).

Do not export a helper that takes a user id as an argument, and do not export
one that returns a capability `Set` for a caller to pass across a module
boundary as a prop. The first is the enumeration-oracle shape D-04 forbids; the
second is the convention phase 35 would have to pay for, because
`private.has_capability` already carries `p_party_id` while `my_access_context()`
does not. `hasCapability(key)` stays the primary API precisely because
`hasCapability(key, { partyId })` is source-compatible with every call site this
phase writes.
  </action>
