<conversion_contract>
Binding on every task in this plan.

1. **Resolve ONCE per invocation.** `const { capabilities, userId, role, status }
   = await getAccessContext();`. In a **Server Action** `cache()` does **not**
   memoise — measured: three calls executed the underlying function once in a
   page render and **three times** in a Server Action body, identically in
   `next dev` and in a `next build --webpack` production build. Two
   `await hasCapability(...)` calls in one action are two Supabase round trips,
   invisible to `npm run build` and invisible on a fast connection. More than one
   `await hasCapability(` inside a single `"use server"` function is the warning
   sign; use the destructured `capabilities` set instead.
2. **A gate becomes a capability question, never a role list.** Never write
   `["master","organizer"].includes(role)`. A fourth role (`staff`) arrives one
   phase later, and a capability question is automatically fourth-role-safe
   while a role list is not — and a role list would pass review as a tidy-up.
3. **A capability key is chosen by the QUESTION, not by the predicate.** Three
   of the eight keys resolve to the same predicate today and are deliberately
   three keys (`keys.ts:38-45`). Picking the wrong one is invisible until phase
   35 grants one night's door and accidentally grants sixteen tables. Record the
   question you answered, in the code comment and in the commit.
4. **Never `catch` around `getAccessContext()` returning a value.** An empty set
   refuses a master exactly the way it refuses a pending member. If a `try`
   surrounds a `redirect()`, call `unstable_rethrow` first — `redirect()` throws
   `NEXT_REDIRECT` and swallowing it turns a refusal into a rendered fault.
5. **Never branch on `err.message`.** Next redacts server-action error messages
   in production builds. A category that must reach a client is a tagged value
   decided by position (CR-01, `32-REVIEW.md`).
6. Delete the now-unused `headers` import and any `UserRole` / `UserStatus`
   import that nothing else needs. `npm run build` will name them.
</conversion_contract>

```ts
async function requireMaster() {
  const { capabilities } = await getAccessContext();
  if (!capabilities.has(CAP.ADMIN_ACCESS)) redirect("/dashboard");

```

Key choice, and record the question in the comment: the question this file asks
is *"may this person reach the finance surface of the admin area"*.
`admin.access` is exactly that question and is exactly what the middleware
already asks for `/admin/*` (`middleware.ts:172-177`), so the two gates in front
of this file now ask the same question of the same authority instead of one
asking a header and the other asking the database. `master.manage` is the
question *"is this a reserved operation"*, which is a different question about
the same people today and may not be about the same people after phase 35.

`requireMaster()` is called at the head of every exported action. That is **one
resolve per action invocation** — correct and accepted. It must not become two:
do not add a second `await hasCapability(...)` anywhere in this file.

Delete the `headers` import and the `UserRole` import if nothing else uses them.

Everything else in this file is out of scope and must not move: the SumUp
calls, the refund idempotency, the `oldest_ref`/`newest_ref` pagination. This
plan changes **who may call**, not what a call does. `ticketing-payments.md` —
never trust the announcement, stay idempotent, terminal states are monotone —

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → Server Action POST | A Server Action is a public endpoint; a page-level check does not extend into it |
| Next server → SumUp | No RLS, no second boundary — the code is the only gate |
| Next server → Postgres via service client | RLS bypassed by design |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-33-11 | Spoofing | `requireMaster()` reading `x-user-role` in front of SumUp | mitigate | Gate moves to `capabilities.has(CAP.ADMIN_ACCESS)` resolved from the session by Postgres; verified by checkpoint steps 3 and 4 |
| T-33-12 | Elevation of privilege | direct Server Action invocation bypassing the page check | mitigate | `requireMaster()` stays at the head of every exported action — the framework's own instruction is to verify inside each Server Function, not to rely on the proxy |
| T-33-13 | Elevation of privilege | key substitution narrowing or widening the refund gate | mitigate | `STAFF_MANAGE` chosen because its predicate is byte-equal to today's; `admin.access` and `catalogue.manage` rejected in writing with their specific verdict changes |
| T-33-14 | Tampering | refund idempotency or terminal-state monotonicity disturbed | mitigate | The diff is asserted to contain no change to any `sumup` / `refundTransaction` / `getServiceClient` line (task 1 done-criteria, checkpoint step 5) |
| T-33-15 | Repudiation | `requested_by` written as null after `user` is removed | mitigate | `if (!userId) throw` precedes every write; task 2 requires each downstream `user.id` be rewired and checked |
