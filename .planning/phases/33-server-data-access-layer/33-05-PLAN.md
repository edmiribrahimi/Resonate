<conversion_contract>
Binding on every file in this plan.

**Before**
```ts
import { headers } from "next/headers";
import type { UserRole, UserStatus } from "@/types/database";

const headersList = await headers();
const role   = (headersList.get("x-user-role")   as UserRole)   || null;
const status = (headersList.get("x-user-status") as UserStatus) || null;

if (role !== "master") redirect("/dashboard");
```

**After**
```ts
import { getAccessContext } from "@/lib/capabilities/server";
import { CAP } from "@/lib/capabilities/keys";

const { capabilities, role, status } = await getAccessContext();

if (!capabilities.has(CAP.ADMIN_ACCESS)) redirect("/dashboard");
// role / status still flow to <MobileNav role={role} status={status} />.
// Their SOURCE changed; their consumer has not. Phase 34 owns the consumer.
```

Six rules, each with its reason:

1. **`CAP.ADMIN_ACCESS`, and record the question.** The question every one of
   these pages asks is *"may this person reach the admin area"* — which is
   verbatim what `keys.ts:61-62` says `admin.access` is for, and verbatim what
   the middleware already asks for `/admin/*` at `middleware.ts:172-177`. After
   this plan the page gate and the route gate ask the same question of the same
   authority. Do **not** substitute `MASTER_MANAGE` because its predicate
   currently matches: three of the eight keys resolve to the same predicate
   today and are deliberately three keys, and picking by predicate is invisible
   until phase 35.
2. **Never a role list.** `["master","organizer"].includes(role)` and any
   variant is forbidden. A fourth role (`staff`) arrives one phase later; a
   capability question is automatically fourth-role-safe and a role list is not,
   and a role list would pass review as a tidy-up.
3. **Keep `role` and `status` flowing to the nav.** CAP-05 is about the SOURCE,
   not the vocabulary. `MobileNav` and `StaffNav` are `"use client"` components
   and cannot import the DAL; Next.js's own guidance is to resolve in a parent
   Server Component and pass props down. Rewriting them to consume capabilities
   is STAFF-03, **phase 34**, and doing it here turns eight mechanical edits into
   a nav redesign that phase 34 would redo against four roles.
4. **Do not wrap the resolve in `try`/`catch`.** A resolve failure must throw;
   Next's error boundary is the observable effect and the
   `[capabilities.resolve_failed]` line is the diagnosis. `catch { … }` returning
   an empty set refuses a master exactly the way it refuses a pending member.
   Note that `cache()` caches errors, so within one render the failure is
   consistent and not retryable — which is correct, and worth knowing before
   someone writes a retry.
5. **Delete the `headers` import and any now-unused `UserRole`/`UserStatus`
   import.** `npm run build` will name them. A dead import is the "left unused"
   that criterion 3 rejects.
6. **In a page, `cache()` DOES memoise**, so several capability questions in one
   render cost one round trip. This is the one context where the convenience
   form is free. Even so, prefer the single destructure — it is the form that
   stays correct when a block of code is later moved into an action.

**Behaviour equivalence, argued and checkable.** For an anonymous caller
`getAccessContext()` returns `ANONYMOUS_CONTEXT` — empty set, `role: null`,
`status: null` — so `!capabilities.has(...)` redirects to `/dashboard`, which the
middleware turns into `/login`. Today `role` is `null` from the header and
`role !== "master"` produces the same `redirect("/dashboard")`. Same two hops,
same destination. These pages are additionally unreachable anonymously because
`/admin` is in `protectedPrefixes`.
</conversion_contract>

`headersList.get("x-user-id") || ""` — `string`. `getAccessContext().userId` is
`string | null` (33-01, deliberately: `null` is the honest answer for "there is

everything). Read what `currentUserId` is used for in the receiving component
