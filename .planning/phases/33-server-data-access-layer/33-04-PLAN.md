<objective>
Consolidate the door onto one authorisation function, and make a scan cheaper
while doing it.

Two facts shape this plan and both are measured.

**The door has no decisional header readers.** `admin/scanner/page.tsx` reads
`x-user-role` only to hand `role`/`status` to `<MobileNav>`; the page renders
`<ScannerClient />` unconditionally, and the gate is the middleware's
`door.operate` rule. It is the lowest-risk file in the entire census despite
sitting on the highest-consequence path. Do not treat it as Critical and do not
serialise it.

**The four check-in routes are four copies of one predicate.** They authenticate
with `supabase.auth.getUser()` **and** a `public.profiles` select — two network
calls before a scan resolves — and then test `role ∈ {master, organizer}`.
`public.my_access_context()` derives the subject from `auth.uid()` inside the
JWT and needs neither. Converting to `CAP.DOOR_OPERATE`, resolved **once**, is
round-trip *negative*: one fewer call before a scan, on a phone, on a bad
network, in front of a queue.

`src/app/api/tickets/checkin/route.ts:110-130` carries the owner decision this
plan must preserve verbatim: *"Role decides the door. Status does not … The three
other door routes must stay identical: the same person refused by one scanner
and admitted by another, on the same night, is undiagnosable with no error
tracking anywhere in this repository."* Consolidating the four into one function
is the strongest possible form of that requirement — after this plan they cannot
diverge, because there is only one of them.

Purpose: criterion 3, on the family that matters most. Wave 2, parallel — these
files belong to no other plan.

Output: one door authorisation function, six converted files, and a manual
procedure run with the network off.
</objective>

<conversion_contract>
1. **Resolve ONCE per request.** `cache()` does **not** memoise inside a Route
   Handler — measured: three calls executed the underlying function three times
   in a Route Handler, identically in `next dev` and in a production build.
   `requireDoorOperator()` is called once at the top of a handler and its result
   is reused. Two `await hasCapability(` calls in one route are two round trips.
2. **A gate is a capability question, never a role list.** A fourth role
   (`staff`) arrives one phase later, and `ACCESS-MODEL-DECISIONS.md` §2 says
   `staff` gets **no** work permission and specifically **not** `door.operate`.
   `["master","organizer"].includes(role)` would be exactly the enumeration that
   breaks then, and it would pass review as a tidy-up.
3. **Never `catch` around `getAccessContext()` returning a value.** An empty set
   refuses a master exactly the way it refuses a pending member.
4. **Never branch on `err.message`.** The category is a value decided by
   position (CR-01).

Create the module alongside `@/lib/door/outcome`, which is where the door's own
vocabulary already lives.

Export one function returning a **tagged union decided by position**, never by a
parsed message:

```ts
export type DoorAuth =
  | { ok: true; userId: string }
  | { ok: false; kind: "unauthenticated"; error: string; status: 401 }
  | { ok: false; kind: "forbidden";       error: string; status: 403 }
  | { ok: false; kind: "unresolved";      error: string; status: 503 };

export async function requireDoorOperator(): Promise<DoorAuth>;
```

Body, in this exact order, each line with its reason:

1. `let ctx; try { ctx = await getAccessContext(); } catch { return { ok:false,
   kind:"unresolved", … } }` — **this is the one place in the phase where a
   `catch` around the resolver is correct, and it is correct only because it does
   not return a permission answer.** It returns a fourth, distinct outcome. The
   rule that stands everywhere else — never `catch { return false }` — is about
   collapsing "could not find out" into "not permitted". This does the opposite:
   it keeps them apart. `server.ts` throws precisely so that a caller *can* tell
   them apart, and the door is the caller that must. Write that reasoning into
   the comment, or the next reader will delete the `catch` on principle.
   The `catch` must NOT inspect the error message. It is entered by position.
2. `if (!ctx.userId) return { ok:false, kind:"unauthenticated", error:"Unauthorized",
   status:401 }` — preserves the current 401. Today the routes return 401 when
   `auth.getUser()` yields no user; `ctx.userId` is null in exactly that case,
   because `ANONYMOUS_CONTEXT.userId` is `null` (33-01).
3. `if (!ctx.capabilities.has(CAP.DOOR_OPERATE)) return { ok:false,
   kind:"forbidden", error:"Forbidden", status:403 }` — preserves the current
   403 and its body string.
4. `return { ok:true, userId: ctx.userId }`.

**Key choice — `door.operate`, and nothing else.** The question is *"may this
person work the door tonight"*. `keys.ts:65-66` names this key for exactly the
middleware `/admin/scanner` rule and these four routes, **role alone**. Its two
grant rows carry `requires_approved = false` and
`supabase/migrations/20260807000000_capability_model.sql:416-417` comments
*"These two rows must not become true."* A status check here locks a `pending`
organizer out of the scanner in front of a queue — the failure
`checkin-offline.md` names as the worse of the two. `staff.manage` resolves to
the same predicate today and would be the wrong key: phase 35 must be able to
grant one night's door without granting sixteen tables.

**Do not add a status check. Do not add one "for consistency". Do not add one
because the two axes look uneven.** The unevenness is the decision.

**503, not 500, for `unresolved`** — and check this against
`src/lib/offline/sync-manager.ts` before committing. That file classifies HTTP
status into buckets (`:97-133`): `401 || 403 → blocked`, `408 || 429 → …`. Read
the full table and choose the code whose bucket means **retryable**, so a
capability lookup that failed at 02:00 is retried when the network returns
rather than being filed as a permanent refusal. If the table's retryable bucket
is a different code, use that code and say so. Record the bucket you landed in.

**The observable effect.** This project has **no error tracking** — a logged
error reaches nobody (`meta-gates.md`). `checkin-offline.md`, gate *il
fallimento va visto*: every check-in error path must show itself to the staff on
the spot, the only observer who really exists. So the `unresolved` branch must
carry a body the scanner can render as something other than "not authorised" —
at 02:00 the difference decides whether staff reboot the phone or fetch a
different account. Give it a distinct `error` string and a distinct machine-
readable field, and check `src/app/(admin)/admin/scanner/ScannerClient.tsx` for
where a non-2xx body is surfaced. If the scanner would today render this new
outcome as a generic failure, **say so in the summary as a named gap** rather
than silently shipping a fourth outcome nobody can see.

`console.error` the unresolved case with a category prefix
(`[capabilities.resolve_failed] door`), knowing the log is the diagnosis and not
the notification.

⚠️ **The status assertion below filters comment lines, and that is deliberate.**
The module's own comment must explain `requires_approved = false`, so an
unfiltered `grep -c 'requires_approved'` would count the explanation and fail on
a correct file — a check that is self-invalidating the moment someone documents
the decision it protects. Filter the comments, then count the code.
