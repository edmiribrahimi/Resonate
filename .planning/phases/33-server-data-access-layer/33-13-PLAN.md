<objective>
Convert the last five database-sourced permission predicates, in three files
that share nothing with any other plan.

Two of them are ordinary. The third contains the phase's most instructive
near-miss.

**`admin/members/actions.ts` holds `verifyMaster` (`:45-67`) and
`verifyAdminOrOrganizer` (`:73-95`), and they are NOT duplicates.** Their
preambles are identical — twenty lines of `getUser()` + `profiles` select — and
that identity is what makes them look mergeable. They differ in the one line
that matters: `profile.role !== "master"` versus `profile.role !== "master" &&
profile.role !== "organizer"`, and they map to two different capabilities. Three
actions call the first (role change, deactivate, reactivate); four call the
second (approve, reject and two more). **Merging them would hand every organizer
the power to change roles**, which is the exact ceiling
`ACCESS-MODEL-DECISIONS.md` §6 puts in place: *"An organizer may promote staff →
organizer. An organizer may NOT create a master … a self-replicating power must
not reach the top."*

Criterion 3 says duplicates are deleted. These are not duplicates. What is
duplicated is the **preamble**, and the preamble is what disappears.

Purpose: criterion 3 on the remaining predicate sites, with the one pair that
must survive as a pair explicitly protected.

Output: three converted files, seven call sites intact, two functions still two.
</objective>

<conversion_contract>
1. **Resolve ONCE per action invocation.** `cache()` does **not** memoise in a
   Server Action body — measured, three executions for three calls, in both
   build modes. More than one `await hasCapability(` in one `"use server"`
   function is the warning sign.
2. **A server action is a public endpoint.** Every exported action keeps its own
   gate; a page-level check does not extend into it.
3. **Never a role list.** `staff` arrives one phase later.
4. **Never `catch` around the resolver returning a value.**
5. **Never branch on `err.message`** anywhere reachable from a client — Next
   redacts server-action messages in production builds.
6. **Delete, do not orphan.** The `getUser()` + `profiles` select that existed
   only to authorise must go. Where `user` is used downstream, it becomes
   `ctx.userId`, narrowed non-null by an explicit throw rather than by a `!`.
</conversion_contract>

Two sites.

**`:124-136`, media moderation.** The predicate is role ∈ {master, organizer}
and the error is `"Forbidden: only organizers can moderate media"`. Replace with
`assertStaffManage()` from `@/lib/capabilities/guards.ts`.

Key justification: `CAP_DESCRIPTIONS["staff.manage"]` names **media moderation**
by hand, and its predicate — role ∈ {master, organizer}, status ignored — is
byte-equal to today's. `CATALOGUE_MANAGE` would require approved status and
refuse a pending organizer who moderates today; `ADMIN_ACCESS` would narrow to
master. Both are verdict changes and criterion 4 forbids them.

**`:180-196`, `deleteMedia`, and this one has a shape that must survive.** The
current logic is: fetch the media row; **if the caller is the uploader, allow**;
otherwise require the staff role. So a member can delete their own upload and
nobody else's.

```ts
if (media.uploaded_by !== user.id) {
  …profiles read…
  if (profile.role !== "organizer" && profile.role !== "master") {
    throw new Error("Forbidden: you can only delete your own media");
  }
}
```

Rewrite as:

```ts
const ctx = await getAccessContext();
if (!ctx.userId) throw new Error("Not authenticated");
…fetch media…
if (media.uploaded_by !== ctx.userId && !ctx.capabilities.has(CAP.STAFF_MANAGE)) {
  throw new Error("forbidden.staff_manage_required");
}
```

⚠️ **Three things about this rewrite.**
- The `getAccessContext()` call replaces the existing `auth.getUser()` **and**
  the conditional `profiles` read — a member deleting their own upload now pays
  one round trip instead of one, and a staff member deleting someone else's pays
  one instead of two.
- `ctx.userId` is `string | null`. `media.uploaded_by` may also be null. The old
  form compared `user.id` (never null past the auth guard) against
  `uploaded_by`. The explicit `if (!ctx.userId) throw` above restores that
  property; do **not** remove it "because the capability check covers it" — the
  ownership arm runs when the capability arm is false, and that is exactly the
  path where a null-equals-null admission would happen.
- The short-circuit order matters for cost: `uploaded_by !== userId` is a local
  comparison and `capabilities.has` is a `Set` lookup on an already-resolved
  context, so both are free. Keep the ownership test first because it is the
  common case and it reads as the rule the code is expressing.

⚠️ Media touches `media-and-storage.md` and, indirectly, `venue-secrecy.md`
(an uploaded photo can show a venue). This plan changes who may moderate or
delete, not what is stored or shown. The diff must contain no change to a
storage path, a bucket, or a URL.

Rewrite both function bodies. **Keep both functions. Keep both names. Keep all
seven call sites.**

```ts
// Master-only: role management, deactivate, reactivate.
async function verifyMaster(): Promise<AccessContextResult> {
  const ctx = await getAccessContext();
  if (!ctx.capabilities.has(CAP.MASTER_MANAGE)) {
    throw new Error("forbidden.master_manage_required");
  }
  if (!ctx.userId) throw new Error("capabilities.resolve_failed: no_subject");
  return ctx;
}

// Master or organizer: approve / reject.
async function verifyAdminOrOrganizer(): Promise<AccessContextResult> {
  const ctx = await getAccessContext();
  if (!ctx.capabilities.has(CAP.STAFF_MANAGE)) {
    throw new Error("forbidden.staff_manage_required");
  }
  if (!ctx.userId) throw new Error("capabilities.resolve_failed: no_subject");
  return ctx;
}
```

The `supabase` parameter both currently take exists only to run the `getUser()`
+ `profiles` read. Drop it, and update the seven call sites (`:107`, `:146`,
`:168` for the first; `:188`, `:222`, `:256`, `:301` for the second). The
callers that use the returned `user` — `:107` and `:146` — now use `ctx.userId`.

**Why two keys and not one, recorded in the code:**
- `verifyMaster` → **`CAP.MASTER_MANAGE`**. The question is *"is this a reserved
  operation"*, and `CAP_DESCRIPTIONS["master.manage"]` names *"changing another
  member's role or status"* by hand. This is the ceiling from
  `ACCESS-MODEL-DECISIONS.md` §6. `ADMIN_ACCESS` resolves to the same predicate
  today and is the wrong question — it is *"may they reach the admin area"* —
  and the two will part company when phase 34 collapses the admin and organizer
  trees into one surface.
- `verifyAdminOrOrganizer` → **`CAP.STAFF_MANAGE`**. The question is *"may this
  person manage a staff surface"*, and approving or rejecting a membership
  request is one. Predicate byte-equal to today's.

**Do not merge them.** They are the phase's clearest example of two functions
whose bodies look identical and whose one differing line is the whole point.
Write that sentence into the file, above the pair, so the next reader who runs
`diff` on them reaches the right conclusion.

⚠️ **`updateMemberRole` (`:102-141`) must not be touched below its guard line.**
It carries the owner decision of 2026-08-06 in a comment block: granting
`organizer` approves the account in the same write, and demotion does **not**
revoke approval because `member` and `approved` are different axes. That block
is also where the door's escalation hole is closed
(`32-CARRY-FORWARD.md` §1). The only line this plan changes in that function is
`const user = await verifyMaster(supabase);` → `const ctx = await verifyMaster();`
plus the `memberId === user.id` comparison becoming `memberId === ctx.userId`.
Everything else, including the comment, stays byte-identical.

⚠️ **Attribution.** `ACCESS-MODEL-DECISIONS.md` §5 requires approval, rejection
and role promotion each to record **who** and **when**. Whatever these actions
write today for attribution keeps receiving a real subject id — which is why the
`if (!ctx.userId) throw` sits inside both verify functions rather than at each
call site. If any of the seven actions writes an attribution column, name it in
the summary and confirm it still receives a non-null value.
