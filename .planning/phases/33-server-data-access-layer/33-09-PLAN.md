<measured_evidence>
**On whether the guest-list ownership read may move to the cookie client
(assumption A3 of the research, left open there):**

The phase-32 container read matrix
(`.planning/phases/32-capability-model-in-the-database/baseline/32-BASELINE-reads.container.final.json`)
records, for `public.events`:

| persona | rows read through RLS |
|---|---|
| `master/approved` · `master/pending` · `master/rejected` | 2 of 2 |
| `organizer/approved` · `organizer/pending` · `organizer/rejected` | **2 of 2** |
| `member/*`, `anon`, `authenticated/no-profile` | 0 |

So on the container an organizer reads every `events` row through the cookie
client, and a cookie-client read of `created_by` would return the same value the
service client returns. **That is evidence, not proof of the production case:**
the same file for the production target records `organizer/*` as
`resolved: false` — no such account exists there — so the production read matrix
says nothing about an organizer, and the two targets' `events` fixtures differ
(container `anon` reads 0, production `anon` reads 2).

**The decision this plan takes: do not swap the client.** Reasons, in order:
1. Criterion 4 says every role still reaches exactly the surfaces it reached
   before. A client swap changes which rows the ownership read can see, and the
   evidence for equivalence exists on one target out of two.
2. The difference between the three functions is real and this plan's job is to
   make it **visible**, not to erase it. `assertEventOwnership` takes the client
   as an argument precisely so the divergence lives in one legible line at each
   call site instead of in three function bodies.
3. Consolidating a service-role read onto a cookie client is a security-relevant
   change with its own evidence burden. It is worth doing; it is not worth doing
   inside a 63-site transport swap.

Record it as a carry-forward item with this evidence attached, so the next phase
does not re-derive it.
</measured_evidence>

<conversion_contract>
1. **Resolve ONCE per action invocation.** `cache()` does **not** memoise inside
   a Server Action body — measured, three executions for three calls, in
   `next dev` and in a production build alike. `assertStaffManage()` returns the
   context so it can be passed to `assertEventOwnership`. **Never** call
   `getAccessContext()` or `hasCapability()` a second time in the same action.
   More than one `await hasCapability(` in a single `"use server"` function is
   the warning sign.
2. **A server action is a public endpoint.** Next.js states it directly:
   *"A page-level authentication check does not extend to the Server Actions
   defined within it. Always re-verify inside the action."* Every exported action
   in these three files keeps its own gate.
3. **Never a role list.** `staff` arrives one phase later.
4. **Never `catch` around the resolver returning a value.**
5. **Never branch on `err.message`** anywhere reachable from a client.
</conversion_contract>

  <name>Task 1: Add the one staff-surface gate to guards.ts</name>
  <files>src/lib/capabilities/guards.ts</files>
  <action>
Add one export:

```ts
/**
 * The staff-surface gate: events, parties, ticket tiers, drinks, guest lists,
 * media moderation. Returns the resolved context so the caller can pass it on
 * WITHOUT paying a second round trip — cache() does not memoise in a Server
 * Action body (measured).
 */
export async function assertStaffManage(): Promise<AccessContextResult> {
  const ctx = await getAccessContext();
  if (!ctx.capabilities.has(CAP.STAFF_MANAGE)) {
    throw new Error("forbidden.staff_manage_required");
  }
  return ctx;
}
```

**Key choice — `staff.manage`, and record the question.** The question these
call sites ask is *"may this person manage a staff surface"*.
`CAP_DESCRIPTIONS["staff.manage"]` names events, parties, tickets, tiers,
drinks and guest lists by hand, and its predicate is role ∈ {master, organizer}
with status ignored — **byte-equal to today's** `profile.role !== "organizer" &&
profile.role !== "master"`, so no role's reach changes. The stronger argument:
the RLS policies behind these very tables already call
`private.has_capability('staff.manage')` (family P1, the 34 policies that gated
on `is_admin_or_organizer()`), so after this change the TypeScript gate and the
row-level gate ask **the same key of the same authority** rather than two
predicates that happen to agree.

Rejected, in writing:
- `ORGANIZER_ACCESS` — the question *"may they reach the organizer area"*, a
  routing question. These actions are not a route; a Server Action is a POST to
  whatever route hosts it, and a matcher change can remove proxy coverage
  without touching the action.
- `CATALOGUE_MANAGE` — `requires_approved = true`. A `pending` organizer manages
  events and tiers today; this key would refuse them. Verdict change.
- `MASTER_MANAGE` — would lock every organizer out of their own events.

**On collapsing the error strings.** D-1 and D-2 differ *only* in prose
(`"…manage events"` / `"…manage ticket tiers"`; `"…your own events"` / `"…tiers
for your own events"`). Collapsing four prose variants into two stable
categories is free and is an improvement, for a measured reason: **Next redacts
the message of an error thrown out of a Server Action in a production build**
(CR-01), so those four strings are already invisible in the deployment that
matters and exist only in `next dev`. A stable category (`forbidden.*`) is more
useful to the one person who will ever read it than four prose variants that
production erases. State this in the commit — otherwise the diff reads as a lost
diagnostic.

Do not add a `catch`. Do not add a message parameter. Do not export anything
that takes a user id as an argument (the D-04 enumeration-oracle shape), and do
not export anything that hands a capability `Set` across a module boundary as a
prop convention — `hasCapability(key)` stays the primary API because
`hasCapability(key, { partyId })` is source-compatible with every call site this
phase writes, and phase 35 will need exactly that.

- `events/actions.ts`: `:245`, `:320/:322`, `:443/:445`, `:472/:474`,

- `tickets/actions.ts`: `:85/:87`, `:149/:151`, `:200/:202`, `:246/:248`,

**Round-trip arithmetic, which is the reason to do this carefully.** Today each
`verifyOrganizer` costs `auth.getUser()` **plus** a `profiles` select — two
network calls — and a paired `verifyEventOwnership` adds a third for a
non-master. After conversion an invocation costs **one** `my_access_context()`
call plus, for a non-master, one `events` read. That is a halving, and it holds
**only** if `ctx` is threaded through instead of re-resolved. If you find
yourself writing `await assertStaffManage()` twice in one exported action, stop:
that is two round trips, invisible to `npm run build`, invisible on a fast
connection, and the exact defect P-1 names.

**`user.id` downstream.** Several call sites use the returned `user` after the
guard — `created_by` on an insert, `requested_by`, an audit column. Those become
`ctx.userId`, which is `string | null`. `assertStaffManage()` throws unless the
caller holds `staff.manage`, which implies an authenticated subject, so `userId`
is non-null in practice — but TypeScript does not know it. Narrow it once, right
after the guard, with an explicit `if (!ctx.userId) throw new
Error("capabilities.resolve_failed: no_subject");` rather than sprinkling `!`
assertions. `ACCESS-MODEL-DECISIONS.md` §5 makes attribution a requirement; a
`!` that is wrong writes a null into an attribution column and nothing tells
anybody.

**`reorderDrinkItems` (`events/actions.ts:925-942`) has a fifth, inline copy** of
the ownership check — `if (!isMaster) { …fetch…; if (… || event.created_by !==
user.id) throw }`. Replace it with `assertEventOwnership(supabase, eventId, ctx)`
too. It is inline rather than named, so "delete the duplicate" here means remove
the inline block and call the shared function.

`events/actions.ts` also uses `getServiceClient()` in places (e.g. the
`drink_items` writes at `:946+`). Do not change any of those. This plan changes
who may call, not what a call does.

Replace the function body:

```ts
async function verifyOrganizerAccess(eventId: string): Promise<string> {
  const ctx = await assertStaffManage();

```
