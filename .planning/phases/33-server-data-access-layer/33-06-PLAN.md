`role !== "master"` gating a `redirect("/dashboard")`, plus nav props — with

row-level policy: `[id]/tickets/page.tsx`, `[id]/sales/page.tsx` and

`verifyOrganizer` + `verifyEventOwnership`. That file is converted by plan 33-09.

path, and criterion 4 says every role reaches exactly what it reached before.

<conversion_contract>
**Before**
```ts
const headersList = await headers();
const role   = (headersList.get("x-user-role")   as UserRole)   || null;
const status = (headersList.get("x-user-status") as UserStatus) || null;
if (role !== "master") redirect("/dashboard");
```
**After**
```ts
const { capabilities, role, status } = await getAccessContext();
if (!capabilities.has(CAP.ADMIN_ACCESS)) redirect("/dashboard");
// role / status still flow to the nav. Source changed, consumer did not.
```

1. **`CAP.ADMIN_ACCESS`** — the question is *"may this person reach the admin
   area"*, which is what `keys.ts:61-62` names and what `middleware.ts:172-177`
   already asks for `/admin/*`. Not `MASTER_MANAGE` (a different question about
   the same people today, and possibly not the same people after phase 35).
2. **Never a role list.** A fourth role arrives one phase later.
3. **Keep `role`/`status` flowing to `<MobileNav>` / `<StaffNav>`.** They are
   client components and cannot import the DAL. Phase 34 (STAFF-03) owns them.
   Do not redesign the nav here.
4. **No `try`/`catch` around the resolve.** A failure throws; the error boundary
   is the observable effect. `catch` returning an empty set refuses a master
   exactly the way it refuses a pending member.
5. **Delete the `headers` import and any orphaned `UserRole`/`UserStatus`
   import.** A dead import is the "left unused" criterion 3 rejects.
6. In a page, `cache()` memoises, so several questions in one render cost one
   round trip. Still prefer the single destructure.
</conversion_contract>
